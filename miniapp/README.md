# Mini App

The editor opened from the bot's `web_app` button: `<pages url>?job=<id>`. React (JS) + Vite SPA, plain CSS, `arch-features.md` layout under `src/`. API contract: `backend/rounds/README.md` (coordinates 0..1 of the display-oriented frame, times in seconds with ms precision).

Run locally without Telegram or the backend: needs the owner's local `dev/` folder (Dev plugin). With it: `npm install`, `npm run mock` (test video, needs `ffmpeg`), `npm run dev` with `VITE_API_URL` unset, open `/` for the browser version or `/?job=ready` for the Mini App; scenarios and the rest are in `dev/README.md`.

On the phone before a deploy: the page needs HTTPS there (WebCodecs, `crypto.subtle` and the Cache API exist only in a secure context, so `vite --host` on `http://192.168.x.x` opens the page but no video), so put a Cloudflare quick tunnel in front of the local server. Once: `winget install --id Cloudflare.cloudflared`. Then in `miniapp/`, PowerShell: `$env:__VITE_ADDITIONAL_SERVER_ALLOWED_HOSTS = '.trycloudflare.com'` (Vite answers 403 to an unknown `Host` otherwise), then `npm run dev` (source, edits reload the page) or `npm run build; npx vite preview --port 5173` (the production bundle, what Pages will serve: use it for chunk, CSS and Safari-syntax problems), and in a second terminal `cloudflared tunnel --url http://localhost:5173`; open the printed `https://<words>.trycloudflare.com/` in Safari on the phone. The browser version (`/`) works fully there (probe, lift, track, local render). Calls to the real API do not: the backend allows CORS only from `MINIAPP_URL` (`backend/rounds/api.py`), so sign-in and server steps need the deployed page; `/?job=ready` uses the mock API under `npm run dev` only.

## Dev plugin

Owner decision 2026-10-26: no mock or local-test code in the repo or the build. All of it (Vite plugin, Telegram shim, mock API, test media generator and its output, its README) lives in `miniapp/dev/`, which is gitignored and exists only on the owner's PC. The repo knows only the hook in `vite.config.js`: if `dev/plugin.js` exists it is imported (through a computed URL, so the config bundler does not try to resolve a file CI does not have) and added to `plugins`; the plugin's own `apply` limits it to `vite` / `vite preview` and `vite build --mode mock`. A plain `vite build` has no trace of it (checked 2026-10-26: no `mock`, `__dev` or `Load video` in `dist/`), and CI has no `dev/` at all.

`src/services/api.js` has no mock branch: it requests `VITE_API_URL + path`, and an unset variable means the same origin, where the dev client answers the calls (`src/services/README.md`, API URL). `package.json` keeps `mock` (`node dev/mock-media.mjs`) and the `--mode mock` of `perf`: paths and a mode name, no mock code; on a clone without `dev/` they fail with a missing file.

## Relative base

`base: './'` in `vite.config.js`: the build works under any GitHub Pages project subpath and from `vite preview` without knowing the repo name. Safe because the app has one route; state lives in the query (`?job=`), and Telegram appends its launch data to the hash (`#tgWebAppData=…`), which only the launch router reads (Launch router); the app itself uses `Telegram.WebApp.initData`.

## Build target

`build.target` is `safari18` + `chrome130` + `firefox131` (the autumn 2024 releases of each engine). The Mini App runs in Telegram for iOS 18+ (WKWebView, the Safari 18 engine) and Telegram Desktop on Windows (lib_webview, which picks WebView2, evergreen Edge Chromium, and falls back to EdgeHTML only without the WebView2 runtime: `webview/platform/win/webview_win.cpp` in desktop-app/lib_webview, read 2026-10-25). The browser version (owner decision 2026-10-27) runs in current Safari (macOS, iOS), Chrome and Edge (desktop, Android) and Firefox; no legacy browsers. So no syntax lowering, no CSS prefixes, and `modulePreload.polyfill` is off (every target supports `modulepreload`). Raising the target saved 0.3 KB gzip: the bundle was already modern; its weight was React DOM (Preact, below). Adding `firefox131` changed nothing in the output (2026-10-27: inlined CSS byte-identical, chunks identical up to hashes and export names).

## Preact

The app runs on Preact 10 with the React API of `preact/compat` (owner decision 2026-10-25, overrides react.md): the production entry chunk went from 75.5 to 15.0 KB gzip (15.5 in the mock build), which was the "Reduce unused JavaScript" item of PageSpeed. The source keeps importing `react` and `react-dom/client`; `resolve.alias` in `vite.config.js` points them at `preact/compat` and `preact/compat/client`, and Vite's own oxc transform compiles JSX for `preact` (no `@vitejs/plugin-react`, so no Fast Refresh: an edit reloads the page in dev). The `react` import is deliberate: oxlint's `react` plugin recognizes hooks by their import source, and with `preact/hooks` imports it reported every `ref.current =` as a mutation of a hook value (`react(immutability)`). `@preact/preset-vite` was not used: its peer range rejected Vite 8 (npm ERESOLVE, 2026-10-25).

Differences that matter here:

- No `useEffectEvent` (not exported by `preact/compat` 10.29): a handler an effect reads goes into a ref updated by a layout effect.
- No `StrictMode` (a Fragment in compat), so effects are not double-invoked in dev.
- Renders are batched to a microtask even for discrete events (React flushes a click or a keydown synchronously): code that reads the DOM right after a `dispatch` sees the old render. Nothing in the app does; a test must wait a tick.
- `onChange` of a text input is mapped to `input` by compat (as in React); the app has only a checkbox, where both fire on click.

Checked on the mock build in headless Edge (2026-10-25): load, tap to add a point, option switch, play / pause, arrow keys on a trim handle, submit through the mock MainButton with the current draft; no console errors.

## Inline CSS

The `inline-css` plugin in `vite.config.js` replaces the built `<link rel="stylesheet">` in `index.html` with a `<style>` of the same file and drops the file (web.md: no stylesheet request blocks the first paint). Only CSS linked from the page is inlined; a CSS file of a lazy chunk would stay a file, since its chunk links it at runtime. The page grows to 3 KB gzip and has the same 10-minute cache as the CSS had.

The built head order is: charset, viewport, title, icon, the theme `<style>` of `index.html` (Vite minifies it in place, dev serves it as written), the launch router (it writes the Telegram script and the Mini App module, or appends the web module: Launch router), the `modulepreload` of the shared chunk, the inlined app CSS (Vite puts its `<link>` before `</head>`). The colours paint from the theme style before any app CSS or JS (`src/README.md`, Theme tokens); the app CSS needs no particular place, since the module scripts are deferred or async and `#root` is empty until they run.

The inlined CSS is the CSS of the HTML entry (`main.jsx` and the shared chunk), so both branches get it. CSS imported only by `web.jsx` would not be linked by anything: Vite links the CSS of the HTML entry only and emits a JS entry's CSS as an orphan file. Web-only styles therefore go in through `?inline` and a `<style>` the web entry adds before its first render (no extra request, no unstyled frame).

- `web.jsx` must not import `index.css` statically: a CSS module imported by both entries goes to the shared chunk's CSS file, every lazy chunk (`look-*.js`) then lists that file as a preload dependency (`__vite__mapDeps`), and `inline-css` has deleted it, so the Mini App requested a missing `api-*.css` when the look preview loaded (seen 2026-10-27, CDP request list of the mock build; a failed CSS preload also fires `vite:preloadError`). The built page already has `index.css` inlined for both branches, so `web.jsx` loads it only under `import.meta.env.DEV` (dev injects CSS from JS, and `main.jsx` does not run there). After a change to the entries, check that no `.css` name appears in `dist/assets/*.js`.

## Theme tokens

The inline `<style>` in `index.html` is the single home of the colour tokens and of the page background, so the first paint has the right colour in dev and in the build: `src/README.md`, Theme tokens. It sits before the Telegram script so it is parsed while that script downloads (its `var(--tg-…)` resolve whenever the script sets them); keep it free of anything but colours.

## Favicon

`<link rel='icon' href='data:,'>` in `index.html`, no icon file. No client of the app shows a favicon (Telegram iOS and Telegram Desktop open it without a tab), but without any icon link Chromium requests `/favicon.ico` by itself: headless Edge 154 on a test server fetched it and logged `Failed to load resource: 404` in the console (a Lighthouse best-practices failure); with `data:,` it made no request and logged nothing; with the former `favicon.svg` it made one request (2026-10-26). WebView2 shares Edge's browser layer, so the same is expected there (reasoned, not run in Telegram Desktop). Under GitHub Pages `/favicon.ico` is the host root, outside the project, so it would 404.

## No SEO

The Mini App is not searchable, so there is no `<meta name='description'>` and no `robots.txt` (removed 2026-10-26). The browser version is public (owner, 2026-10-28), so SEO counts there and only there: `web.jsx` sets a descriptive `document.title` and adds the `<meta name='description'>` before its first render, so the Mini App HTML carries nothing for it. Reasoned, not checked: Google renders JavaScript, and Lighthouse audits the DOM after load, so a meta added by script counts; a crawler that does not run scripts sees only `<title>Round editor</title>`. Still no `robots.txt` (see below: it cannot be served from a project path, and the default is "crawl everything"). A `robots.txt` would not work there anyway: RFC 9309 §2.3 says crawlers read it only from `/robots.txt` at the top-level path of the host, and a GitHub Pages project site lives under `/<repo>/`. `<title>` stays: HTML requires it and axe (Lighthouse accessibility) audits it (`document-title`); `lang` stays for screen readers. The SEO score is not a budget here (owner, 2026-10-26: only weight and speed matter): `perf.config.mjs` sets `budgets: {SEO: -Infinity}`, so the harness still prints the score (82 without these files) with no limit.

## Telegram script

In the Mini App branch `https://telegram.org/js/telegram-web-app.js?64` loads in `<head>` before the app's scripts, as core.telegram.org/bots/webapps prescribes (checked 2026-10-25; the `?64` cache-buster is the one the page shows, update it in `index.html`, where the tag stays as the source the launch plugin moves into the router). The browser branch never loads it (Launch router). It is parser-blocking on purpose: `window.Telegram.WebApp` must exist before `main.jsx` calls `setupTelegram()` and `ready()`. Cost: desktop FCP 204–352 ms locally against the 200 ms budget (Perf harness). Do not make it `async` or move it below the module script without moving `setupTelegram()` behind its `load`. Being parser-blocking also puts Telegram's theme variables on `<html>` before the first paint (`src/README.md`, Theme tokens); an `async` script would paint the fallback colours first. Locally it still loads; the dev client then replaces `window.Telegram` (Dev plugin).

## Launch router

One URL (`https://l1nway.github.io/rounds/`) serves both the Mini App and the browser version (owner decision 2026-10-27: no URL split, and not a byte of browser code in the Mini App beyond the router). Two entries: `src/main.jsx` (the Mini App, the HTML entry) and `src/web.jsx` (the browser, a second Rolldown input in `vite.config.js`). A classic inline `<script>` in `<head>` of `index.html` picks one before anything else loads:

- Telegram is detected without its script: `tgWebAppData` in `location.hash` (Telegram appends the launch data there) or in `sessionStorage.__telegram__initParams` (where `telegram-web-app.js` keeps it, so a reload inside Telegram stays in the Mini App branch). Read in `telegram-web-app.js?64`, 2026-10-27: `urlParseHashParams(location.hash)` merged with that `sessionStorage` key. `sessionStorage` is read in a `try`: it throws where storage is blocked.
- Mini App: `document.write` of the `modulepreload` of the `main` entry, the Telegram script and the `main` module script. Written, not appended, so the Telegram script stays parser-blocking exactly as before (Telegram script) and the module runs after it (a parser-inserted module is deferred, in document order). An appended script would be async: the theme could paint late (a flash) and `main` could run before `window.Telegram` exists. The `modulepreload` comes first so the entry downloads in parallel with the Telegram script.
- Browser: `modulepreload` links for any chunk of `web` the HTML does not preload already, then the `web` module, all appended (no `document.write`, nothing from telegram.org: PageSpeed reported that script on the browser page).
- What the Mini App HTML carries of the browser version: the router's `web` constant and `else` line (about 0.2 KB raw); the whole router adds 0.35 KB gzip to the page. Shared code is one chunk (`app-*.js`) preloaded by a static `<link rel=modulepreload>` that both branches need; each entry is about 0.1 KB. Measured 2026-10-27 against the single-entry build: Mini App JS 22.35 + 0.12 KB gzip in two parallel requests instead of 22.36 KB in one, HTML 6.19 KB gzip instead of 5.84.
- Since the browser version renders the same editor (2026-10-28, `src/features/web/README.md`), the editor, Preact and the services are one shared chunk (Rolldown names it after one of its modules, now `editor-*.js`) and each entry is small: Mini App `index-*.js` 0.90 KB + `editor-*.js` 22.45 KB gzip = 23.35 KB, against 9.74 + 14.00 = 23.74 KB before the change (measured with `vite build` into a scratch folder, HEAD against the working tree; the Mini App HTML went from 6.26 to 6.28 KB gzip). The browser entry `web-*.js` is 5.1 KB gzip and the browser-only code is lazy: `probe`, `server` and `render-*.js` (Mediabunny, 112 KB gzip) load when a file is dropped. Nothing of `features/web`, `account` or `local` is in a Mini App file (grep of `dist/assets`; the only browser-version text in the shared chunk is the "Sign in" badge label of the options).
- The editor's CSS is in the shared chunk now, so check after a change to the entries that no `.css` name appears in `dist/assets/*.js` (Inline CSS): checked 2026-10-28, none.

The `launch-router` plugin (`transformIndexHtml`, `order: 'post'`, dev and build) fills the two placeholders of the router: `__MINIAPP__` with a template literal of the tags it cuts out of the page (the `telegram.org` script and the first module script that is not `/@vite/client`), `__WEB__` with `{entry, preload}` (dev: `/src/web.jsx`; build: the hashed file and its static imports from `ctx.bundle`, minus what the HTML already names). `</script>` inside the literal is escaped as `<\/script>`. The tag patterns accept both quote styles: dev serves the module tag as written in `index.html` (`type='module' src='/src/main.jsx'`), the build as Vite rewrites it (`type="module" crossorigin src="./assets/…"`); a double-quote-only pattern crashed `npm run dev` with `object null is not iterable` (2026-10-27).

- The tags inside `__MINIAPP__` keep Vite's double-quoted `src="…"` / `href="…"`: the perf engine finds Entry KB by matching those in the served HTML, so the Mini App entry is still counted. The web entry is an object property, which it does not match, so Entry KB measures the Mini App branch. The Telegram script's single quotes keep it out of Entry KB, as before.
- `document.write` cost, read in Chromium `third_party/blink/renderer/core/script/document_write_intervention.cc` (main, 2026-10-27): a cross-site parser-blocking script written by `document.write` is blocked only in the outermost main frame, when the load is not a reload, on an effectively 2G connection (`slow-2g` / `2g`), and only if it is not in the HTTP cache (the fetch becomes `only-if-cached`); after a block Chromium fetches it at idle priority for the next visit. Telegram Web (an iframe) and WKWebView (not Chromium) are never affected. If it does happen (Telegram Desktop or Android on 2G with a cold cache), `window.Telegram` is missing and the app shows "Open it from the bot"; reopening loads it. Not handled further on purpose.
- Lighthouse runs on the browser branch when PageSpeed opens the URL, and that branch has no `document.write`.
- Dev and the mock build: without `?job=` the local dev plugin opens the browser branch (it clears the stored launch params and any `#tgWebAppData`); with `?job=` it puts `#tgWebAppData=mock` into the URL, so the editor scenarios open the Mini App branch (Dev plugin; `dev/README.md`). That hash exists only in dev: Telegram adds its own to a real launch.
- Checked 2026-10-27 in headless Edge on the production build: with launch data in the hash it requested the shared chunk, `index-*.js` and the Telegram script, and painted `bg_color` from `tgWebAppThemeParams`; a fresh browser without it requested the shared chunk and `web-*.js` only (no telegram.org, no Mini App entry) and painted the system dark theme; no console errors in either. Not checked on a device: the first frame in Telegram iOS, Android and Desktop.
