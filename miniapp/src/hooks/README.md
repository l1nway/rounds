# hooks

`state.js`: the project merge reducer, `createStore` (a `useSyncExternalStore` store with per-selector reads), `useOnline` and `usePresence` / `useLeave` / `leave` (unmount after the exit animation, `src/README.md`, Presence). `player.js`: the one `<video>` the app has, as a store (`time`, `paused`, `waiting`, `loaded`, `failed`, `parked`, `hash`; the last two belong to Player park; `loaded` turns true once, on the first `loadeddata`, and drives the placeholder crossfade in `viewer`) plus imperative `seek` / `step` / `toggle` / `hold` and `useAway(time)` (true while the shown frame is not the frame of `time`; the viewer marks and the lift); the viewer attaches the element, the timeline and the selection read and move it.

## Watch player

`watchPlayer(fn)` subscribes to the player store and calls `fn(state)` on every change; it returns the unsubscribe. For per-frame work that must not render (the following marks, `features/viewer/README.md`, Follow). `createStore` exposes `subscribe` for it.

## Frame times

The proxy is CFR 30 (`FPS`, backend contract), times are seconds rounded to ms. A browser shows the frame whose timestamp is at or before `currentTime`, so frame `k` starts at `k / 30` and a time rounded *down* to ms (frame 1 → 0.033 < 0.0333) shows frame `k - 1`. Hence `frameTime(k)` rounds **up** to ms (0, 0.034, 0.067, 0.1 …) and `frameOf(t)` floors with a 0.001-frame epsilon for float noise; display and logic then agree on which frame a time means. The backend maps `prompt.time` to a working frame with `round((time - start) * FPS)`, which stays within one frame of what the owner saw (reasoned, not measured on the GPU side). Do not switch either helper to `Math.round` without re-checking the frame burned into the mock video (testsrc2 prints the frame number) against `formatTime`.

## Seek coalescing

One seek in flight at a time: `seek(t)` stores the target and updates `time` at once (the playhead and clock never wait for the decoder); the target goes to `video.currentTime` only when the previous seek fired `seeked` (latest target wins, intermediate ones are dropped). `requestVideoFrameCallback` is not used for this: it fires only when a *new* frame is presented, so a seek that lands on the frame already shown would never release the lock.
- The lock belongs to the attached element: `attach`'s cleanup clears `busy` with `video`. A `<video>` unmounted mid-seek (a new job, `key={job.proxy_url}`) never fires `seeked` to us, since its handlers are already removed, and a `busy` left `true` blocked every seek on the next video, because `flush` returns while `busy`. The pending `target` is kept on purpose: the next element takes it at `loadedmetadata`.

The write itself waits for the next frame plus a task (`later`, rAF then `setTimeout`). Measured in Edge headless with the perf engine's mobile profile (CPU ×4, slow 4G, touch emulation, cold cache): a frame-step tap that set `currentTime` in the same task as the DOM update was presented 1384–1392 ms later (Event Timing duration, processing 5 ms, the seek itself done in 4 ms); with the deferral 64 ms. With the proxy blocked the same tap took 48 ms either way, so the paused-video seek held back the presentation of the frame that carried the clock update. The deferral also caps seeks at one per frame while scrubbing. Whether a phone shows the same hold is unverified; keep the deferral.

## Playback clock

While playing, `time` follows the presented frame through `requestVideoFrameCallback` (`mediaTime`), so the playhead and the frame match exactly (MDN BCD: Chrome 83, Safari 15.4, Firefox 132). Fallback: a `requestAnimationFrame` loop reading `currentTime`. Either loop runs only between `play` and `pause`, never idle. Playback stops at the trim end (`setRange` from the editor) and restarts from the trim start.

## Player park

[DOC: player-park] `parked(work)` unloads the editor's `<video>` while `work` runs and brings it back after; meanwhile the stage shows a colour hash of the current frame (`features/viewer/README.md`, Player hash). Used by the device tracking (`followLocal` and `trackLocal` in `features/local/track-local.js`), only on the light tracking path, the devices short on memory (`features/local/README.md`, Park light; owner, 2026-11-02, after it first ran on every device): owner, 2026-11-01, "unload the editor video during tracking and show a frozen frame" (`BUGS.md`, iPhone reload on tracking). The viewer then says so by the point (`features/viewer/README.md`, Park memo), so a new caller must park only for memory too. Why: on the iPhone XR and SE2 the WebKit GPU process was killed by Jetsam at about 300 MB during a light track of a 4K source, and the editor's own 4K decoder was one of the two 4K decoders it held next to the tracker's (`features/local/README.md`, Light pump).

- [DOC: park-lull] Park starts one `--dur-long` after the call (`lull`, read from the root's computed style, so it is 0 under reduced motion). The call comes in the Follow tap's commit, and the XR's main thread was busy for about 270 ms right there (the cause was not traced; drawing the 4K frame for the hash and the blur's first raster are the suspects): the pill showed "Preparing tracking…" in black on white for one frozen frame and then snapped to glass (`IMG_4465.MP4`, 2026-11-02). Waiting lets the pill morph play first; the stall then lands before the blur's transition starts, where it costs nothing visible. The tracker starts that much later.
- Park: pause, draw the hash (`hashOf`, below), set `{hash, parked: true}` in the store, wait for the fade (`settle`: one task for the render, then every animation on the `<video>` finishes, at most `SETTLE` 1.5 s, so a hidden page that runs no animation frames still parks), then `removeAttribute('src')` and `load()`. Removing the attribute alone does not reload; `load()` with no source empties the element (`readyState` 0, an `emptied` event, no `error`: HTML, the media element load algorithm). The time is read after the fade (the timeline is inert from the first frame of it).
- Hash (`hashOf`): the frame drawn at 256 px on its long side (`HASH.from`), halved onto itself down to 8 px (`HASH.side`, `globalCompositeOperation = 'copy'`, the `shrink` pattern of `features/local/probe.js`: one big reduction would sample a few pixels instead of averaging), then drawn up to 32 px (`HASH.out`) and kept as a PNG data URL of about 1–2 KB, so nothing has to be revoked. Both canvases are freed at once (`width = 0`). A failed draw (zero size, a tainted frame) skips the park rather than blank the editor.
- Wake: the same `src` attribute again (setting it runs the load algorithm itself), and the store's time as the seek target unless a newer one is queued. Then it waits until the frame is shown (`seeked` or `loadeddata` with `readyState` ≥ 2 and no seek running, or `error`; at most `RELOAD` 10 s, so a reload that never ends cannot leave the player locked), sets `parked: false` (the fade back), and clears `hash` once that fade ends, unless a new park started meanwhile. If the element was replaced meanwhile (another file), it only unlocks.
- Nested calls share one park (`rest.count`): the first parks, the last wakes, and every caller awaits the same park (`rest.nap`), so no tracker starts while the editor's decoder is still loaded. A park that starts during a wake waits for it (`rest.waking`), because a park on a reloading element (`readyState` < 2) does nothing and that run would keep the video.
- `loaded` stays true, so the marks and the look canvas stay mounted; the lift layer and `look-gl.js` skip drawing while `videoWidth` is 0 or `readyState` < 2.
- Rejected: a JPEG `poster` of the frame at the displayed size (2026-11-01 to 11-02). On the iPhone XR in Safari (iOS 18.5, owner's recording `IMG_4459.MP4`, 2026-11-02) the stage went black for the whole track instead of showing the poster, and the frame popped back at the end; the cause was not traced (the draw itself works there: the lift layer draws the same `<video>`). The owner asked for the hash and a blur instead, which also costs no full-size image.
- Checked in headless Edge before the hash (touch viewport, the browser version, a 3840 × 2160 file, `followLocal` with VitTrack; scratch script, not kept): `src` gone and `readyState` 0 during the track, `src` back on resolve, `loadedmetadata` and `seeked` at the parked time (1.000 s). Not seen on a phone: whether WebKit frees the media player's decoder at once on `load()` without a source (the trace's `videos` beat shows it).

## Offline

`useOnline` is the network store core asks for: `navigator.onLine` plus `online` / `offline` events through `useSyncExternalStore`. What it gates: the submit button (disabled offline, the status line says why), the job poll and the load retry (paused, resumed on reconnect). Not gated: everything already loaded (selection, trim, scrubbing inside the buffered part of the video). A seek into a part the browser has not buffered shows the `waiting` spinner until the connection returns; a proxy that fails to load at all sets `failed` and the viewer shows a notice instead of an endless spinner.
