# account

The browser version's sign-in: a round button fixed at the top-left (`account.jsx`, `account.css`), the session and the Telegram login steps (`session.js`). Only `src/web.jsx` and `features/web/` import it, so none of it reaches the Mini App bundle (`miniapp/README.md`, Launch router). `account.css` goes in through `?inline` and a `<style>` from `web.jsx` (`miniapp/README.md`, Inline CSS).

## Account widget

Signed out: a Telegram-blue round button. A click opens Telegram's sign-in in a popup window (Popup login); the page itself never navigates (the owner's request 2026-10-28). While the popup is open and while the code is exchanged, the button shows a spinner (`aria-busy`); a click on it then only focuses the open popup. A failure shows a small panel under the button with the message and Try again (`role='alert'`, Escape closes it). Closing the popup by hand just clears the spinner, no error. Signed in: the button shows the user's picture (`user.photo`, the `picture` claim of the id token, a direct Telegram URL; `referrerPolicy='no-referrer'`; a failed image falls back to the first letter of the name) and opens a small menu with the name, the tier line ("Free version" / "Full version") and Sign out. Escape closes either panel. Offline: the sign-in button is disabled in the shared disabled style (the OIDC page needs the network); the menu works.

The tier comes with the login reply (`user.tier`, `backend/rounds/README.md`, Telegram login) and is kept in the session. A session stored before 2026-10-28 has no tier and reads as `free`: an allowed user signs in once more to get `pro`.

## Popup login

The OIDC Authorization Code + PKCE flow of core.telegram.org/bots/telegram-login, run in a popup window. `oauth.telegram.org` refuses to be framed: Firefox showed "oauth.telegram.org will not allow Firefox to display the page if another site has embedded it" for the first version, which ran the same flow in an `<iframe>` (owner, 2026-11-06).

- **Click.** `begin()` calls `window.open('about:blank', 'rounds-telegram-login', 'popup,width=550,height=650,…')` synchronously inside the click, because a popup needs transient user activation (`web-platforms.md`, Popups). `crypto.subtle.digest` is async, so the URL is not known yet: the blank popup is opened first, and `location.replace` sends it to `GET /api/auth/start` once the PKCE pair is ready. The API redirects it to `oauth.telegram.org/auth`. The size and centring copy Telegram's own `telegram-login.js`; phones ignore the features and open a tab. `null` from `open` (blocked) shows "Allow pop-ups"; no `API` (a local `npm run dev` without `VITE_API_URL`) shows "Could not open Telegram" before any window opens.
- **Return.** Telegram sends the popup back to the page's own URL with `?code&state` (or `?error`), the BotFather Allowed URL (`REDIRECT`). `web.jsx` sees `RETURNED` and runs only `relay()`: it posts `{type: 'rounds-login', search}` to `window.opener` (target origin = our origin), or, when the opener is gone, on a `BroadcastChannel('rounds-login')`; then it writes "Signed in. You can close this window" and calls `close()` (a window opened by script may close itself). Any load of the page with `?code` or `?error` is a popup return: nothing else sends the page there, so the app never renders with a code in its URL.
- **Parent.** `listen()` accepts a window message only from our origin and the popup's own window, and any message on the channel (the `state` check is the real guard). The parent closes the popup, checks `state` against the pair kept **in memory** (a module variable, never storage), and posts `{code, verifier, redirect}` to `/api/auth`; the backend exchanges it with the client secret (`backend/rounds/README.md`, Telegram login). A poll of `popup.closed` every 500 ms clears the spinner when the user closes the popup; it never drops the pending pair, so a message that arrives after the poll saw the window closed still completes the sign-in.
- **Why the channel fallback.** The opener survives the trip only while no page on the way sends `Cross-Origin-Opener-Policy: same-origin` (Telegram's docs say their own popup library fails under it). `oauth.telegram.org/auth` sent no COOP (curl, 2026-11-06) and GitHub Pages sends none, so the opener is the normal path; the channel covers a future COOP, since the popup and the opener are both top-level documents of one origin and share the channel. Under COOP `popup.closed` may read `true` early, which only clears the spinner.
- **Rejected: Telegram's `telegram-login.js` (`Telegram.Login.auth`).** Read in full (`oauth.telegram.org/js/telegram-login.js`, 2026-11-06): it opens the same `/auth` page with an undocumented `response_type=post_message`, and `oauth.telegram.org` posts the `id_token` itself to the opener. The token then comes from the browser, not from the token endpoint over TLS, so the backend would have to verify its signature against the JWKS (a JWT library, a new dependency, or hand-written RSA), plus a server nonce against replay; and a third-party script would load in the page. The code flow keeps the backend as it is. The library's in-app branch (`TelegramWebviewProxy`, `/inapp`) serves pages opened inside Telegram's own WebView; the Mini App signs in with `initData` instead.
- A reload of the opener in the middle of a sign-in drops the pair: the answer is then "This sign-in expired".
- `redirect` is `location.origin + location.pathname` and must equal a BotFather Allowed URL byte for byte (`https://l1nway.github.io/rounds/`). A real sign-in from `localhost` also needs `http://localhost:5173/` there and in the API's CORS origin (`backend/rounds/api.py`, only the `MINIAPP_URL` origin); neither is set up.
- **Not verified on a device:** the whole round trip against the real Telegram (desktop browsers and iOS Safari, where the popup is a tab and `close()` returns to the opener tab), and whether Telegram's page hands off to the Telegram app (`tg://`) and back inside the popup.

## Auth header

`session.js` registers `authorize(() => 'web ' + token)` with `services/api.js` at import, so every API call of the browser version is signed (`src/services/README.md`, Auth header). The session `{token, user}` is kept in `localStorage` (`rounds-session`): the GitHub Pages origin `l1nway.github.io` is shared by all of the owner's project pages, so the key carries the `rounds-` prefix. Not a cookie: the API is another site (`backend/rounds/README.md`, Web session). A 401 from a later call (expired or revoked) does not clear the session yet.
