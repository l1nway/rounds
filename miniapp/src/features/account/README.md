# account

The browser version's sign-in: a round button fixed at the top-left (`account.jsx`, `account.css`), the session and the Telegram login steps (`session.js`). Only `src/web.jsx` and `features/web/` import it, so none of it reaches the Mini App bundle (`miniapp/README.md`, Launch router). `account.css` goes in through `?inline` and a `<style>` from `web.jsx` (`miniapp/README.md`, Inline CSS).

## Account widget

Signed out: a round button in the theme's button colour with the Telegram plane. A click opens Telegram's sign-in in a popup window on desktop and in a new tab on a touch device (Popup login, Tab login); the page itself never navigates or reloads (the owner's request 2026-10-28 and 2026-11-06). While the popup is open and while the code is exchanged, the button shows a spinner (`aria-busy`); a click on it then only focuses the open popup. A failure shows a small panel under the button with the message and Try again, or Open Telegram when the browser blocked the window (`role='alert'`, Escape closes it). Closing the popup by hand just clears the spinner, no error. Signed in: the button shows the user's picture (`user.photo`, the `picture` claim of the id token, a direct Telegram URL; `referrerPolicy='no-referrer'`; a failed image falls back to the first letter of the name) and opens a small menu with the name, the tier line ("Free version" / "Full version") and Sign out. Escape closes either panel. Offline: the sign-in button is disabled in the shared disabled style (the OIDC page needs the network); the menu works.

## Account faces

The button itself paints nothing: no background, no `overflow: hidden`. It stacks three layers in one grid cell, in paint order (owner 2026-11-06: every swap animated, the plane leaving on its own while the white "dissolves" and the picture appears):

- `.account-disc`, the coloured circle: the button colour signed out, `--surface` while signed in without a shown picture (loading, or the letter fallback), a `background-color` transition between them. It is present (`usePresence`) unless the picture is decoded and shown. It leaves with `account-dissolve` (opacity to 0, `blur(6px)`, scale 1.4, `--dur-long`, `--ease-both`): the white melts outward behind the picture. It enters with the shared `enter`, except the disc that is there on the widget's first render (`data-still`, read once by `Disc` from the `boot` flag), which comes with the page's entrance instead.
- `.account-photo`, the picture: `opacity: 0` until `img.decode()` settles after `load` (`frontend.md`, a loaded photo is revealed after `decode()`), then `data-shown` and `account-bloom` (from opacity 0, `blur(8px)`, scale 0.5, `--dur-spring` on `--spring`). `shown` and `broken` hold the photo URL they were set for, not a flag, so a later sign-in with another picture starts hidden again and a sign-out keeps the leaving picture visible during its `leave`.
- `.account-glyph`, a `Swap` (`src/README.md`, Swap) of the plane, the spinner or the initial: each change is the shared `leave` / `enter` (opacity, blur, scale). The glyph present on the first render does not animate. No glyph over a shown picture.

Why the layers: the old button had `background: var(--button)` and `overflow: hidden` with the picture inside. The white background bled through the anti-aliased round edge as a thin white ring around the picture (the owner saw it in Firefox while the picture loaded and in Edge after the swap from the plane, 2026-11-06), and nothing animated. Now nothing is painted under a shown picture, and the disc leaves only once the picture is decoded, so there is no white under its edge and no empty frame. Checked in headless Edge (dark, DPR 3): after a reload with a session the button holds only `.account-photo[data-shown]` and the edge shows no ring. Firefox and the swap timings on a phone are not checked.

Hover lightens the disc, only signed out (a picture has nothing to lighten). The letter takes `--text` on the `--surface` disc (`[data-user]` on the button), the plane and spinner `--button-text`.

## Account panel

`Panel` in `account.jsx` renders the menu and the error panel through `usePresence` (`src/README.md`, Presence), so both animate out and are unmounted. The panel "resizes" out of the corner by the button (owner 2026-11-06): `account-open` animates `clip-path` from `inset(0 100% 100% 0 round var(--radius))` (an empty box at the top-left corner) to `inset(0 round var(--radius))`, on `--spring` over `--dur-spring`, with the opacity rising; `account-close` runs it back on `--ease-both` over `--dur-long`. The panel's children come in with the shared `enter` 80 ms later and go with `leave`. Leaving content is the last value (`useLast`: the last user, alert, photo), so the panel does not empty while it shrinks.

- Any size: `inset()` percentages refer to the panel's own box, so new content, a longer message or another width animates the same with no measuring and no JS. The panel's size itself is not animated when its content changes while open; that would need the measured WAAPI resize of `Swap` (`resize`).
- The shadow lives on `.account-holder`, a wrapper, as `filter: drop-shadow(…)`: a `box-shadow` on the panel would be cut by its own `clip-path` while it opens and then pop in at the end. A filter on the parent is drawn from the clipped result, so the shadow follows the growing shape.
- Text in a panel sits in a `span`, because `> *` animates only elements.
- [DOC: panel-pixels] `line-height: 20px` on the panel keeps every row on a whole CSS pixel. With the default `normal` (Segoe UI 15px: 20.25px) the Sign out button sat at `y = 120.5`; while its `enter` ran (filter, scale) the text was drawn on its own compositor layer, and when the animation ended it was drawn into the parent at the half pixel and jumped 1px up for good (owner 2026-11-06; measured in headless Edge at DPR 1: the text's vertical centroid 24.36 during, 23.35 after). With 20px rows the final position equals the animated one at DPR 1 and 1.25; one frame at the very end still shifts by about 0.5px. `normal` differs per font (SF Pro, Roboto), so do not go back to it here; a new row type keeps a whole-pixel height.
- Checked in headless Edge: 120 ms after the click the menu is a partly revealed box at the corner with blurred content; at 700 ms it is complete.

The tier comes with the login reply (`user.tier`, `backend/rounds/README.md`, Telegram login) and is kept in the session. A session stored before 2026-10-28 has no tier and reads as `free`: an allowed user signs in once more to get `pro`.

## Popup login

The OIDC Authorization Code + PKCE flow of core.telegram.org/bots/telegram-login, run in a popup window. `oauth.telegram.org` refuses to be framed: Firefox showed "oauth.telegram.org will not allow Firefox to display the page if another site has embedded it" for the first version, which ran the same flow in an `<iframe>` (owner, 2026-11-06).

- **Click.** `begin()` calls `window.open(url, name, 'popup,width=550,height=650,…')` synchronously inside the click, because a popup needs transient user activation (`web-platforms.md`, Popups). `crypto.subtle.digest` is async, so the PKCE pair and the `GET /api/auth/start` URL are prepared ahead (`prepare()`, at import and again after each `begin`, held in `ready`); the click opens the final URL at once, with no blank window. The API redirects it to `oauth.telegram.org/auth`. The size and centring copy Telegram's own `telegram-login.js`. No prepared pair (no `API`: a local `npm run dev` without `VITE_API_URL`) shows "Could not open Telegram" before any window opens. `null` from `open` (blocked) shows "Your browser blocked the Telegram window" with an Open Telegram link (Tab login).
- **Return.** Telegram sends the popup back to the page's own URL with `?code&state` (or `?error`), the BotFather Allowed URL (`REDIRECT`). `web.jsx` sees `RETURNED` and runs only `relay()`: it posts `{type: 'rounds-login', search}` to `window.opener` (target origin = our origin), or, when the opener is gone, on a `BroadcastChannel('rounds-login')`; then it writes "Signed in. You can close this tab and go back to Rounds" and calls `close()` (a window opened by script may close itself). Any load of the page with `?code` or `?error` is a popup return: nothing else sends the page there, so the app never renders with a code in its URL.
- **Parent.** `listen()` accepts a window message only from our origin and the popup's own window, and any message on the channel (the `state` check is the real guard). The parent closes the popup, checks `state` against the pair kept **in memory** (a module variable, never storage), and posts `{code, verifier, redirect}` to `/api/auth`; the backend exchanges it with the client secret (`backend/rounds/README.md`, Telegram login). A poll of `popup.closed` every 500 ms clears the spinner when the user closes the popup; it never drops the pending pair, so a message that arrives after the poll saw the window closed still completes the sign-in.
- **Why the channel fallback.** The opener survives the trip only while no page on the way sends `Cross-Origin-Opener-Policy: same-origin` (Telegram's docs say their own popup library fails under it). `oauth.telegram.org/auth` sent no COOP (curl, 2026-11-06) and GitHub Pages sends none, so the opener is the normal path; the channel covers a future COOP, since the popup and the opener are both top-level documents of one origin and share the channel. Under COOP `popup.closed` may read `true` early, which only clears the spinner.
- **Rejected: Telegram's `telegram-login.js` (`Telegram.Login.auth`).** Read in full (`oauth.telegram.org/js/telegram-login.js`, 2026-11-06): it opens the same `/auth` page with an undocumented `response_type=post_message`, and `oauth.telegram.org` posts the `id_token` itself to the opener. The token then comes from the browser, not from the token endpoint over TLS, so the backend would have to verify its signature against the JWKS (a JWT library, a new dependency, or hand-written RSA), plus a server nonce against replay; and a third-party script would load in the page. The code flow keeps the backend as it is. The library's in-app branch (`TelegramWebviewProxy`, `/inapp`) serves pages opened inside Telegram's own WebView; the Mini App signs in with `initData` instead.
- A reload of the opener in the middle of a sign-in drops the pair: the answer is then "This sign-in expired".
- `redirect` is `location.origin + location.pathname` and must equal a BotFather Allowed URL byte for byte (`https://l1nway.github.io/rounds/`). A real sign-in from `localhost` also needs `http://localhost:5173/` there and in the API's CORS origin (`backend/rounds/api.py`, only the `MINIAPP_URL` origin); neither is set up.
- **Not verified on a device:** the round trip on a phone (Tab login), and whether Telegram's page hands off to the Telegram app (`tg://`) and back inside the popup. The desktop popup works (owner, 2026-11-06).

## Tab login

On a touch device (`(pointer: coarse)`) `begin()` passes no window features, so `window.open` opens a plain new tab and the browser switches to it; after the sign-in the return page posts to the opener and calls `close()`, and the browser shows the opener tab again, which never reloaded (owner 2026-11-06: on the iPhone the popup was refused, see below; a same-tab redirect is not wanted, it reloads the editor).

- Why: on the owner's iPhone (Safari, 2026-11-06) `open('about:blank', name, 'popup,width=…')` in the click returned `null` ("Your browser blocked the Telegram window"). WebKit's own check allows a popup while a user gesture is processed (`LocalDOMWindow::allowPopUp`, `UserGestureIndicator::processingUserGesture()`, read 2026-11-06), so the refusal came from elsewhere (Safari's popup policy or its UI delegate); the exact cause was not found. The tab without features and the final URL instead of `about:blank` did not fix it: with that build the XR (Safari, iOS 18) still got `null`, while Firefox on the same XR and Safari on the SE2 (iOS 26) opened the tab (owner, 2026-11-06).
- [DOC: fresh-name] Every attempt opens under a new window name (`rounds-telegram-login-<random>`, made in `prepare()` with the pair; the Open Telegram link uses the same one). A known iOS Safari bug fits that picture: when the tab that `window.open(url, name)` opened is closed with Safari's back button (the button that returns to the opener and closes the child), every later `window.open` with the same name returns `null`, while a new name opens normally (Apple Developer Forums thread 813866, reported on iOS 26.2, FB21773746, no fix stated). Earlier tests on the XR opened such a tab under the fixed name, so a back-button close there would explain why every later try failed and the SE2 did not. Not verified that this was the cause; the old fixed name cannot be reused (`popup.focus()` on a second click uses the handle, not the name).
- Fallback that does not depend on the popup blocker: when `open` returns `null`, the error panel offers Open Telegram, a real `<a href={url} target={name} rel='opener'>` to the same prepared URL (`link()`, the pair already in `pending`). A link activated by the user is a navigation, not a popup. `rel='opener'` keeps `window.opener` (a `target` other than `_self` gets `noopener` by default); the channel covers it if not. A tab opened by a link is not script-closable once it has more than one history entry (HTML, "script-closable"), so `close()` there may do nothing: the return page says "Signed in. You can close this tab and go back to Rounds", and the opener signs in from the message anyway.
- The link gives no window handle to poll, so `phase: 'popup'` is cleared when the page becomes visible again without a message (`visibilitychange`); a message that comes later still completes, since the pair stays pending.
- Trap: iOS may discard a background tab under memory pressure; the opener then reloads on return, the in-memory pair is gone and the answer is "This sign-in expired".

## Auth header

`session.js` registers `authorize(() => 'web ' + token)` with `services/api.js` at import, so every API call of the browser version is signed (`src/services/README.md`, Auth header). The session `{token, user}` is kept in `localStorage` (`rounds-session`): the GitHub Pages origin `l1nway.github.io` is shared by all of the owner's project pages, so the key carries the `rounds-` prefix. Not a cookie: the API is another site (`backend/rounds/README.md`, Web session). A 401 from a later call (expired or revoked) does not clear the session yet.
