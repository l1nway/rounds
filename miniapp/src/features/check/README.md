# check

## Device check

[DOC: device-check] A temporary panel under the editor of the Telegram Mini App, shown only to `pro` jobs (`app.jsx`, lazy chunk), that measures what the device can run for local processing in Telegram's own web view (WKWebView on iOS, not Safari). It feeds the routing decisions (`local/README.md`, Speed gate, WebGPU by platform; project `CLAUDE.md`, Server tracking): whether the Mini App gets WebGPU on iOS 26, how fast the lift and VitTrack run there, and how fast a phone decodes the proxy, which is the only copy of the video the Mini App has. Remove it once the decisions are made.

- Buttons run a list of steps in order and print `step.key: value` lines; "Copy report" copies them (clipboard, else the text is selected for the system menu). The owner pastes the report into the chat.
- Files: `check.jsx` (panel, modes, beat record), `probes.js` (the steps).
- Steps: `env` (Telegram platform and version, UA, cores, screen, touch, cross-origin isolation); `pace` (frames per second of `requestAnimationFrame` over 1 s, 30 in Low Power Mode, and a fixed CPU spin, so a cold or low-charge run shows up, `web-platforms.md`); `webgpu` (adapter info, fallback flag, a device created and destroyed on the page, a few limits); `gpuBench` (Check gpu bench); `meter` (Check meter); `media` (WebGL2 float rendering for stabilization, codecs the device cannot encode at 640², 4K HEVC / H.264 decode); `light` (fetch of `proxy_url`, VitTrack on WASM over the first 4 s at 15 fps with the real `lightFrames` pump: decode per frame, net per step, `speed` as seconds of video per second of work: above 1× the phone tracks faster than the clip plays); `lift` (the model load timed alone, then 1–5 `segmentLocal` calls at the screen centre on the live `.viewer-video` frame, Check lift settings; the backend the worker really got, and `fast()` afterwards, the speed gate's verdict). The lift runs last because it is the heaviest; `release()` drops the models afterwards.
- The light step disposes its Mediabunny `Input` when it ends (it held an undisposed second copy of the proxy before 2026-11-06).

## Check modes

[DOC: check-modes] "Run all" runs every step; "GPU speed", "Light only", "Lift on GPU" and "Lift on CPU" (the lift with `cpu: true`, so the worker never touches WebGPU and is terminated on `release()`) run one heavy step after `env` and `pace`; "Memory meter" runs `meter` after `env`, "Lift, then meter" runs the lift with the current settings and then `meter` in the same page. One button per fresh open of the Mini App, then 2 minutes of waiting on the report (the meter ends the app by design).

## Check gpu bench

[DOC: check-gpu-bench] Why (owner 2026-11-06): the speed gate reads the WebGPU lift's own time, but in the Telegram Mini App on the SE2 that lift is what kills the page, while the same lift in Safari runs fine; and a CPU timing says nothing about the GPU, where a phone that is fast on WASM is faster still. So the GPU is timed with a kernel too small to hurt: a tiled f32 matmul, 1024² × 1024² (`BENCH`: 16² tiles, 2 KB of workgroup memory, 256 invocations, so it fits the XR's limits too), three 4 MB buffers, on a device of the page that is destroyed after. One dispatch first (`first`, with the shader compile), then the best of 3 rounds of 8 dispatches (`matmul` per dispatch, `gflops` = 2n³ / time). No ONNX Runtime and no model, so it compares phones by GPU alone and can be calibrated against the lift times measured in Safari (SE2 1.6–3.9 s, 17 Pro 0.3–0.4 s, web-platforms.md). Checked 2026-11-06 in headless Edge, GTX 1660 Ti: first 427 ms, 4.0 ms per matmul, 534 GFLOPS. Not yet run on a phone.

## Check meter

[DOC: check-meter] Measures the WebGPU headroom of the Mini App's web view, to test the owner's reading that Telegram's WKWebView gets far less memory than Safari. It adds 32 MB storage buffers (capped at `maxBufferSize`), clears each on the GPU so it is really allocated, and saves the reached size in the beat record after every buffer (`step: meter N MB`), until the app dies, an `out-of-memory` error scope fires, the device is lost, or 6 GB (`METER.cap`). Then it frees everything. Live WebGPU buffers count about one to one against the WebContent limit on iOS (local/README.md, gpu-buffer-cache, Buffer churn), so the size at death is the headroom at that moment. Compare with the dev memory meter in Safari on the SE2: 1472–1488 MB on the start screen, 1408 MB in the editor with the video (local/README.md, meter round). "Lift, then meter" gives the headroom with the lift loaded (or after its release, per the settings).

## Check lift settings

[DOC: check-lift-settings] The lift modes take three settings from the panel, printed in the report's third line: the WebGPU buffer cache (`lazyRelease`, the app's value; `bucket`, which keeps the buffers instead of creating and destroying about 500 MB per run on the tracker; `simple`; never `disabled`, local/README.md, gpu-buffer-cache), the number of runs (1, 3, 5) and whether `release()` runs after. The probe loads the group itself with `ready('lift', NAMES, {cpu, cache})` (`NAMES` exported from `lift-local.js`), then `segmentLocal` finds it loaded and does not pass its own `CACHE`. A group left loaded (release off) keeps its cache mode for the next mode of the same open, so change the cache only in a fresh open. Planned runs on the SE2: GPU ×1 with no release (does the first run alone kill it?), `bucket` ×3 (is the churn the cause?), `lazyRelease` ×3 with no release (is the release the cause?).

## Check beat

[DOC: check-beat] The run record (`rounds.check-run` in `localStorage`: mode, report lines, current step with a detail such as `lift run 2`, step start, end, last beat, `hiddenAt`) is saved at every step and on a 1 s beat that goes on 120 s after the finish. The next open shows a verdict line and the previous report, so a crash report needs no screen recording:
- no `end`: the page died during the step, with the time into it;
- a last beat ≥ 118 s after the end: it survived;
- otherwise the last beat N s after the end: it died, or the Mini App was closed (the owner knows which).
- Going to the background sets `hiddenAt` once and stops the saves (iOS suspends timers there), and the verdict names it, so a swipe away is not read as a crash.
- Replaces the earlier `rounds.check-step` marker, which was removed at the end of the run and so was blind to a death after it.
- `ready('lift', [])` after the lifts returns the group's cached load result (`{gpu, reason}`) without loading anything: `ready` answers from `groups` before it reads the names.
- Checked 2026-11-06 in headless Edge with a touch viewport (the panel mounted on the dev server with the mock job and `proxy.mp4`; the mock loader of `miniapp/dev` did not start in that headless run, cause not traced): every step finished, copy worked. GTX 1660 Ti: VitTrack 30 ms a step, 2.07× real time; EdgeSAM lift on WebGPU 7.0 s cold with the download, then 428 and 267 ms. Not yet run in Telegram or on a phone.
- Phones, 2026-11-06, Telegram 9.6:
  - **iPhone XR, iOS 18.5.** No `navigator.gpu` in the Mini App, as expected for a WKWebView on iOS 18. VitTrack runs on WASM: 50 ms a step and 1.28× real time when charged, 70 ms and 0.90× in Low Power Mode on a cold phone. The lift runs on WASM: 9.1 s on the first call, then 2.6–2.9 s. The check finished and the page survived.
  - **SE2, iOS 27.3 beta.** WebGPU works in the Mini App (`apple / apple`, a device is created). VitTrack: 64 ms a step, 1.00× real time. The lift runs on WebGPU: 9.9 s on the first call, then 2.7–4.3 s, so `fast` is false. Both runs finished every step, then the page died about 30 s later while idle on the report (screen recording `IMG_0455.MP4`). The two JetsamEvents at 03:39:14 and 03:40:46 show WebContent `highwater` at 98 304 pages (1536 MB), with the GPU process at 25 and 58 MB.
  - **Blind spot.** The old crash marker was removed when the run ended, so a death after the run left no trace on the next open (fixed by Check beat). Which step leaves the memory behind is unknown: the run was on a low, worn battery, and only the SE2 had WebGPU.
  - **SE2 rerun with the modes** (2026-11-06, 03:24–03:28 UTC, one mode per open, without the 2-minute waits). Every death came from the WebGPU lift (EdgeSAM, `lazyRelease`), in 3 of 3 runs: "Lift on GPU" died 1.1 s into run 2; a second "Lift on GPU" finished all three runs (load 2.7 s, then 4.7, 1.4, 1.6 s) and died within a second after the finish, during or just after `release()` (the last beat came before `end`, so the verdict printed a negative time); "Run all" died 0.2 s into lift run 3, after env, webgpu, media and light had finished. (The negative time is clamped to 0 since: a last beat before the end means a death within 1 s after it.) One `JetsamEvent-2026-11-06-042811.ips` matches that last death by its time (its contents were not read). "Lift on CPU" (WASM: 5.8 s, then 2.6 and 2.4 s) and "Light only" (VitTrack WASM 38 ms a step, 1.68× real time) finished, and the page lived on: the next mode ran in the same open 23 s and 38 s later. The WebGPU lift gains little there: 1.4–1.6 s warm against 2.4–2.6 s on WASM, both slow for the speed gate.
- The lift calls use a fake source name and distinct `time` keys so the embedding cache never answers them; every call runs the encoder. They call `notePace`, so the speed gate of that page is set by the check (harmless: the Mini App does not track on the device yet).
