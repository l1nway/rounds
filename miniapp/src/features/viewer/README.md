# viewer

The proxy video with the selection overlay, `viewer.jsx`. There is no selection bar under it on purpose (owner decision 2026-10-25): the "Not this" mode, the summary / "Jump" chip and Clear duplicated what the gestures and closing the Mini App already do, and were noise. Do not bring them back.

## Letterbox

`.viewer-stage` is exactly the displayed video: `aspect-ratio` from `--aspect` (`meta.width / meta.height`, set on `.viewer` and inherited, see Viewer fit) (display-oriented, the same aspect as the proxy) and `width: min(100cqw, 100cqh * aspect)` inside a `container-type: size` parent, so it fits both ways and the black bars belong to `.viewer`. Pointer positions are normalized against this box, which makes them 0..1 of the display-oriented frame (the API contract) with no letterbox maths in JS. Marks are HTML elements positioned in percent, so they stay put at any size and keep a fixed pixel size. Container query units: Chrome 105, Safari 16, Firefox 110 (MDN BCD); older engines get `height: 100%; max-width: 100%`, which can overflow on a very wide video.

## Viewer fit

Owner request 2026-10-26 (`IMG_0407.MP4`, iPhone SE2): the viewer got only the grid leftover, about 100 pt of 667, too small to tap an object. `.viewer` always has `height: min(100cqw / var(--aspect), 0.7 * var(--room))` (`100cqw` of the editor, an inline-size container; `--room` is the editor's visible height, set on `.editor`, `editor/README.md`, Editor scroll): a vertical video grows to 70 % of the editor height, a horizontal one gets exactly its own height with no bars. The editor then scrolls (`editor/README.md`, Editor scroll); nothing is compressed to fit (owner decision).

- Fitted from the first frame (owner's recording 2026-10-26, Firefox 736 × 1036, a 16:9 video, reload: before the job the viewer took the grid leftover, about 70 % of the screen, then shrank to the 16:9 height, and the whole column under it jumped up about 80 px; with the old ease-out curve most of the travel fell into 2–3 frames). The aspect is computed by `Editor` and comes in as the `aspect` prop (the editor's layout reads it too, `editor/README.md`, Split layout). Before the job it is `FALLBACK_ASPECT` (`editor.jsx`): the aspect from the launch URL (`a`, written by the bot since 2026-10-26, `services/README.md`, Launch aspect), else 16:9. With `a` the placeholder already has the video's shape and nothing moves; without it (old buttons, the mock without `&a=`) a 16:9 video never moves the layout and any other aspect changes it once. `a` is rounded to 6 digits, so `useFit` may still run a sub-pixel animation when the job's exact aspect arrives; it is invisible. There is no `data-fit` attribute any more; the editor's fitted grid is its base rule.
- `useFit` in `viewer.jsx` animates an aspect change with WAAPI, one layout effect per aspect: the previous aspect is kept in a ref; set it inline as `--aspect`, read `offsetHeight` (from), set the new one, read again (to), then `animate({height, '--aspect'}, FIT)`. Nothing runs when the aspect did not change. No fill: when it ends the CSS rule holds the same height, and later viewport changes follow CSS. Reduced motion: no animation, the rule applies at once.
- `FIT` is 600 ms on `cubic-bezier(0.4, 0, 0.2, 1)`, a move curve that accelerates and settles instead of the `--ease` ease-out (`0.2, 0.8, 0.2, 1`), which dumped most of the height change into the first frames and read as a jump. JS literals because the minifier writes `--dur-long` as `.4s`, so do not parse tokens from computed style. FIT's duration and curve are copied by the editor's `grow` (late option rows, `editor.css`, `editor/README.md`) and by the notice's `unveil` (Notice unveil): change them together. Both run with no stagger, so the column moves as one body.
- `100cqw` is the editor's content width only because `html` has `scrollbar-gutter: stable` (on `.editor` while it was the scroller): with a classic Windows scrollbar the container width otherwise counted the scrollbar's space and left a 4 px letterbox strip above and below a 16:9 video (`features/editor/README.md`, Editor scroll). Do not fix such a strip in the viewer's sizing.
- `--aspect` is registered (`@property`, `<number>`, inherits) so it interpolates from the previous aspect to the video's along with the height, and the stage (sized in `.viewer` container units) morphs smoothly instead of jumping shape. Do not add a CSS transition on `--aspect` or `height`: the "to" read would then return the start value.
- `offsetHeight`, not `getBoundingClientRect`: the entrance (`src/README.md`, Entrance) scales the viewer by 1.06 at the same time, and a transformed rect made the animation end with a 1–2 px jump.
- Fit runs on the job, not on `loadeddata`: the placeholder takes its final shape while the video loads, and the video then fades into a box that no longer moves under the finger.
- Rejected: the owner's `collapse` library. On Preact it builds only with a `useEffectEvent` shim, split aliases and `forwardRef` (+1.86 KB gzip), and it animates closed ↔ natural height, not grid leftover → target height. `calc-size()` / `interpolate-size` are not in Safari; a `grid-template-rows` transition from `1fr` to px is discrete.
- Measured in the mock after the change (Edge headless spawned without `--hide-scrollbars`, so the editor's 15 px classic scrollbar is real; `meta` width and height swapped for the vertical case; viewer `offsetHeight` and the timeline top sampled every frame): 16:9 at 375 × 667 stays 202 px and at 736 × 1036 stays 397 px from the first sampled frame to the end, and the timeline top does not move at all. Vertical: 202 → 421 px (375 × 667) and 397 → 679 px (736 × 1036), each in about 600 ms; the biggest single-frame steps (45 and 34 px) came after 57–140 ms frame gaps while the video was loading in the same moment (main-thread stalls in headless, reasoned, not profiled), not from the curve. CLS while loading: 0.002–0.05 for 16:9 (none of it from the viewer, whose height never changed), 0.27–0.43 for vertical, the requested growth itself. Before the change: vertical 231 → 422 px and horizontal 231 → 211 px at 375 × 667, CLS 0.182 in the perf harness. The feel on the iPhone is not verified.

## Notice unveil

Owner's recording `IMG_4373.MP4` (2026-10-26, iPhone, a vertical video): the loading sheen covers the whole viewer width in phase 1 (the notice is `inset: 0` of `.viewer`), the stage sheen only the video's box; the notice used to fade out over the narrower stage, so the grey area snapped from full width to the video width in about one frame. Now `.viewer-notice[data-leaving]` runs `unveil` in `viewer.css`: `clip-path` from `inset(0)` to exactly the stage box, written in the same container units as the stage (`.viewer` is the size container: stage width `min(100cqw, 100cqh × aspect)`, height width / aspect, centred), so the grey shrinks onto the stage while the text fades (`--dur-long`); only then the notice's own opacity goes to 0 (`transition-delay` 600 ms), a short crossfade of the two sheen bands, whose phases differ.

- 600 ms on `cubic-bezier(0.4, 0, 0.2, 1)`, the `FIT` values (Viewer fit), so when the aspect also changes (no `a` in the launch URL) the clip and the stage move on one curve. The keyframe reads `var(--aspect)`, which `useFit` animates on `.viewer`, so the target follows the morph frame by frame (reasoned from CSS Animations: `var()` in keyframes is resolved against the element's current style; not observed on a device).
- The rule sits after `[data-still]` (`animation: none`) with the same specificity, and must stay there: the notice present at the first render keeps `data-still` while it leaves.
- `settle` (`hooks/state.js`) waits for both the animation and the delayed opacity transition before the notice unmounts (`getAnimations` includes a delayed transition).
- Reduced motion: no clip animation, no delay; the notice goes at once as before.

## Selection gestures

The handlers live in `gestures.js` (`useGestures`, split out of `viewer.jsx` for the 200-line limit; it also exports `pct` and `boxStyle` for `Marks`). The stage itself is the input layer (`touch-action: none`, the handlers on `.viewer-stage`; `data-off` when read-only or without a job turns it into `pointer-events: none`, so a swipe there scrolls the editor). Its children never take the hit: marks and lift have `pointer-events: none`, and so has the `<video>`, which keeps WebKit's own touch handling of a video element out of the gesture (there was a separate transparent `.viewer-input` layer for this until 2026-10-26; it duplicated the stage box and was removed). Pointer events with capture, primary pointer only. Movement under 8 px is a tap, more is a box (drawn live by writing the style of the `[data-draft]` element, no React state per move, Draft box; a box under 12 px either way is dropped). A tap within 24 px (screen) of an existing point first cycles the lifted outline (Lift) and removes the point once every candidate was shown; without a lift it removes the point at once. Otherwise it adds a point (label 1, "this object"; exclusion points with label 0 are no longer placed, but a prefilled draft from an older request still shows them red via `data-negative`). One box: a new one replaces it, or it is edited in place (Box edit). `pointerdown` during playback freezes on the presented frame first (`hold`), so the mark belongs to the frame under the finger. Every change gives a light haptic. Coordinates are rounded to 4 decimals.

Keyboard and screen readers cannot place marks: picking an object on a video frame is pointer work, and the editor is for the owner on a phone. The rest (trim, playhead) is reachable by keyboard.

## Draft box

The dashed `[data-draft]` box exists only while a pointer is pressed on the stage (owner rule 2026-10-26: nothing invisible stays mounted). `press` in `viewer.jsx` calls the gesture's `down` and, if it started a drag (`refs.current.drag`), sets `pressed`: one Viewer render mounts the element with `hidden`. Preact flushes renders in a microtask, so it is in the DOM before the next `pointermove` task. From there `gestures.js` draws it imperatively as before (`style` and `hidden` per move, no render per move: Preact leaves the attributes alone because their props never change). `release` wraps `up` and `hide`: it does nothing without a drag (a pointer that `down` ignored), otherwise it runs the handler and unmounts the box. Cost: two Viewer renders per press, which a tap already pays for its `select`; `Marks` and `Lift` are `memo` and skip them. Checked in the mock: the box is mounted and hidden on `pointerdown`, shown during the drag, gone after release.

## Box edit

Owner request 2026-10-26: the box is moved and resized instead of redrawn. On the selection frame, `pointerdown` is tested against the box (`grab`) in screen pixels: within `reach` of a corner (24 px, `HIT`, but at most a third of the box side, so a small box still has a middle to grab) it resizes, inside the box it moves, elsewhere it draws a new box as before. Resize is the draw gesture with its origin set to the opposite corner (`from`), so it can flip past the anchor and obeys the same 12 px minimum. Move translates the box, clamped to the frame (`shifted`). Both start only past the 8 px tap slop: a tap inside the box still adds or cycles a point. While editing, `data-editing` on the stage hides the committed box and the dashed draft shows the new one; on release `drawBox` commits it, which re-asks the lift. The four `.viewer-corner` squares (10 px, centred on the 2 px border) mark the handles; edges are not handles. Checked in the mock (Edge headless, 390 × 844): draw, move, move clamped at the frame edge, resize from the top-left corner, a new box outside, a tap inside; no console errors. The feel on the iPhone is not verified.

## Box reset

Owner request 2026-10-26: a quick double tap inside the box removes it. `reset` in `gestures.js` remembers a tap that landed inside the box (`drag.shift`, so only on the selection frame) with its time, place and the points before it (`refs.current.tapped`); a second tap inside the box within `DOUBLE` 350 ms and `HIT` 24 px clears the box and restores those points, which undoes the point the first tap added (or the one it removed). With no points left `time` is freed, as when the last point is tapped away. Chosen over delaying the single tap by 350 ms: a point inside the box would then appear late on every tap. The cost: the first tap of a double tap still flashes a point and asks the lift once more. A drag, a tap outside the box or a slow second tap resets the memory. Not verified on the iPhone; 350 ms is a guess near the iOS double-tap window; 300 was too tight in the mock: two scripted clicks with a 100 ms pause ended 328 ms apart, since the first tap re-renders and asks the lift. Checked in the mock (Edge headless, 390 × 844): a double tap inside removes the box and keeps the earlier point; two slow taps inside add and then remove a point; a double tap outside adds and removes a point; no console errors.

## Stable refs

`refs.current.{stage, video, draw}` in `viewer.jsx` and `own.current.host` in `look.jsx` are set by ref callbacks created once (`useState`), never inline arrows. Preact calls a changed ref callback with `null` during the diff and sets the new element only in the commit. `Look` flushes its pending passive effect at the start of its own re-render, which is after the `<video>` was diffed: with an inline ref the effect read `refs.current.video === null` and threw `null is not an object (evaluating 'video.requestVideoFrameCallback')` out of the render, which left the tree half-updated (sliders, switches and codec segments stopped following their state; the viewfinder kept applying the values). Seen on the iPhone with an on-screen trace log (2026-10-28), when the first slider step mounted `Look` and the next render came before the effect ran. The cause chain is reasoned from the error text and Preact's hooks source, not yet confirmed on the device after the fix.

## Video source

The `<video>` src ends with `#t=0.001`. iOS (Telegram's WKWebView) does not honour `preload` and shows nothing until it is played, so no `loadeddata` arrives, the spinner never stops and a frame cannot be picked; the media fragment forces the first frame to load. Reasoned from the symptom (the editor worked in Telegram Web, not on the iPhone), not yet confirmed on the device.

## Selection frame

The selection belongs to one frame (`time`, `prompt.time`). On another frame the marks dim (`data-away`), unless the object is followed there (Follow: they move with it and stay nearly opaque); the blue dot under the filmstrip shows where the selection frame is. A tap or a box on another frame **moves** the selection there: the old marks are dropped and the new mark starts a fresh selection at the current frame. Chosen over a confirm dialog because a dialog interrupts the gesture, the old marks are visible (dimmed) right up to the tap, and redoing one or two marks is cheaper than answering a question each time. Since the playhead is kept inside the trim range, `time` always lies in `[start, end]`, and the trim handles stop at it (`timeline/README.md`, Trim bounds). Ways to undo without Clear: double tap inside the box to remove it (Box reset), tap a point to remove it (after cycling through the outlines, Lift) (the last one removed with no box frees `time`), draw a new box (replaces the old), select on another frame (moves the selection), or close the Mini App (the draft is not kept).

## Lift

Tap-to-lift (owner decision 2026-10-26, after the demo on the iPhone): after every selection change the viewer asks the backend for SAM's outlines of the tapped object (`POST /segment`, `backend/rounds/README.md`, Lift) and shows the chosen one lifted from the frame (Lift look). The outline is what the tracker follows: its PNG goes into the draft as `mask` and to `POST /render` as `prompt.mask`.

- `useLift` (in `viewer.jsx`, its only consumer) owns the ephemeral state `{time, candidates, index, best, pending}`; the draft holds only the chosen `mask`. `ask(selection)` runs after every `select`: it clears `mask` at once (a submit while waiting sends plain points), keeps the old outline dimmed (`data-stale`) when the new selection is on the same frame, and sends through a single flight (Single flight): one `/segment` at a time, a newer selection waits and replaces the waiting one, an answer for a superseded selection is dropped. A selection without a positive point or a box clears the lift.
- Gestures: a repeated tap on the point cycles the candidates from `best` (the middle one by area: part, whole, surroundings) and wraps; when the next one would be `best` again, the tap removes the point instead, as before Lift. Two points or a box give one outline, so a tap on a point removes it at once. Adding outside and subtracting inside the outline were proposed and are not built.
- Failure (`502`, offline, `?job=nolift` in the mock): no outline, no message, the point stays and is tracked from points. An error line for a decoration would be noise.
- Warm-up: `warmLift` (`POST /warm`) when the editor gets a job that is not rendering, and again on every `visibilitychange` to visible (the GPU container sleeps after 120 s idle). Errors are ignored.
- A prefilled draft (`done`, `failed`, `rendering`) shows the submitted `prompt.mask` as the only candidate. `useJob` gives `job` a new identity once, so the "store the previous `job`" reset in render runs once.

## Lift look

`lift.jsx` + `lift.css`: the iOS "lift subject" look, tuned on the owner's iPhone with the demo page (2026-10-26). Over the stage, under the marks: `lift-dim` darkens everything outside the outline (`mask-composite: exclude`); `lift-pop` scales a copy of the frame inside the outline by 1.012 around the tap point (a 1.03 overshoot on arrival); `lift-glow` puts three `drop-shadow`s (0.75 px white rim, 7 px and 20 px glows) on that masked copy; `lift-shine` is a faint silver gradient with one light band (`::before`) that sweeps twice on the first outline and once on a switch (`translate` only). A switch crossfades two layers (`prev` fades out, `cur` fades in, keyed by a counter).

- Nothing invisible stays mounted (owner rule 2026-10-26, `src/README.md`, Presence). `prev` leaves through `useLeave` (`lift-out` under `[data-leaving]`, `--dur-long`) and its `gone` callback drops it from the state, so the layer is unmounted after its fade. The `.lift` wrapper is a `usePresence` element shown while there is a layer and the selection frame is on screen: away, it fades out on the `data-away` opacity transition and is unmounted; empty (the outline was cleared and `prev` is gone), it has no transition and goes at once. A `prev` still in the state when the wrapper unmounts is dropped in render, or it would replay its fade on the next mount.
- The sweep band and the pop exist only under `data-sweep`: `animationend` of the band (on `.lift-shine`, the only animation that ends there) calls `swept`, which clears `sweep` of that layer, so the pseudo-element is gone after its pass and a layer remounted on return to the selection frame only fades in (`appear`), with no second pop or sweep. A layer remounted before its sweep ended plays it again (it never finished). Under reduced motion neither is declared, and `sweep` simply stays.
- The frame copy is a `<canvas>` painted from the `<video>` (`drawImage`) when the layer mounts (after `seeked` if a seek is running), and repainted from the graded frame while the HDR / exposure preview is on (Lift source). The layer mounts only once the video has loaded and while the selection frame is shown, so "back on the selection frame" is a fresh mount. Known gap: the player defers the `currentTime` write by a frame (`hooks/README.md`, Seek coalescing), so right after a seek to the selection frame `video.seeking` is still false and the canvas may get the previous frame; this was so before the remount change too and is not fixed yet. A cross-origin video taints the canvas, which only blocks reading it back; nothing reads it. Showing the live `<video>` through the mask was rejected: a glow needs a masked element of its own above the video, and a white or translucent fill there hides or greys the object.
- `--bleed` (32 px): the glow element is that much larger than the stage so the shadow is not clipped at its box. WebKit still clipped the glow where the outline ran along the frame edge; the backend therefore insets the outline 4 px from the frame border (`backend/rounds/README.md`, Lift mask), so the rim is drawn inside the picture.
- Away from the selection frame (another frame shown, playback) the lift is removed, not dimmed like the marks: the frame copy would sit over a different picture. Before `loadeddata` it is not mounted (Loading crossfade).
- Waiting: the point pulses with two staggered rings (`data-pending` on `.viewer-marks`, `scale` and `opacity`), the old outline at 0.45.
- Reduced motion: no sweep, no pop, a static ring; the fades follow `--dur-long` (0).
- Checked in the mock (Edge headless, 390 × 844): pending rings, lift, two cycles, removal on the third repeated tap, the submitted `prompt.mask`, and the `nolift` fallback; no console errors. The look on the iPhone was approved on the demo page, not yet in the Mini App. After the unmount change (375 × 667): first outline `data-sweep='2'` with the band, no band after the sweep; a second point gives `prev` leaving plus `cur` with sweep 1, and 300 ms later only `cur` is in the DOM; playback removes `.lift`.

## Loading crossfade

What the viewer shows from the first paint to the first video frame, with no layout shift and no pop (owner's recording `IMG_0406.MP4`, 2026-10-26: the selection box drew over a black stage for 1.4 s, then the video popped in).

- Phase 1, no job (loading, ingesting): the `Notice` covers the whole viewer. A busy notice (`LOADING`, `INGESTING`, `data-busy`) has a `Sheen` as its background and theme text colours on it (`--text` / `--hint`: the sheen is `--surface`, light in a light theme); it has no spinner, the sheen is the activity indicator. A non-busy notice (errors, offline, outside Telegram) stays opaque `--stage`.
- Phase 2, job known, no frame yet: the notice shrinks onto the stage box and then fades (Notice unveil; `usePresence` unmounts it with its sheen once its animations end) and reveals the stage, morphing to the video's aspect if it is not 16:9 (Viewer fit), with its own `Sheen` and black letterbox bars. Inside the stage box both sheens are the same colour, so only the bars appear to fade in. The notice keeps its last content while it fades (`shown` state, updated during render only when title, text or action differ, React's "store information from previous renders" pattern: a ref read in render and a `setState` in an effect are both lint warnings here).
- Notice swap: the body is a `Swap` keyed by the shown notice (`item='div'`, its children a render function, `src/README.md`, Swap), so a new notice enters (blur, scale 1.06 → 1, opacity) in the same grid cell while the old one leaves (blur, scale 0.9, fade) and is unmounted, instead of an instant replace. The cell is centred both ways (`place-items: center`), so when the taller body leaves the remaining one does not move. The leaving body renders with the live `online` state (the render function reads it), so its button does not flip. Busy → not busy (loading → an error) fades the notice sheen out (`--dur-enter`) and transitions the text colours. The notice present at the first render does not animate (`data-still`); a notice that appears later (the `BROKEN` one after a failed video) fades in with `appear` over `--dur-long`. Trade-off: `role='status'` sits on an element that is inserted with its content, which some screen readers do not announce; the notice is visual feedback for the owner on a phone.
- Phase 3, `loadeddata` (`loaded` in the player store): the stage sheen freezes and fades out (`[data-leaving]`, opacity over `--dur-enter`, then unmounted) while the video comes into focus under it (`focus`: blur 10 px and scale 1.06 to sharp, the same 700 ms), and the marks and the lift mount and fade in (`appear`). The reveal is `data-reveal` on the stage, from `loaded` until the video's `focus` animation fires `animationend` (also with a 0 s animation under reduced motion, checked in Edge): what mounts within that window fades with the video, what mounts later (a tap, a new outline) has only its own entrance. Marks and lift are not mounted before `loadeddata` (they used to wait at `visibility: hidden`; a box over a black stage looked broken), and the marks only while there is a point or a box. The video is opaque from the start and sits under the sheen (`z-index: -2` against the sheen's `-1` inside the isolated stage): owner's recording `IMG_0409.MP4` (2026-10-26) showed that a `<video>` fading in from `opacity: 0` in WKWebView was not painted during the fade, so the sheen stood still for about 0.33 s and then the frame popped in. Now the reveal is the sheen's own opacity, an ordinary layer, and the video has had time to paint underneath. The marks' own `data-away` dim is untouched (the reveal is an animation, not an opacity override).
- Spinner: mounted only while `waiting && loaded` (the sheen covers the first load). It fades in from `@starting-style` after a 300 ms `transition-delay`, so a seek that settles quickly never shows it, and leaves over `--dur` without the delay. Keep the spinner rules before the `@starting-style` block: starting-style rules cascade like normal ones, and a later `.viewer-spinner {opacity: 0.8}` overrode the starting value (it popped in at once, measured). A waiting → playing flap inside 60 ms leaves no visible spinner and unmounts at once (checked in the mock with synthetic `waiting` / `playing` events).
- The stage sheen is mounted only with a job (`on` = job, not loaded, not failed): in phase 1 it would only run hidden under the notice.
- A one-shot `animation`, not a transition, for the video and marks reveal (perf-web.md: a cached video can fire `loadeddata` before the hidden state was ever painted).
- The video is the LCP element; under the sheen it may become an LCP candidate as soon as its first frame paints. See `miniapp/README.md`, Perf harness, for the measured effect.
- Measured in the mock (Edge headless, 390 × 844, CPU ×4, slow 4G, `?job=done` and `?job=ingest`): CLS 0 through the whole load, every state change a fade. That was before Viewer fit, whose growth is a counted layout shift. Only a phone shows how WKWebView paints the `<video>` layer under `opacity: 0`.

## Look preview

Owner decision 2026-10-26 (hybrid preview): the HDR and exposure sliders (`features/editor/README.md`, HDR slider, Exposure slider) show their effect on the viewer frame at once, so the strength is judged by eye. The honest part and the exposure are computed live on the device with WebGL2 over the proxy `<video>`, paused and while playing; in the AI zone, paused, an exact frame from the server crossfades over it (Exact frame). Files: `look.jsx` (the component), `look-gl.js` (WebGL2 plumbing, Look GL), `look-glsl.js` (shaders, Look shaders), the constants in `src/constants/look.js` (Look mirror there).

- Mounted only while `look > 0 || exposure !== 0` and the video has loaded. At 0 / 0 the viewer is exactly what it was before: no canvas, no GL work. Props are primitives (`job`, `look`, `exposure`, `refs`), the component is `memo`.
- Lazy chunk: `useLook` in `viewer.jsx` imports `look.jsx` (with `look-gl.js`, `look-glsl.js`) once the video has loaded, in the background, whatever the sliders say. The chunk stays out of the entry, and it is already there for the first slider move and when the connection drops later (core, Offline: the live preview needs no network). A failed import (offline at that moment) is retried when the effect is switched on or off. The component is kept in a module-level variable with a `ready` state, not in state itself: oxlint's `react(static-components)` flags a component read from state.
- Layering: `.viewer-look` (absolute, `inset: 0`, `z-index: -2`) right after the `<video>` inside the isolated stage: the video's z-index, later in the DOM, so above it; under the stage sheen (-1, Loading crossfade) and under the lift and the marks (auto). `pointer-events: none`, so the stage keeps every gesture. It holds the canvas (inserted imperatively, Look context) and the exact frame `img`. The stage is the video's own box (Letterbox) and the canvas has the video's intrinsic size, so `100%` lays it exactly over the picture. The `focus` reveal runs on it too.
- The `<video>` stays rendered under the canvas (never `display: none`): WebKit fires `requestVideoFrameCallback` only for a video that is rendered, and the plain video is the fallback (lead's research, not re-checked here).
- Draw triggers: `requestVideoFrameCallback` on every presented frame (playing, and paused seeks where the engine reports them), `seeked` (a paused frame change, in case rVFC is silent there), and a layout effect on a slider change (synchronous, so the new strength is on the next paint). No rAF loop: nothing runs while idle. rVFC is in Chrome 83 and Safari 15.4 (MDN BCD), both below the build target, so there is no fallback loop.
- `top` (the brightest local mean, which caps the highlights) is smoothed while playing like the backend's per-frame EMA: `alpha = 1 − exp(−Δt / TAU)` from the `mediaTime` step. Paused, after a seek, after a jump over 1 s and on the first frame the frame's own value is used (alpha 1). A slider change during playback keeps the smoothed value (alpha 0).
- Fallbacks, each leaving the plain video and everything else working: no WebGL2, no `EXT_color_buffer_float` / `EXT_color_buffer_half_float`, a shader that does not link (its log goes to `console.warn`), a lost context, a throwing upload. A throw in a draw (a `SecurityError` from a cross-origin frame without CORS, WebGL spec, Origin restrictions) marks the preview broken for the session, so a failing upload is not retried on every frame. The exact AI frame does not need WebGL and still shows.
- CORS: the `<video>` has `crossOrigin='anonymous'`, so the proxy request is a CORS request. **The backend must answer the proxy URL with `Access-Control-Allow-Origin` (and allow the `Range` header) before this build ships**: without it the video itself fails to load (`failed`, "The video did not load"), not only the preview. A side effect: the Lift frame copy (`drawImage` into a 2D canvas) is no longer tainted; nothing reads it back anyway. The dev mock serves the proxy from the same origin (`/__dev/`) or as a `blob:` (Dev panel), so it never exercises CORS.

## Look context

One canvas and one WebGL2 context for the page (`gpu` in `look.jsx`), created on the first mount. When the effect is switched off the canvas leaves the DOM (owner rule: nothing invisible stays mounted) but the context and its programs stay in memory, so dragging the exposure through 0 does not recreate a context and recompile five programs in the middle of the drag, and repeated toggles cannot pile up contexts (browsers cap the number of live WebGL contexts and drop the oldest).

- The canvas is inserted into `.viewer-look` only after a draw succeeded (`paint`), so a failed or not-yet-possible draw (no frame yet, `readyState < 2`) never shows an empty opaque canvas (it has `alpha: false`, so an undrawn canvas is black).
- `webglcontextlost`: `preventDefault()` (without it the context is never restored), `draw` dropped, the component re-renders and removes the canvas. `webglcontextrestored`: `createLook` rebuilds programs and textures on the same canvas, and the next draw puts it back.
- `gpu` is module state (like `live` in `hooks/player.js`): there is one viewer.

## Look GL

`createLook(canvas)` returns the draw function `(video, {t, ev, hdr, alpha}) => drawn`, or `null` when WebGL2 or a renderable float format is missing; it throws when a program does not link (the caller catches). Per draw: upload the frame, 12 passes, no reads.

- Upload: `texImage2D(TEXTURE_2D, 0, RGBA, RGBA, UNSIGNED_BYTE, video)`, the whole frame at level 0 every draw: WebKit's GPU fast path for video; `texSubImage2D`, float targets or `UNPACK_FLIP_Y` would take a slow path (lead's research). So the texture is top-down (row 0 = the top of the picture), and only the last pass flips (Look shaders).
- Grid targets: `RGBA32F` when `EXT_color_buffer_float` exists, else `RGBA16F` with `EXT_color_buffer_half_float`. Every grid read is `texelFetch` with `NEAREST`, and the bilinear sampling of the maps is done by hand in the shader, so no float texture is ever filtered: `OES_texture_float_linear` is missing on many iPhones (lead's research). `RGBA16F` loses precision in the guided filter (`log²` near 100 has an fp16 step of about 0.06 against `EPS` 0.3; reasoned): it is only the fallback.
- No `getError`, `readPixels` or `checkFramebufferStatus` in the frame loop. The link status is read once, when the programs are built.
- Full-screen triangle from `gl_VertexID`, no vertex buffers. Two-target passes (`POOL`, `COEF`) write two grid textures at once (`drawBuffers`).
- The grid textures are rebuilt (old ones deleted) only when the video size changes, which is once per job.

## Look shaders

`look-glsl.js` mirrors `grid()` and `apply()` of `backend/rounds/look.py`, plus the display step of `look.Look` and `color.to_sdr`. Every constant is a `#define` generated from `LOOK`; the derived ones (mobius `a`, `b`, `K`; `pq_inv(HDR_PEAK)`, the EETF knee) are computed in JS from the same object.

- Passes on the grid (long side `GRID` 256, size `round(n × 256 / max(w, h))` with Python's round-half-to-even, `even` in `look-gl.js`): `POOL` (the exact `adaptive_avg_pool2d` cells of the R'G'B' frame, then linearized: the backend pools Y'UV then converts, and Y'UV → R'G'B' is affine, so the order matches; out: `log`, `log²` and the clip-weighted `x × keep`, `lum × keep`), `BOX` twice per filter (separable, replicate padding as a clamped `texelFetch`: the same sums as the backend's 2-D `avg_pool2d` on replicate padding), `REDUCE` (max of `mi` over 8 × 8 cells per pass down to 1 × 1, the EMA folded into the last pass), `COEF` (`a`, `b`, `ratio`), `BOX` again (`A`, `B`). Then `APPLY` on the full frame: `rebuild` (SDR, `t > 0`), the base/detail split, `curve`, and the display step.
- Bilinear sampling of `A`, `B` and `ratio` at the pixel centre is `grid_sample(align_corners=False, padding_mode='border')`: `uv × n − 0.5`, clamped to `[0, n − 1]`.
- Orientation: `gl_FragCoord.y` counts from the bottom, the video texture and the grid from the top, so `APPLY` reads row `height − 1 − y`; everything before it stays top-down.
- Working space, linear light with 1.0 = SDR white. SDR job (`meta.transfer` `'sdr'` or missing): `v^2.4` (BT.1886, as the backend). HDR job (`'hlg'`, `'pq'`): the proxy is `zscale … t=linear:npl=100 → p=709 → tonemap=mobius:param=0.3:peak=10:desat=0 → zscale t=709` (`backend/rounds/media.py`), so the shader inverts it: BT.709 inverse OETF to linear in 100-nit units, then the mobius on `max(R, G, B)` analytically, `x = (y·b − K·a) / (K − y)` for `y > j` (ffmpeg `vf_tonemap.c` scales all three channels by `mobius(sig) / sig` with `sig = max(r, g, b)`), then `× 100 / 203`.
- Display: SDR `shoulder` (only when the look is on, as in `look.Look`), HDR the BT.2390 EETF on `max(R, G, B)` in the PQ domain (`color.eetf`, `HDR_PEAK` 1000, `SDR_WHITE` 203), then `v = lin^(1/2.4)` like `color.encode`.
- Approximations, all reasoned, none measured against a backend frame: HDR maps are pooled from the tone-mapped proxy and inverted per cell instead of pooled from the PQ / HLG source (the mean of a curve is not the curve of the mean, most at bright edges); HDR luma uses BT.709 weights on 709 primaries where the backend uses BT.2020 on 2020; the HDR display skips the 2020 → 709 matrix and `soft_gamut` (the proxy is already 709), so very saturated HDR colours can differ; the grid comes from the proxy size, the backend's from the source size (same aspect, at most one cell apart); the proxy is x264 CRF 23 in 4:2:0; `texImage2D` gives the browser's R'G'B' of the frame, the values the `<video>` shows. An HDR picture changes as soon as the effect is on, even at the lowest strength: the canvas shows the render's EETF where the plain proxy shows the mobius. That is the note's real look, not a bug.
- Cost: 11 small passes on about 256 × 144 cells and one full pass at the proxy size (long side ≤ 960). Not measured on a phone.

## Exact frame

The AI repair (FastDVDnet + Zero-DCE++) runs only on the server, so in the AI zone the preview asks for the real frame: `lookFrame` (`POST /api/jobs/{id}/look`, `{time, look, exposure}` → `{image, width, height}`, the whole display-oriented frame at proxy size with the complete effect; `services/README.md`).

- Asked only when `r > 0` (`split`), the video is paused and the device is online; not while a level slider is pressed (`adjusting`, `editor/README.md`, Slider lock); 350 ms (`DEBOUNCE`) after the last change of the frame or a slider, through the single flight (Single flight), which also locks the HDR and exposure sliders until it ends. No request offline (core, Offline); the live canvas keeps working.
- The answer belongs to its key (`time:look:exposure`): it shows only while the key still matches, so a seek, a slider move or play hides it at once and the live canvas is what shows; coming back to the same frame and values shows it again without a request.
- [DOC: ai-pending] While the exact frame is on its way (from the key change, through the debounce and the request, until the image is decoded or the request fails) a four-point sparkle sits in the bottom-right corner of `.viewer-look` and pulses grey → white (`ai-pulse`, 1.6 s, plus a slight scale). It shows while `key` is set, the device is online, no frame is shown and `settled !== key` (`settled` is set when a request for that key finishes, success or failure), so a seek, play or a slider move removes it at once, and a failed request clears it (no endless spinner); offline it never appears. Known limit: after a failed request the same key shows no indicator on a retry (the frame is revisited), only a new key does. It fades in and out with `usePresence`; `prefers-reduced-motion` leaves it static white. Its colours are fixed (grey `#8e8e93`, white) because it sits on the video, not on themed chrome.
- Shown as an `img` over the canvas: decoded first (`img.decode()`, web.md), then mounted with `appear` (`--dur-long`); on a key change it fades out over `--dur` (`usePresence`, `data-leaving`) and is unmounted.
- Failure (409 while the proxy is not ready, 502 from the GPU call, offline, `?job=nolook` in the mock): nothing shown, no message; the honest preview stays. There is no pending indicator either; whether the owner wants one is open.

## Lift source

The lifted copy of the object (Lift look) must match the graded frame around it. When a Lift layer mounts it paints its canvas from the `<video>` and then dispatches `STAGE_EVENTS.ask` on the stage; a mounted preview answers in the same task: it draws and dispatches `STAGE_EVENTS.paint` with `detail` = the current source (the exact AI image when shown, else the preview canvas, or `null` when it has none), and the layer repaints from it. The preview also sends `paint` after every paused draw, when the exact frame appears or goes, and with `null` when it unmounts (the copy goes back to the plain video).

- Synchronous on purpose: a WebGL canvas without `preserveDrawingBuffer` is readable by `drawImage` only in the task that drew it (the drawing buffer may be cleared once composited, WebGL spec, The Drawing Buffer), so the preview always draws right before it hands the canvas out. `preserveDrawingBuffer: true` was not used: it costs a copy on every frame.
- Events, not a function in `refs`: the lazy component writing into the `refs` prop was flagged by oxlint (`react(immutability)`), and the ask / paint pair needs no shared mutable slot.
- The AI image is handed out as the decoded `Image` object, not the mounted `img` (which may not have loaded its data URL yet).
- The layer canvas is resized only when the video size differs. Setting `width` / `height` reallocates and clears the backing store even to the same value (HTML spec, canvas, "set bitmap dimensions"). The preview sends `paint` on every slider step, so the old code did one reallocation per step and per layer.

## Follow

Owner request 2026-10-27: when the playhead leaves the selection frame, the dot and the box move with the object. Before this, they stayed where they were and dimmed. `follow.js` (`useFollow`) asks the backend for the object's box over the trim range (`services/README.md`, Follow; `backend/rounds/README.md`, Track preview: SAM 2.1 video on the warm `Lift`, 10 samples/s up to 36 s, 6 up to 60 s) and moves the marks imperatively.

- When it asks: 600 ms (`DELAY`) after the selection, the lifted mask or the trim settles, never while the lift is pending (the mask is the better prompt). It sends through the single flight (Single flight). The server also drops a superseded follow within one step, so re-selecting never stacks 40 s GPU calls.
- Cache: a path answers for its selection (`time`, `points` and `box` identity). A new selection drops it at once, so old offsets never shift new marks. A trim change keeps it, and asks again only when the trim leaves the covered span (± `SLACK` 0.2 s): narrowing the trim is free.
- Placement: `place` runs on every player store change (`watchPlayer`, `hooks/README.md`, Watch player). It runs at the presented-frame rate while playing, with no Preact render. The marks layer gets `style.translate` = the box centre at `t` minus the centre at the selection frame, both linearly interpolated between samples, in percent of the stage (the layer is `inset: 0`, so `%` is the frame). The style is written only when the string changes. On the selection frame itself and where the box is lost (`null`) there is no shift and `data-follow` is off, so the marks dim as before (Selection frame).
- Translate only: dots keep their pixel size, and the box keeps its drawn size. Scaling with the object (the box-size ratio, the backend agent's suggestion `p' = b_k + (p − b_p) × size_k / size_p`) is not built.
- Smoothness: `data-glide` (set while paused) adds a `translate` transition of `--dur-long`, so a seek or a frame step glides the dot to its new place. While playing there is no transition: per-frame values with a transition would lag behind the object.
- `[data-away][data-follow]` keeps the marks at 0.85 opacity (followed, not the selection frame). Tapping elsewhere still moves the selection (Selection frame).
- Mock: `dev/client.js` answers `/track` with a synthetic sine path after 900 ms (`window.mockTracks`). Checked (Edge headless, 390 px, 2026-10-27): no shift on the selection frame, a gliding shift on a frame step, per-frame shifts while playing, no stale shift after a new selection, 2 requests for 2 selections, no console errors. Not checked: the real SAM path and the feel on the iPhone.

## Single flight

Owner rule 2026-10-27: a new event replaces the previous one and takes over its values; nothing queues up and nothing leaks. Both GPU calls of the viewer, `/segment` (`useLift`) and `/look` (`Look`), go to the one `Lift` container (`max_containers=1`, `backend/rounds/README.md`, Lift). Before this, every tap or debounced slider pause started a call, and the calls ran back to back. Device log: a burst of `/look` calls at about 0.85 s each, with the outline answer waiting behind them.

- State in a ref: `want` (the latest wanted request, or null) and `busy` / `flying`. At most one request per kind is in flight. A new event only overwrites `want`. When the flight lands, its answer is used only if `want` is still the same object; otherwise the newest `want` is sent (Lift) or, if it was queued after its debounce (`queued`), flown (Look). So a burst of N events costs at most 2 calls: the one in flight and the last one.
- No `AbortController`: aborting the fetch would not stop the GPU call on Modal; the single flight is what keeps the container free.
- `Look` raises the editor's `previewing` from the start of a flight until it lands with nothing queued, and lowers it on unmount. That draft flag locks the HDR and exposure sliders (`editor/README.md`, Slider lock). `want` is cleared while a slider is pressed, during playback and offline, so a landing flight then releases the lock without a new call.
- `DEBOUNCE` 350 ms is at least the slider's double-tap window (`DOUBLE` in `components/slider.jsx`). With a shorter debounce the first tap of a double tap would start a flight, and the lock would swallow the second tap (the exposure reset). Change both together.

## Tiers

On a `free` job (`editor/README.md`, Tiers) `useLift` and `useFollow` get no job id: no warm calls, no outline, no track preview, which the free server would refuse with 403. Points and the box still work: they centre the free crop.
