# local

Work done on the user's device in the browser version (owner decision 2026-10-28: everything the hardware can do runs locally; Oracle next; Modal last). Web-only: `features/web/web-app.jsx` loads these modules with dynamic `import()`, so none of it reaches the Mini App, and Mediabunny (442 KB raw, 112 KB gzip, the `render-*.js` chunk, with the four input formats below) is fetched only when a file is dropped. Files: `probe.js` (read a file), `render.js` (the note), `hevc-decoder.js` (WASM CPU HEVC decoder fallback), `loudness.js` (BS.1770 loudness), `denoise.js` + `denoise-worker.js` (DeepFilterNet3 WASM), `look.js` (WebGL exposure / honest HDR), `models.js` (ONNX model cache, device check, the model worker's client), `model-worker.js` (the one ONNX Runtime worker), `lift-local.js` + `lift-mask.js` (SAM 2.1 tiny tap-to-lift), `track-local.js` + `light-frames.js` + `track-infer.js` + `track-measure.js` + `tpos.js` (SAM 2.1 video tracking, WebGPU only), `camera.js` + `camera-lp.js` + `spline.js` (camera path), `motion.js` + `motion-worker.js` + `motion-flow.js` + `motion-fit.js` (stabilization motion), `gl.js` + `warp.js` + `fill.js` + `fill-gl.js` (stabilization warp and edge fill, WebGL2), `stabilize.js` (stabilization wiring), `plan.js` (which executor), `server.js` (the Oracle / Modal path).

## Local probe

`probe(file)` opens the file with Mediabunny (MP4, QuickTime, WebM, Matroska only: `ALL_FORMATS` pulled in audio-only formats nobody drops), refuses a file without a decodable video track ("This file cannot be read as a video"), and returns `meta` shaped like the server's (`width`, `height` display-oriented, `duration`, `has_audio`, `tags` from `getMetadataTags()`, `interpolable` from `computeFrameRateMetrics()`) plus `off`, the codecs this device cannot encode (Local encoders), and a filmstrip: 24 frames of 96 px height in one JPEG sprite behind a blob URL (Filmstrip mips), the same `{tiles, tile_width, tile_height}` as the server's (`backend/rounds/media.py`, `TILES`, `TILE_H`). The sprite is made before the editor opens because `Editor` resets its draft whenever `job` changes identity; a sprite that fails leaves the strip empty and the editor works. `meta.hdr` (`track.hasHighDynamicRange()`) marks an HDR source: WebCodecs would encode its frames as SDR without tone mapping and the colours would come out flat, so an HDR file never renders locally (Local plan): the server does it (`backend/rounds/media.py`, `sdr_chain`, zscale + mobius). `meta.transfer` stays unset on purpose: the viewer's look preview reads it to undo the server proxy's tone map, and a local file is played as is. Not verified: that `hasHighDynamicRange()` is true for an iPhone HLG clip in Chrome (reasoned from Mediabunny's doc, not run).

- The editor plays the file itself (`URL.createObjectURL`, no proxy): a 4K source plays as well as the browser decodes it. A file the `<video>` element cannot play shows "This browser cannot play the video".
- `interpolable` and `tags` are probed locally, so "Smooth to 60 fps" and "Keep original metadata" show immediately when the file qualifies. "Keep original metadata" is local (`local: true`, `LOCAL_OPTIONS`); "Smooth to 60 fps" requires the server (Modal).

## Local frame

`frameOf` ports `crop.frame` (`backend/rounds/README.md`, Free frame; change both together): one fixed square for the whole range, centred on the box, else on the mean of the positive points, else on the frame centre, clamped inside the frame; side = the short side, with zoom and a box the box's long side × 1.6 but not under a quarter of the short side, rounded down to even. Checked 2026-10-28 against hand numbers for a 1920 × 1080 source (centre, box, box with zoom, an edge point). No tracking and no edge fill locally, so the frame never leaves the picture.

- [DOC: crop-mode] With `prompt.crop` (`viewer/README.md`, Crop mode) the margin is 1, not `ZOOM_MARGIN`: the square is the box's long side, which the viewer already snapped to a square. `follows` is false for a crop, so the render never tracks, and `plan.js` does not count a cropped box as following (`picked`): no Modal and no "following the object" in the fallback list. Oracle and the device can render it.

## Local encoders

The encode is WebCodecs through Mediabunny's `Conversion` (trim, `crop`, resize to 640², re-encode, `tags` kept when `options.metadata` is on via `keepTags`, else `() => ({})` like the server). Owner rule (2026-10-29, replaces "hardware only" of 2026-10-28): local wherever the browser can encode the picked codec, in hardware or in software, and AV1 stays the default (no automatic switch to HEVC). `encoders()` asks `canEncodeVideo(codec)` with no acceleration hint (WebCodecs' default `no-preference`; Mediabunny passes `undefined` through) and returns the codecs that fail; the encode passes no hint either, so the browser takes a hardware encoder where it has one; they are disabled in the codec picker (`meta.off`, `editor/options.jsx`) and trigger the server path for a signed-in user or a block with a message for an anonymous one (Local plan).

- Why the hint was dropped: on the owner's PC (2026-10-28, GTX 1660 Ti, Firefox and Edge) `prefer-hardware` turned all three codecs off, so an anonymous user could do nothing. Expected for AV1 and VP9: Turing NVENC encodes only H.264 and HEVC (NVIDIA's NVENC support matrix; AV1 encode starts with the RTX 40 series, VP9 encode has never been in NVENC). HEVC: Edge answered `isConfigSupported({codec: 'hvc1.1.6.L93.B0', …, hardwareAcceleration: 'prefer-hardware'})` with `supported: false` (owner, 2026-10-29), so that Edge build does not hand NVENC HEVC to WebCodecs; why is not known. A browser's software encoders are its bundled libraries (Chromium: libaom / libvpx; no software HEVC encoder), so HEVC stays off on such a machine and AV1 / VP9 run on the CPU. The GPU's shader cores cannot stand in: a page reaches them only through WebGPU / WebGL, and no browser encodes video with them.
- **Not verified:** that Firefox's WebCodecs offers AV1 and VP9 encoding on the owner's PC, and how fast a software AV1 encode of a 60 s 640² note is there. The server encodes on the CPU too, never with the GPU (`backend/rounds/encode.py`: libsvtav1, libx265, libvpx-vp9); Modal's GPU runs only the models (tracking, lift, RIFE, repair). The page also has to be a secure context: `http://localhost` is, a LAN address from `--host` (`http://192.168.…`) is not, and there `VideoEncoder` and `crypto.subtle` do not exist.
- A test in headless Edge (no GPU) needs the hint stripped (`VideoEncoder.configure` / `isConfigSupported` patched in a scratch page): then AV1 encoded in software and the round came out as a valid 640² AV1 + AAC MP4 (2026-10-28, `ffprobe`).

## Local size

Every note spends the 10 000 000 B budget like the server (`encode.NOTE_BYTES`, `backend/rounds/README.md`, Note size), but WebCodecs has no two-pass mode (owner: a second encode costs too much time), so: constant bitrate = `(10 MB × 8 × 0.92) / duration − 128 kbit/s audio`, capped at 14 Mbit/s like the server, then the file is **measured**; over the cap it is encoded again with the rate scaled by `0.95 × cap / size`, up to 3 tries, then an error ("try a shorter range"). `HEADROOM` is 0.92 against the server's 0.97 because one-pass constant rate lands further from its target than two-pass ABR. A software encoder on easy content ends far under the cap (6 s of a test pattern: 2.9 MB); a hardware one is expected to fill it, not measured.

- Audio: AAC at 128 kbit/s through `forceTranscode` (a copied track could blow the budget), else Opus if the browser cannot encode AAC, else the round has no sound and the result card says so. **Not verified:** that Telegram plays Opus in MP4 on iOS.
- Progress is `(tries done + share of this try) / 3`, so it never reaches 100 % before the last try ends.

## Local loudness

"Even out loudness" runs on the device (CPU, no ffmpeg). `loudness.js` `measure` decodes the trimmed audio once with `AudioSampleSink` and returns a gain envelope (one value per 10 ms); `apply` multiplies each sample by it inside Mediabunny's `audio.process` (`sampleFormat: 'f32'`, so the hook gets interleaved float). The job object carries `local: true` in the web shell and an option with `local: true` in `OPTIONS` (`editor/draft.js`, `locked(tier, item, device)`) skips its tier lock; the Mini App job has no `local`, so it is unchanged.

- Integrated loudness is BS.1770-4: K-weighting (two biquads, coefficients computed for the sample rate), 400 ms blocks every 100 ms, absolute gate −70 LUFS, relative gate −10 LU. Gain = −16 LUFS minus that, capped at +24 dB. All channels weigh 1 (a 5.1 source would read a little loud; phone clips are mono or stereo).
- [DOC: local-limiter] The gain is also cut where peaks need it: per 10 ms block `min(gain, ceiling / peak)`, then a minimum filter of radius 4 blocks and a moving average of radius 2, so the curve at both centres around any block never exceeds what that block needs (a smaller min radius let the interpolated gain overshoot next to a peak: found by a Node check of the envelope). The 1 kHz sine check: a mono −20 dBFS sine reads −23.01 LUFS, as BS.1770 says. The ceiling is −1.5 dBFS on the sample peak, which leaves 0.5 dB for inter-sample peaks against the −1 dBTP target (reasoned, not measured).
- **Differs from the server** (`ffmpeg loudnorm`, I −16, TP −1, LRA 7, dynamic): the gain is static except around peaks, so a very uneven recording is not compressed, only levelled overall.
- **Not verified:** nothing here has run in a browser. Check with the owner's PC: render a clip, then `ffmpeg -i note.mp4 -af ebur128=peak=true -f null -` should read about −16 LUFS integrated and a true peak under −1 dBTP; also that timestamps given to `process` are relative to the trim start (read from Mediabunny's `conversion.js`, not run).

## Local denoise

[DOC: local-denoise] The "Reduce noise" slider (`request.denoise`, `0..1`, `local: true` in `editor/draft.js`, `'denoise'` in `LOCAL_OPTIONS`) runs DeepFilterNet3 on the CPU in a module Web Worker (`denoise.js` + `denoise-worker.js`) via `@lofcz/deepfilternet-web@0.1.0` (MIT OR Apache-2.0, WASM SIMD build of `libDF` / tract 0.23 with the DeepFilterNet3 weights embedded in `df_bg.wasm`, 32.55 MB raw / 12.12 MB gzip; emitted as a separate asset and worker chunk so nothing is fetched unless `denoise > 0`).

- `decode(input, start, end)` decodes the trimmed range with `AudioSampleSink` into zero-initialized planar `Float32Array` channels (up to 2 channels; placing samples at `(sample.timestamp - start) * rate` fills timestamp gaps with silence like `GAPLESS` on the server) and linearly resamples to 48 kHz (`SAMPLE_RATE`) when the source rate differs. `denoise` transfers the channel buffers to the worker and calls `worker.terminate()` in `finally`, freeing the WASM instance and linear memory before video encoding begins.
- Strength mapping matches `backend/rounds/audio.py` (`VOICE_DB`): `attenOf(s) = 6 * (100 / 6) ** s` dB (`6..100` dB on a log scale), passed as `attenuationLimit` to `DeepFilter.create({attenuationLimit: atten, wasmUrl: {module_or_path: wasm}})`. Passing `{module_or_path: undefined}` in the browser satisfies `wasm-bindgen`'s object check in `__wbg_init` (suppressing its deprecation warning) and lets it fall back to `new URL("df_bg.wasm", import.meta.url)` inside the worker chunk.
- Delay compensation: `libDF` works on 480-sample (10 ms) frames at 48 kHz and has a 3-frame (1440-sample, 30 ms) STFT + lookahead delay (verified by cross-correlation in Node: `bestLag: 0` after dropping 3 frames, matching `deep-filter -D` on the server). `cleanOne` pads `DELAY = 3` silent frames at the end and drops the first 3 output frames, so the output has the exact input length and 0 lag. Dual-mono stereo (`same`) runs the network once and clones channel 0; distinct stereo channels create a fresh `DeepFilter` handle for channel 1 (reusing the compiled WASM module). The server's 6 dB `HEADROOM` pre/post scaling is omitted: `libDF` in WASM takes and returns `f32` directly without the 16-bit WAV round-trip of the `deep-filter` CLI (verified in Node: 1× vs 0.5×·2 max diff `1.5e-3`).
- Stage order matches `backend/rounds/audio.py` (Audio chain): denoise first, then loudness. When both `denoise` and `options.loudnorm` are on, `loudness.js` `levelPlanes(clean, SAMPLE_RATE)` measures BS.1770 integrated loudness and peaks on the denoised 48 kHz planes and applies the gain envelope in place before `encode()`.
- `replace(clean)` feeds the 48 kHz channels through Mediabunny's `audio.process` (`processedSampleRate: 48000`, `processedNumberOfChannels: clean.length`). Each returned `AudioSample` gets a freshly allocated `Float32Array` (`.slice()` for mono, interleaved copy for stereo), never a `.subarray()` view: Mediabunny 1.63.0's `AudioSample.toAudioData()` (`sample.js`) passes `this._data.buffer` to `new AudioData` and ignores `byteOffset`.
- Verified in Node (2026-10-29): white-noise drop matches `attenOf(s)` (`s = 0.01 / 0.25 / 0.5 / 1.0` → `−6.2 / −12.1 / −24.5 / −∞` dB), 0-sample lag, ~20× realtime mono on the owner's PC, `levelPlanes` + `replace` sample continuity. **Not verified in a browser or by ear yet** (needs the owner's listen test).

## Local crop draw

[DOC: local-crop-draw] Every local render, the fixed crop (`frameOf`) and the tracked one (`sampler`) alike, crops in `look.js` (`cropper`) inside Mediabunny's `video.process`; `encode` in `render.js` passes the fixed crop as a constant `at`. Mediabunny's own `crop` (the Conversion `crop` option and `drawWithFit({crop})`) is never used: both end in `drawImage(videoFrame, sx, sy, sw, sh, …)`, and WebKit ignores the source rectangle of a `VideoFrame` ([WebKit bug 260459](https://bugs.webkit.org/show_bug.cgi?id=260459), Safari 17+), so on iPhones the whole frame was squeezed into the square (owner 2026-10-29, every video, both iPhones; desktop browsers were fine).

- How: `drawWithFit(ctx, {fit: 'fill'})` (whole frame, so the ignored rectangle does not matter; Mediabunny still applies rotation and flip) under a canvas transform that scales the frame to `displayWidth × k` and shifts it by `-left × k, -top × k`, with `k = target / s`. The crop never leaves the frame (`at` is clamped), so nothing stale shows.
- Downscale: one draw with `imageSmoothingQuality = 'high'`. A multi-step halving (mipmapping on a reused canvas, as Mediabunny does, against the shimmer a single bilinear step over more than 2× can give on a 4K source) was written and removed (owner 2026-10-29: compare real rounds side by side first, once the phone renders work, instead of switching it on blind). Not compared yet.
- Checked 2026-10-29 in headless Edge (scratch probe, a frame whose colour encodes x and y), with the multi-step version: offset crop, small crop, 4K and a 90° rotated sample, all within one colour step of the expected pixels. The single draw uses the same transform, not rerun. Not run in WebKit (no Safari here); the owner checks a round on the iPhone.
- Do not "simplify" back to Mediabunny's `crop`. The model frames (`track-local.js`, `lift-local.js`) take the whole frame (`fit: 'fill'`, no crop), so they are not affected.

## Local exposure

[DOC: local-exposure] The Exposure slider and the honest part of the HDR slider (`look` up to `LOOK.HONEST` = 0.4) run on the device: `look.js` `grade(look, ev, size)` is Mediabunny's `video.process`; its look part is `toner(look, ev, size)` (`{canvas, ctx, tone(timestamp), on}`, the look applied in place to a 640² 2D canvas), which `stabilize.js` reuses on the warped frame. Each frame is cropped and scaled to 640² on a 2D canvas (Local crop draw), run through the viewer's own WebGL pipeline (`viewer/look-gl.js` `createLook`, so the render matches the preview: highlights compressed, never clipped, local tone mapping and clipped-channel rebuild) with `t` from `split(look)` (`0..1`), `ev`, `hdr: 0`, and drawn back to the 2D canvas, which is returned. The 2D canvas is returned and not the WebGL one because a WebGL canvas without `preserveDrawingBuffer` may be cleared before the encoder reads it. The pipeline's temporal smoothing of the top luminance uses the preview's `LOOK.TAU` with the frame spacing.

- `createLook` takes anything with `videoWidth`, `videoHeight`, `readyState` that `texImage2D` accepts; the canvas gets those three as plain properties so `look-gl.js` stays untouched (it ships in the Mini App chunk `look-gl`).
- Measured on the whole 640² crop, the preview on the whole source frame: the guided-filter grid and the top luminance differ a little, so the render can differ slightly from the preview (reasoned).
- `look` in `editor/draft.js` has `local: LOOK.HONEST` (0.4): for `local` (anonymous) users in the web shell the slider is unlocked and its `max` is capped at `LOOK.HONEST` (40 steps of 0.01, the honest zone only); `free` and `pro` users keep the full `0..1` slider, render locally while `look <= LOOK.HONEST` (`localLevel` in `plan.js`), and go to the server in the AI zone (`look > LOOK.HONEST`): Modal for `pro`, Oracle for `free` (Zero-DCE++ without the denoise, `backend/rounds/README.md`, Free look). Since 2026-10-30 Oracle runs `look` and `exposure`, so `gate` no longer blocks them for `free`.
- A browser without WebGL2 float render targets fails the render with "This browser cannot adjust HDR or exposure".
- **Not verified:** nothing has run in a browser: neither that Mediabunny snapshots the returned canvas (reasoned from the types) nor the look of the result.

## Local metadata

[DOC: local-metadata] `probe.js` `tagsOf` filters `getMetadataTags()` to the 10 keys of `backend/rounds/tags.py` (`creation_time`, the six `com.apple.quicktime.*` movie keys and the three `com.apple.quicktime.camera.*` keys), mapping aliases (`location`, Android `©xyz`, `make`, `model`, `software`, `date`, `©day`, `©mak`, `©mod`, `©swr`) without overwriting a canonical key and dropping other `com.apple.quicktime.*` keys (`live-photo-info`, `content.identifier`, `full-frame-rate-playback-intent`). ## Stage cache

[DOC: stage-cache] `stage-cache.js` `stage(parts, make, onHit, cap)` caches the output of the two slow local stages so that changing only a later option (codec, look, exposure, loudness, metadata) does not redo them (owner-approved 2026-10-29). Frames are never cached (gigabytes), so the final encode always runs.

- Cached: `trackLocal` (`{found, cuts}`: typed arrays and a plain array) and `denoise` (the 48 kHz `Float32Array[]` planes). Not cached: loudness. `levelPlanes` on cached planes is a CPU pass over a minute of audio (cheap), and `measure` returns a tiny envelope after one decode; a cache would save about one audio decode, not worth the complexity.
- Key: SHA-256 (`crypto.subtle`, hex) of `JSON.stringify([VERSION, ...parts])`. Track parts: `identity(file)` (`name`, `size`, `lastModified`), `start`, `end`, the whole `prompt` (time, points, box), and `gpu` from `deviceOf()` (the CPU rate differs from the 30 fps GPU grid, so the results are not interchangeable). Denoise parts: file identity, `start`, `end`, `strength`, `SAMPLE_RATE`. Bump `VERSION` in `stage-cache.js` whenever the tracker, resampling, decoder or DeepFilterNet output changes: old entries then never match and age out by LRU.
- Storage: IndexedDB `rounds-stage-cache-v1`, store `meta` (`{key, size, used}`) and store `data` (the structured-cloned value). Structured clone keeps typed arrays bit-exact (NaN and 1e300 round-trip, checked in Edge). Why not OPFS: writing through `FileSystemFileHandle.createWritable` is Baseline only since September 2025 (MDN, `FileSystemFileHandle.createWritable`, "Baseline 2025"), i.e. Safari 26, while the build target is iOS 18 / Safari 18 (`miniapp/README.md`, Build target). The iOS 18 alternative is `createSyncAccessHandle`, which exists only in a dedicated worker and would need a worker for I/O. IndexedDB with binary values works in every target engine.
- Cap `CAP = 400_000_000` B total. A write sums the `byteLength` of all planes, drops the least recently used entries (`used` is refreshed on every hit) until the new entry fits, and skips an entry bigger than the cap. `meta` is separate from `data` so eviction never loads values.
- Best effort: every failure (no `indexedDB`, no `crypto.subtle` outside a secure context, private mode, quota, abort) is a miss, and a failed write is swallowed; the render never fails because of the cache.
- Ordering trap: the write is awaited inside `stage`, because the structured clone is taken when `put` runs, and `levelPlanes` mutates the planes in place right after `denoise` returns. A fire-and-forget write would cache the levelled audio.
- Progress: a track hit calls `onProgress(1)`, so `renderNote` jumps to its 0.4 share; a denoise hit has no progress of its own.

## Render progress

`trackLocal` reports 0 to 1 in two parts: model load and prepare (`ready` with `onPrepare`) is the first `LOAD_SHARE` (0.1), then one report per tracked frame fills the rest. Owner report (iPhone XR, 2026-10-30): the card sat at 0 % for minutes and then moved in steps, because reports came every 10 frames on GPU (one per 1-2 minutes on a slow phone) and nothing was reported during load. Contract for the smooth bar (`web/README.md`, Web progress): reports are non-decreasing, in 0..1 per stage, as often as the work allows (at least one per unit of work, never batched); the bar eases between them, so sparse reports are fine but each one should be real.
- [DOC: render-progress] `renderNote` calls `onProgress(share, text)`; the analysis share 0.4 is split evenly over the stages that run (tracking, motion), each stage going 0 → 1 inside its slice and kept non-decreasing (`Math.max`), so the bar starts at 0 whatever runs and the encode continues from 0.4; the text is `TRACKING` ("Following the object…") when tracking runs, else `STEADYING` ("Steadying the video…"); the encode passes no text (the web shell shows "Rendering…"). `runTrack` reports every frame on the CPU and every `PROGRESS_EVERY = 10` frames on WebGPU: on an iPhone XR (CPU) one tracked frame takes several seconds, and with a report every 10 frames the card sat at 0 % "Rendering…" for about two minutes (owner 2026-10-29). The render tracks again even right after a preview: the preview keeps only boxes on a coarse grid, the render needs centre, radius, area and histograms at its own rate.
- Limits: a hit still needs `deviceOf()` (cheap) but skips `ready()`, so no model session is created. The file is identified by name, size and `lastModified`, so a different file with all three equal collides (accepted). A cache entry is per trim range: moving the trim by a frame misses.
- **Verified** in headless Edge (2026-10-29, scratch page): key hit, exact typed-array round trip, LRU eviction at a tiny cap, oversize entry treated as a miss. **Not verified:** Safari / iOS, real tracking hits.

## Local plan

Routing priority for every stage that can run in several places (owner 2026-10-30, `CLAUDE.md`, Owner decisions): WebGPU on the device, Oracle CPU, the device CPU, Modal last, and Modal only when the stage cannot run elsewhere or is clearly faster (about 2–3x counting its cold start; 3–5 minutes or more, not about a minute). The routing below is the part of it that `plan.js` implements.

`needsServer(body, job)` decides the executor from the same body the Mini App would post: any option outside `LOCAL_OPTIONS` (`zoom`, `loudnorm`, `denoise`, `look`, `exposure`, `metadata`), any non-zero level outside `LOCAL_OPTIONS` or past its local cap (`look > LOOK.HONEST`), a codec the device cannot encode, or an HDR source (`meta.hdr`). On `pro`, `needsModal` sends a selection to Modal (follow). Since 2026-11-01 `needsServer` is also true for a `pro` selection on a slow device (`job.fast === false`, Speed gate), so it goes to Modal instead of tracking on the phone. On `local` / `free` a selection renders on the device and is followed: SAM 2.1 on a fast device (Local tracking), VitTrack on a slow touch device (Light tracking). (This entry used to say a selection without WebGPU centres one fixed crop; `render.js` has followed on the CPU since the CPU tracking path of 2026-10-29.) Until 2026-10-29 a selection without WebGPU blocked the anonymous render ("Tracking requires WebGPU"): that cut off every iPhone on iOS 18 (no WebGPU in the Mini App's WKWebView, and off by default in Safari; WebGPU by platform) from the render the device did before tracking existed, so the fixed crop is the fallback again. `gate(draft, job)` is the editor's `gate` prop (`editor/README.md`, Editor seams): `{network: false}` for a local render (it works offline and is not blocked by the connection), `{block, note}` when nothing can run (anonymous user and an unsupported codec; a file over 2000 MB on the server path), `{network: true, note}` for the server path.

- The server note names its reason (`reasonOf`, the first that applies: HDR source, codec, a slow `pro` selection, then the first option, then the first level), followed by "The round arrives in your Telegram chat." `needsServer` is `Boolean(reasonOf(…))`, so the note and the routing cannot disagree. Why (owner 2026-11-06): the old generic "The server renders this one" read as a bug that any toggle triggers. Observed in headless Edge as `pro`: on an SDR clip only Smooth to 60 fps brought it; on an HLG clip it stood from the load on, whatever was toggled, because an HDR source never renders on the device (Local probe). An iPhone films HDR by default, so on the owner's clips every signed-in render goes to the server (Oracle unless a Modal option is on).

## Local server

The path for what the device cannot do, for signed-in users: `POST /api/uploads`, parts in 3 lanes (50 MB each, 3 tries per part), `POST …/uploaded`, poll `GET /api/jobs/:id` every 2 s until `ready` (a failed ingest throws its reason), then `POST …/render` with the editor's body. The router picks the backend by the user (`router/README.md`), so an allowed user's job lives on Modal and everyone else's on Oracle; the round arrives in the user's Telegram chat (the bot also sends its editor-button message for the uploaded video). `sendNote` posts a finished local round to `POST /api/notes` (`backend/rounds/README.md`, Client note).

## Modal fallback

[DOC: modal-fallback] Owner request 2026-10-29: when Modal is out of credits or down, the service must keep working on Oracle instead of dying. The router does the switching (`router/README.md`, Modal fallback): an answer from Oracle in Modal's place carries `X-Rounds-Via: oracle`; what cannot move (a job whose files are on the Modal Volume, a streamed upload part) gets `503 {code: 'pro_unavailable', detail}` with `Retry-After: 180`. The client side:

- `respond` in `services/api.js` returns the body and `X-Rounds-Via`; a failed request's `Error` carries `status` and `code`.
- `prepare`: when `POST /api/uploads` came back from Oracle, every later call of that job adds `?via=oracle` (parts, `uploaded`, the poll), and the job is returned with `oracle: true`.

## Edge sam cast

[DOC: edge-sam-cast] EdgeSAM's published decoder has two `Cast` nodes to `int16` (`/Cast_6`, `/Cast_10`) that ORT Web cannot run (`Could not find an implementation for Cast(9)`). Instead of hosting a fixed copy, `weights.js` patches the bytes after the SHA-256 check: in an ONNX protobuf the attribute `to = 5` (INT16) is the byte run `0a 02 74 6f 18 05` (name "to", field `i` = 5), and setting the last byte to 7 (INT64) keeps the length, so nothing else moves. The original file has exactly these two matches; the result is byte-identical to the copy fixed with the `onnx` package and checked to run (2026-10-30). The cache keeps the original bytes (`cache.put` runs before the patch), so the size and hash checks still hold on the next read. A new EdgeSAM revision must be rechecked: a third match would be patched too.

## Model ready

[DOC: model-ready] `ready(group, names, {onReady})` calls `onReady()` as soon as it knows no download is needed: after a `cache.keys(url)` of every weight (reading the 67 MB bodies comes later). Never `cache.match` here: in WebKit `match` brings the whole body into the WebContent process at once (`DOMCache::doMatch` → `queryCache` with `ShouldRetrieveResponses::Yes`; the network process reads the blob file and sends it with the record, `CacheStorageCache::retrieveRecords`), while `keys` passes `No` and the body is dropped in the network process. The old `match().then(Boolean)` check left every unread body (lift 76 MB, tracking 83 MB, possibly twice with the mapped IPC copy) as garbage in the tab, and only a GC frees it. It was suspected for the SE2 deaths of every run that read the models from the cache, but the reloads kept dying after the change and with no cache read at all (2026-10-31, gpu-buffer-cache, fourth and fifth rounds); `keys` stays because it is the cheaper check anyway. The shell turns it into "Preparing tracking…" (or selection) at 0 % (Model prepare). A group already loaded skips all of it and calls `onLoaded()` at once. The browser shell turns it into the busy label on the point (`viewer/README.md`, AI progress). When a weight is missing, `onReady` is not called and the consent card is the first thing the user sees. A cached entry of the wrong size is only found while reading the body, after `onReady`; the label then gives way to the consent card (rare: a truncated write).

- [DOC: model-copies] `cache.put` gets the downloaded buffer itself: `new Response(buffer)` already copies the bytes (Fetch, "extract a body" from a BufferSource), so the old `buf.slice(0)` was a third 58 MB copy at the peak of the download. The buffer is then transferred to the worker.
- [DOC: model-drop] After `load` the worker frees the model bytes it does not keep (touch devices, `keep` false) with `buf.transfer(0)`: in JavaScriptCore that frees the old backing store inside the call (`arrayBufferCopyAndDetach` copies 0 bytes and moves the old contents into a local `ArrayBufferContents` that dies on return, `JSArrayBufferPrototype.cpp`), while a plain dropped reference waits for a GC of the worker's VM. ORT has its own copy by then (`InferenceSession.create` copies the bytes into the WASM heap). Lift 38 MB, tracking 83 MB. Why: the SE2 deaths right after the seed (gpu-buffer-cache, thirteenth round) happened only in runs whose load was fast; runs with a slow worker (the system busy reclaiming memory, so iOS likely sent memory-pressure warnings, and WebKit's critical release calls `WorkerGlobalScope::releaseMemoryInWorkers`, `MemoryRelease.cpp`) survived, and an idle pause did not help, which fits garbage that only a pressure-driven GC frees. Not yet proven on the phone.

## Model worker

- Quiet console (owner 2026-10-29: nothing in the production console): `ort.env.logLevel = 'error'` and `logSeverityLevel: 3` on every session hide ONNX Runtime's warnings ("Some nodes were not assigned to the preferred execution providers", "Could not find a CPU kernel and hence can't constant fold"; both harmless: shape ops run on the CPU by design). Left: Chromium's own "The powerPreference option is currently ignored when calling requestAdapter() on Windows" (crbug.com/369219127). ORT 1.31's native WebGPU EP requests the adapter itself with `high-performance` from C++, and only a `GPUDevice` passed in the EP options (`{name: 'webgpu', device}`) skips that, which means requesting the device with ORT's limits and features ourselves; not done.

[DOC: model-worker] Lift and tracking run in **one** module worker (`model-worker.js`) with one ONNX Runtime instance (`onnxruntime-web@1.31.1`, `onnxruntime-web/webgpu`), one WASM heap and one WebGPU device. `models.js` is its client: `ready(group, names, options)` loads a model group once (`'lift'`, `'track'`; consent and download included) and `call(payload, transfer)` sends a request. The worker keeps `groups[name] = {sessions, bufs, gpu}`, serializes every message through one promise chain (two `run()` calls never interleave on one runtime: a lift tap during a preview track waits for the current frame only), and routes by group (`HANDLERS[group][type]`): `lift` → `segment` in `lift-mask.js`, `track` → `seed` / `step` / `reset` in `track-infer.js`, `light` → the same three in `light-infer.js` (Light tracking). `{type: 'drop'}` releases every group and keeps the worker (Gpu teardown).

- Why one worker (2026-10-29): until then lift and tracking each had a worker, so the page held two ONNX Runtime instances (the 28.7 MB `ort-wasm-*.wasm` compiled twice), two WASM heaps that never shrink, two WebGPU devices and the model bytes once more in JS for the fallback. On an iPhone XR (iOS 18, 3 GB) the lift worked and the first tracking reloaded Safari: the WebContent process crossed its memory limit and was killed (Safari reloads such a tab; reasoned from the symptom and the sizes, not measured on the device). One heap reuses the space freed by the other model; its high-water mark is the larger model, not the sum.
- WebGPU first, WASM fallback: a group created on `webgpu` keeps its model bytes (`bufs`) so a failed run can rebuild the sessions on `wasm` and retry once; a group created on `wasm` drops them. On a touch device `ready` passes `keep: false` and the bytes are dropped there too (83 MB of tracking weights would otherwise stay in the worker next to the GPU copy); a WebGPU failure then surfaces as an error instead of a silent rebuild. WASM sessions are created with `enableCpuMemArena: false` and `enableMemPattern: false` (`LEAN`): the arena keeps every intermediate tensor of the largest run alive, the pattern pre-allocates for it. `load` answers `{gpu}` (the backend that was actually created), which `ready` returns to the caller. Session creation is sequential (never `Promise.all`: ORT's WebGPU sessions share one device).

## Gpu teardown

[DOC: gpu-teardown] A model worker that has asked for a WebGPU device is never terminated. `release()`, a group switch on a touch device and a worker error drop every group in place (`{type: 'drop'}`) and keep the worker. Only a worker that never asked for WebGPU (`touched` false in `models.js`: no adapter, the processor chosen after a crash, or VitTrack alone) is still terminated and respawned (one-model).

- Seen (2026-11-01, `miniapp/dev/trace/2026-11-01T17-58-12.log`): a friend's iPhone 17 Pro (Safari 26.4) finished 6 of 6 `/bench` runs, but 5 pages stopped sending `beat` 0.8–8 s after the bench's `terminate` of the model worker, with no `visibility` or `pagehide`, and one was followed at once by Safari's crash reload (friend: "it worked, then started again"). The owner's SE2 run that finished in the same log (`z22po1`) stopped 6 s after its `terminate` too. The iPhone 14 on iOS 18 (no WebGPU, a WASM worker) kept beating 7–150 s after `terminate` and ended with a normal `pagehide`, and so did BlueStacks (no WebGPU). So terminating a worker that holds a live `GPUDevice` kills the WebContent process within seconds, while a WASM-only worker is safe to terminate (reasoned from these traces; no crash log from the 17 Pro).
- Why, from primary sources: ORT 1.31's WebGPU glue (`ort-wasm-simd-threaded.asyncify.mjs`, emdawnwebgpu's `requestDevice`) sets `device.onuncapturederror` on the device it creates. In WebKit that listener keeps the `GPUDevice` alive after its worker is gone (the uncaptured-error callback held a pending activity on the device): WebKit bug 327093, "Crash in InspectorInstrumentation::instrumentingAgents from GPUDevice::contextDestroyed during dedicated worker teardown when the device has an uncapturederror listener", fixed in WebKit `main` by PR #76747 (merged 2026-10-13, 323630@main), so no shipping iOS has it. Its regression test needs a Web Inspector, and whether the path without one is the same is not shown. A second change, PR #78448 (open on 2026-11-01), fixes GPU process crashes "when a worker that uses WebGPU is terminated" with work still pending. Which of them the 17 Pro hit is not known; not terminating avoids both.
- In place: `drop` releases every session. ORT then destroys its device itself (headless Edge trace, 2026-11-01: `device-lost` reason `destroyed` right after the `drop`), and the next `load` in the same worker asks for a new one. Checked in headless Edge with a touch viewport (`miniapp/dev/README.md`, trace-bench): three SAM 2.1 rounds in one tab, one worker, no `terminate`, live GPU buffers 301 → 0 MB after each drop. The WASM heap stays at its high-water mark (160 MB after SAM 2.1 on WebGPU, 111 MB after EdgeSAM): the cost of keeping the worker during the encode.
- `model-worker.js` also turns `GPUDevice.prototype.onuncapturederror` into a no-op accessor before ORT asks for a device (the workaround of the third-party app VolksRat71/sam-ui, PR #65, which met the same WebKit crash on reload), so a page that is closed or reloaded with the worker alive does not leave the device behind either. Cost: ORT no longer hears of uncaptured WebGPU errors (its handler only forwards them to its log); Chromium still prints them in its console. Applied in every browser with no user-agent check, because the handler has no other use.
- `addEventListener('uncapturederror', …)` is not covered by the accessor and crashes the same way in WebKit (sam-ui's table): never add one in the worker, the dev trace included (`miniapp/dev/README.md`, Phone trace).
- Not yet run on an iPhone. Closes when the 17 Pro runs `/bench?rounds=3` and several renders in one tab with `beat` continuing after `released`.

## Wasm threads

[DOC: wasm-threads] `model-worker.js` sets `ort.env.wasm.numThreads` to `min(4, hardwareConcurrency)` when the page is cross-origin isolated (`self.crossOriginIsolated`: COOP `same-origin` + COEP `require-corp`, which give `SharedArrayBuffer`), else 1. GitHub Pages sends neither header, so production stays single-threaded for now; `npm run phone -- --isolate` serves the build with both headers to measure a phone (`miniapp/dev/README.md`, Phone trace).

- Measured (production build, headless Edge, 6-core desktop CPU, `wasm` tracking at 512²): 2.4 s per step with 4 threads against 5.8 s with 1 (seed 2.0 against 4.1 s); the heap is the same 406 MB. Per session, single-threaded: the vision encoder is about 55 % of a step and memory attention about 40 %. A12 / A13 have 2 fast and 4 efficiency cores, so expect less there (not measured).
- ORT's pthread workers are the same script: ORT 1.31 starts them with `new Worker(new URL(import.meta.url), {type: 'module', name: 'em-pthread'})`, and in our build `import.meta.url` is the `model-worker` chunk (ORT is bundled into it). So every thread evaluates `model-worker.js` with its imports, and the `onmessage` we set replaced Emscripten's own pthread handler (the threads answered ORT's internal messages with `Model is not loaded`, seen in the trace). The handler is therefore set only when `self.name` does not start with `em-pthread`. Each thread still evaluates `lift-mask.js` and `track-infer.js` at module scope (about 8 MB of `Float32Array`s in `track-infer.js`), a cost per thread.
- Enabling isolation on GitHub Pages needs a service worker that adds the two headers to our own responses (GitHub Pages cannot set headers). Under `require-corp` every cross-origin subresource needs CORS or a `Cross-Origin-Resource-Policy` header: Hugging Face downloads and our API (CORS fetches) pass; the user picture from Telegram would be blocked, COOP `same-origin` cuts the sign-in popup's opener (the popup falls back to a `BroadcastChannel`, `account/README.md`, Popup login), and `COEP: credentialless` (which relaxes this) is not supported in Safari. The Mini App would need `telegram-web-app.js` with CORS or CORP as well. Not enabled: the sign-in change is the owner's decision.

## Local lift

[DOC: local-lift] Tap-to-lift in the browser version runs SAM 2.1 tiny locally (EdgeSAM on touch devices, Lift model; the rest of this section describes SAM 2.1) (`lift-local.js` on the page, `lift-mask.js` in the model worker, Model worker). It runs on WebGPU or, without it, on WASM (the Mini App on iOS 18 and Safari 18 without the flag use the WASM path; WebGPU by platform). `web-app.jsx` attaches `lift` to `job`, which `useLift` (`viewer/follow.js`) calls for every selection (`local`, `free`, and `pro`; for `pro`, a local failure falls back to `POST /api/jobs/:id/segment` when `source.id` is ready).

- Frame extraction (`frameRgba` in `lift-local.js`): draws the live `.viewer-video` directly onto a 1024 × 1024 2D canvas (waiting for `seeked` with a 250 ms timeout if it is seeking), or decodes the exact frame with Mediabunny's `CanvasSink` from `job.file` otherwise, avoiding fragile detached `<video>` element seeks that can hang indefinitely in desktop browsers.
- Embedding cache: `lift-mask.js` normalises the 1024 × 1024 RGBA buffer (`MEAN = [0.485, 0.456, 0.406]`, `STD = [0.229, 0.224, 0.225]`), runs `vision_encoder_fp16.onnx` (`pixel_values` `[1, 3, 1024, 1024]` → `image_embeddings` `[1, 256, 64, 64]`, `high_res_feats_0` `[1, 32, 256, 256]`, `high_res_feats_1` `[1, 64, 128, 128]`, about 16 MB of float32 per frame) and keeps the outputs of the last `EMBEDDINGS = 4` frames (LRU, keyed `${name}:${size}:${floor(time * 30)}`), so repeated taps or box edits on the same frame skip frame readback and the encoder. It was 8 (128 MB in the worker) until 2026-10-29; 4 still covers re-tapping and stepping between a few frames.
- Cache protocol: the page first asks with the key only; the worker answers `{miss: true}` when the frame is not cached, and only then the page reads the frame and sends its pixels. The page used to mirror the worker's cache in a `Set` and send no pixels for a key it believed cached; the mirror went stale when the worker cleared its cache (WASM fallback), and the worker then ran the encoder on `null`.
- Prompt / mask decoder (`prompt_encoder_mask_decoder_fp16.onnx`): coordinates are scaled to `1024`; a box `[x0, y0, x1, y1]` appends two points with labels `2` and `3`. Output `pred_masks` has shape `[1, 4, 256, 256]`: slot `0` is the single-mask output (`multimask_output=False`, used for 2+ points or a box) and slots `1..3` are the three multimask candidates (`multimask_output=True`, used for a single positive point without a box).
- [DOC: local-lift-mask] Mask cleanup (`lift-mask.js`, after `backend/rounds/segment.py` `clean`, `distinct`, `feather`): the 256 × 256 logits are resized bilinearly to a working size of `min(0.5, MAX_MASK / long side)` of the source (`MAX_MASK = 480`, at least 16 px), thresholded at `> 0`, opened with a 3 × 3 erosion then dilation, reduced to 8-connected components of at least `KEEP_BLOB = 0.2` × the largest, hole-filled (everything not reached by a flood fill from the border), inset by `EDGE = 4` working pixels, deduplicated (`distinct`: by ascending area, a candidate with IoU ≥ `SAME = 0.9` against a kept one is dropped; `best` is the middle one), feathered by a Gaussian (radius 4, σ 1.2) and encoded as a white RGBA PNG (`OffscreenCanvas.convertToBlob`). Reported by the agent that wrote it (not rerun 2026-10-29): 2 pixels differ from Python out of 129 600 (`IoU = 0.9999`).
- Measured on the owner's PC (2026-10-29, GTX 1660 Ti, Turing, Edge 154 headless with WebGPU enabled):
  - Session creation (`InferenceSession.create` for encoder + decoder on `webgpu`): `1.89 s`.
  - Image encoder (`vision_encoder_fp16.onnx`, 1024²): **1.26 s** on the first frame (cold shader compilation), **233–242 ms** on subsequent frames (warm).
  - Prompt / mask decoder (`prompt_encoder_mask_decoder_fp16.onnx`): **2.49–2.65 s** on the first tap (cold shader compilation), **43–77 ms** warm on `webgpu` (both 1-point and 2-point / box prompts); **251–301 ms** on `wasm` fallback.
  - End-to-end `segmentLocal` in Edge (worker + WebGPU inference + mask cleanup + PNG encoding): **184 ms** on a warm 1-point tap (3 candidates), **152 ms** on a warm box prompt (1 candidate).
  - VRAM (`nvidia-smi`): `2577 MiB` baseline → `2610 MiB` after session creation (`+33 MiB`) → `3648 MiB` peak after encoder + decoder inference (**`+1071 MiB`** / `~1.05 GB` delta).
  - **Not verified:** interactive feel in the owner's visible Edge and Firefox windows (WebGPU availability and latency in Firefox on Windows).

## Local tracking

[DOC: local-track] Video object tracking runs SAM 2.1 tiny video locally (`track-local.js` on the page, `track-infer.js` + `track-measure.js` + `tpos.js` in the model worker), mirroring `backend/rounds/track.py` and `media.py`. Model: `diffusionstudio/sam2.1-tiny-video-onnx-fp16` (Apache-2.0, revision `66673b5db39371b7dd7847f4d3bc0d4f4179b79e`, 83.16 MB total across 5 ONNX graphs: `vision_encoder.onnx` 58.39 MB, `mask_decoder.onnx` 8.90 MB, `memory_attention.onnx` 13.03 MB, `memory_encoder.onnx` 2.81 MB, `pointer_tpos.onnx` 34.2 kB), cached via the Cache API `rounds-models-v1`.

- On a slow touch device (Speed gate) none of this section runs: VitTrack tracks instead (Light tracking). What follows is the SAM 2.1 path of fast devices and of every desktop.
- **WebGPU or CPU** (owner decision 2026-10-29: tracking must exist on every device, slower is fine, crashes are not): with WebGPU the worker runs the five graphs on the GPU (about 0.2 s a frame); without it the same graphs run on the WASM CPU backend, single-threaded (the page is not cross-origin isolated). Measured in headless Edge with the GPU disabled (desktop CPU, one thread): about 8 s a frame, so the CPU path tracks less often: the preview takes at most `CPU_STEPS = 12` frames (3, 2 or 1 fps by the range) and the render tracks `CPU_RATE = 2` fps and interpolates to 30 ([DOC: track-cpu-rate]: `merge` takes samples at any times, sorts them, lerps centre, radius and area between the two around each output frame, takes `present` from the nearer sample, holds the first and last sample at the edges, and finds scene cuts in the sample histograms (`window = 3`, `minShot = 1` on the CPU), mapped to frames by their times). The render seeds on the exact prompt frame (`anchorOf`, as the preview does), replacing the nearest planned time; it used to seed on the nearest 2 fps grid time, up to 0.25 s off.
- [DOC: track-reuse] On the CPU the render reuses the preview's samples (owner 2026-10-29, iPhone XR: the render sat at 0 % for minutes after a preview had just tracked the same object). `followLocal` keeps its last complete pass (`preview`: every sample's time and full result, about 2 KB each, keyed by file identity and the prompt's time, points and box; an aborted pass is not kept). "Without WebGPU" means the backend the tracking group really loaded on (`onGpu`, set from `ready`'s answer by `followLocal` and `runTrack`; `deviceOf()` only before any track): until 2026-10-30 it was `deviceOf().gpu`, so a device whose adapter exists but whose tracking sessions were refused (suspected on the owner's XR with the WebGPU flag on; the trace later showed its sessions on WebGPU, Model worker) tracked the preview on the CPU and then the whole range again at 2 fps, and the stage-cache key said `gpu`. `runTrack` on such a device takes the samples inside `[start, end]` and plans only the gaps: a 2 fps grid time is skipped when a preview sample lies within half a step (0.25 s) or when it is outside the preview's span by at most one step (held). A preview at 2 or 3 fps (ranges up to 6 s) leaves nothing to track and the render starts encoding at once, without even loading the model; at 1 fps (longer ranges) the render tracks the half-second points between, as a second chain seeded on the same frame. Trade-off: two interleaved chains, each with 1 s between frames, instead of one 2 fps chain; the camera path smooths the difference. Not on WebGPU: the render there tracks every frame in one chain, and the 1–3 fps preview samples (at most 10 % of the frames) come from a chain with long gaps, so mixing them in would lower the track's quality to save at most a tenth of the time. Measured memory of the CPU path (Windows working set of the renderer process, Edge, tracking alone with the coarse pointer emulated): about 160 MB before, 1.2–1.4 GB peak while the sessions run the first frame, about 0.9 GB steady (lift alone peaks near 0.7 GB). The memory input of the attention graph is a fixed 7232 tokens (a shorter bank fails with `Got invalid dimensions`), and `graphOptimizationLevel`, `disable_prepacking` and the arena options changed the numbers by under 5 %. So an iPhone with 3 GB may still lose the tab on the first CPU run: the Track guard then offers the processor once (after a WASM crash it can only give tips). The server prompt also passes the lifted mask (`track.py`, `_mask`); the local tracker uses only the points and the box (the ONNX decoder has no mask input).
- Normalization and geometry (`track-infer.js`): 512 × 512 ImageNet mean and std in planar CHW (`toChw`), transposition of 256-dim feature planes to tokens `[1024, 1, 256]`, and temporal positional encodings (`tpos.js`, 7 rows of 64 floats, [DOC: local-track-tpos]: the `pointer_tpos.onnx` export's constant table, one row per memory slot).
- [DOC: track-buffers] The per-frame inputs (CHW pixels 3 MB, feature tokens 1 MB, the memory bank and its positions 1.85 MB each) are module-level buffers reused every frame: a run copies its inputs into WASM or uploads them before it resolves, and the worker serializes requests, so reuse is safe. The image encoder's `vision_pos_embed` is a sine position encoding of the fixed 64 × 64 grid, the same for every frame, so its token transpose is computed once (`pos`). Before, each frame allocated about 10 MB of garbage.
- Rejected warm-up (2026-11-01): running `pointer_tpos` and `memory_attention` once on zeroed inputs at the start of a WebGPU seed, so their first run lands where the most memory is free (80 MB of tracking buffers live then, 300 MB at step 1). The SE2 ran it and still died on step 1 in 3 of 3 fresh tabs (Model worker, gpu-buffer-cache, ninth round), so it was removed. Do not bring it back as a fix for the step-1 crash.
- The memory bank keeps the last `RECENT = 15` frames (`state.recent`): 6 feed the memory attention, 15 feed the object pointers.
- [DOC: local-welzl] Welzl's minimum enclosing circle (`minEnclosingCircle`, iterative, $O(N)$ expected time) runs on boundary points after 8-connected component filtering (`KEEP_BLOB = 0.2`, `MIN_AREA = 1e-4`), matching OpenCV `connectedComponentsWithStats` and `minEnclosingCircle`. It was recursive until 2026-10-29, with a depth of up to 3 × the boundary point count (thousands for a large object), which risks a stack overflow in a worker. Collinear triples fall back to the widest pair circle. Checked in Node: equal to a brute-force search on 300 random sets (max radius difference 1e-14), same result as the recursive version on a 200 px disc.
- Color histogram (`histogram`): 512-bin 3D RGB histogram (`(r >> 5) << 6 | (g >> 5) << 3 | (b >> 5)` downsampled every 4 px). `changes(hists)` computes Manhattan step distances and `sceneCuts(d)` detects cuts (`window = 15, floor = 0.3, ratio = 3.0, min_shot = 6`), matching `backend/rounds/media.py` `scene_cuts`.
- [DOC: track-frames] Frames are decoded as a stream (`frames`, Mediabunny `CanvasSink` at 512 × 512, `fit: 'fill'`, `poolSize: 1`; VitTrack through Light pump): forward from the prompt frame to the end, then backwards in chunks of `CHUNK = 30` (each chunk decoded in time order, then fed in reverse), each RGBA buffer transferred to the worker and dropped. Until 2026-10-29 every frame of the range was decoded into memory first: 1 MB per frame, 1.8 GB for a 60 s render at 30 fps. A frame the sink returns as `null` (before the first timestamp) is black.
- [DOC: local-follow] Preview tracking (`followLocal`): the grid is 3, 2 or 1 fps, the first rate that keeps the range within 45 steps (`RATES`, `STEPS`), anchored on the prompt frame; it returns `{fps, start, boxes}`. The request takes its `active` number before it parks the editor video (`hooks/README.md`, Player park; `trackLocal` parks only when it really tracks, not on a stage-cache hit), so a Stop during the park still stops it. Each request bumps `active`, and an older preview stops at its next frame and returns `null` (the viewer's single flight asks again). `stopFollow()` bumps it too: Stop in the viewer (`viewer/README.md`, Follow confirm) ends a running preview at its next frame; a render's `trackLocal` ignores it (its loop never checks `active`).
- Render tracking (`trackLocal`): every frame at 30 fps like the server (`config.FPS`), forward and reverse, `{present, cx, cy, r, area}` scaled to `meta.width` × `meta.height` (the radius by the larger scale), and `cuts`. It bumps `active` too, so a preview still running when the user presses Make round stops.
- [DOC: track-serial] Runs are serialized (`exclusive`): the worker holds one tracking state, and a preview and a render interleaving their `seed` / `step` messages corrupted each other's memory bank. Checked in headless Edge: a preview started together with a render returns `null` and the render's note is correct.
- Measured in headless Edge on GTX 1660 Ti (2026-10-29, after the changes above): lift 0.1–0.5 s warm, preview of 3 s (10 frames) 5.8–6.2 s including the first session creation, render of a 4 s range with tracking (120 frames, VP9) 24–30 s. Earlier numbers of the previous implementation:
  - Warm inference: **185–201 ms** per frame (~5.2 fps) on WebGPU.
  - Tracking accuracy: normalized center distance vs PyTorch **0.002** (1.05 px on 512²), occlusion detection at score $-3.39$, recovery on reappearance at score $+0.10$.
  - End-to-end `followLocal` (16 frames at 10 fps on 960 × 540 proxy): **14.41 s** cold (including shader compilation for all 5 graphs).
  - End-to-end `renderNote` with dynamic tracking: **10.38 s** for a 1.5 s clip (45 frames at 30 fps), generating a valid 640 × 640 AV1 MP4 (`339 kB`).

## Speed gate

[DOC: speed-gate] On a touch device the tracker is chosen by the measured speed of the device, not by its model (owner, 2026-11-01). Safari tells nothing about the device: every iPhone reports `architecture: 'apple'` and the frozen UA `iPhone OS 18_7`, the limits follow the iOS version (gpu-buffer-cache), and there is no memory signal. The free measurement is the lift that precedes every selection. `segmentLocal` times the call that runs the encoder (frame pixels sent; the page-side round trip, the same thing `/bench` logs as `lift`) and, when the lift group runs on WebGPU, passes it to `notePace` in `models.js`. `fast()` is true on any non-touch device, and on a touch device whose fastest such lift is at most `FAST_LIFT` = 800 ms. A tap answered from the embedding cache (no encoder) does not count. A lift on WASM never counts, so a touch device without WebGPU is always slow.

- Data (bench `lift`, EdgeSAM on WebGPU; logs `2026-11-01T17-58-12.log`, `-17-32-49.log`, `-17-04-58.log`): iPhone 17 Pro 297–423 ms; SE2 1648–3907 ms (mostly 1.7–2.5 s); XR (iOS 18.5, flag on) 13 890 ms. The iPhone 14 on iOS 18 lifts on WASM in about 1.9 s and does not count. 800 ms sits about 2× from both measured classes. Tracking steps are in the same order (17 Pro 0.23–0.37 s, SE2 1.8–2.5 s, XR 18–20 s, iPhone 14 WASM 3.6–4.4 s). The A14–A16 phones (iPhone 12–15) are not measured: the threshold is a guess between two points, to be set from their bench lines.
- Routing: fast → SAM 2.1 on the device (Local tracking). Slow → on `pro` the render goes to the server (`needsServer` in `plan.js` is true for a selection when `job.fast === false`, and `needsModal` sends a selection to Modal), and the editor's preview follow goes to `POST /api/jobs/:id/track` when the job already has a server id (`web-app.jsx`; only a file the device could not read has one, `features/web/README.md`, No background upload), else the preview runs locally with VitTrack. On `local` and `free` a slow device tracks with VitTrack (Light tracking): Oracle has no tracker yet (`BUGS.md`, Tracking on the free tier).
- Traps: Chromium compiles WebGPU shaders on first use, so the first lift in a fresh profile is slow (GTX 1660 Ti, EdgeSAM: 2.1 s cold, 0.4–0.5 s warm), and an Android phone may be classed slow on its first selection. The minimum over the page's lifts corrects it on the next tap on a new frame. On iOS no trace showed a slower first lift. No lift (failed, or the bench's `lift=0`) leaves the gate slow. The measure lives only in memory (`pace`), so a reload measures again. The stage cache key of `trackLocal` includes the choice, so a track by the other tracker is not reused.

## Light tracking

[DOC: light-track] On a slow touch device (Speed gate) tracking runs VitTrack, the transformer tracker of the OpenCV Zoo (GSoC 2023, derived from OSTrack): one 715 kB ONNX graph, `template` `[1, 3, 128, 128]` and `search` `[1, 3, 256, 256]` in, `output1` (score map `[1, 1, 16, 16]`), `output2` (size map `[1, 2, 16, 16]`) and `output3` (offset map, same shape) out. It gives a box, not a mask: enough for the crop and the zoom (centre, radius, area); the selection outline still comes from the lift.

- Licence: Apache 2.0 (the folder's `README.md` and `LICENSE` in the Hugging Face repo `opencv/opencv_zoo`), derived from OSTrack (MIT, Botao Ye 2022). Weights: `models/object_tracking_vittrack/object_tracking_vittrack_2023sep.onnx` at revision `39a1451d0f9b23fc4ebaed06a277127efa0374d0`, `714 726` B, SHA-256 `2990f0b7cd44d92afa48cd97db6de7be113fc1d9594fddb74e2725c10478e91d` (downloaded and hashed 2026-11-01; equal to the Hub's LFS hash). Owner's go-ahead: 2026-11-01, "implement the table" (light tracker for slow devices).
- `light-infer.js` (in the model worker; group `light`) ports `cv::TrackerVit` (`modules/video/src/tracking/tracker_vit.cpp`, OpenCV branch `4.x`): a square crop of side `ceil(sqrt(w·h) · factor)` around the box (factor 2 for the template at the seed, 4 for the search at each step), black outside the frame, a bilinear resize with OpenCV's pixel-centre mapping rounded to 8 bits, planes in OpenCV's order (B, G, R: OpenCV feeds its BGR frames without a swap) normalised per channel with the ImageNet mean and std (index 0, 0.485 / 0.229, on the B plane), the score map times a 16 × 16 Hann window (`0.5 (1 − cos(2π (i + 1) / 17))`), the best cell's offset and size decoded into a box, and the box clipped to the frame with a 10 px margin. Below a score of 0.2 the frame is "not present" and the search stays at the last box. No template update, no motion model. Two deliberate departures from OpenCV come after the decode: the lost state with relock, and the size limit (Light relock).
- Normalisation trap (measured 2026-11-01): the released OpenCV 4.14 and 5.0 compute the per-channel scale as `(1 / std) / 255` on a `Scalar`, which is the quaternion inverse, so the G and R planes are negated and every plane is scaled by std / |std|². A Python re-implementation with that scale reproduces the released tracker's scores to 4 digits; with the per-channel scale it does not. The `4.x` branch head fixes it (`getScaleFactor`, "Note: (1.0 / Scalar) is the quaternion inverse"). On the 32 s test clip (`miniapp/dev/media/proxy.mp4`, a ball over colour bars, 959 frames at 640 × 360) the released scale lost the ball (centre error p95 467 px) and the fixed one held it (median 1.4 px, p95 3.8, max 12.6); RGB planes with the fixed scale did as well (1.8 / 4.0 / 7.0). The port follows the fixed branch. `cv.TrackerVit` from `opencv-python-headless` gives different and worse results until a release carries the fix: check the version before comparing. The server's tracker is therefore not `cv.TrackerVit` but a Python port of this file, `backend/rounds/vittrack.py` (`backend/rounds/README.md`, Vit track), with exact parity: a change here is made there too.
- Parity: against the fixed algorithm built from OpenCV's own `copyMakeBorder`, `resize` and `blobFromImageWithParams` with `cv.dnn` (opencv-python-headless 4.14; scratch scripts, not kept), the port run in Node with ORT Web WASM gave the same boxes within 2 px over 119 frames, and equal scores except on one frame (gap 0.04).
- Page side (`track-local.js`): `modeOf(meta)` picks SAM 2.1 or VitTrack per call. VitTrack frames keep the source's aspect ratio with a long side of 640 (`LIGHT.long`; SAM 2.1 gets the stretched 512² frame). The render samples 15 fps (`LIGHT.rate`) and `merge` interpolates to 30 with the dense scene-cut settings; the preview samples 10 fps (`LIGHT.preview`) whatever the range. The group loads on WASM (`cpu: true`) and adds a few MB; whether it unloads the lift is Light memory. Results come in SAM 2.1's units (centre and radius in the 512² space, area in its pixels), so `merge` and the camera path take them as they are. The radius is half the box's diagonal, larger than SAM 2.1's enclosing circle for a non-rectangular object.
- Seed box: the bounding box of the lifted mask (alpha ≥ 128 of the PNG, decoded in the worker with `createImageBitmap` and an `OffscreenCanvas`), else the drawn box, else a square of 15 % of the short side around the tapped points (`TAP`).
- Measured (2026-11-01): Node, one thread, 20 ms per step (crop, net, histogram); headless Edge (`/bench`, one thread: the page is not cross-origin isolated) 20–23 ms per step, `err` 0–1 px. The app's `trackLocal` on the 32 s clip (headless Edge, touch viewport, 480 samples) took 14 s, centre error against the ball median 2.8 px at 960 × 540, p95 7.9, max 33, no time lag. The whole web flow (upload, tap, follow, Make round) finished a 32 s AV1 round 27 s after the preview. In that round the ball was off centre by a median of a quarter of the circle: the camera path keeps the object inside the safe circle and moves smoothly; it does not centre it (Camera path). First phone runs (2026-11-01, app, a 4K HEVC vertical source): SE2 about 120 ms per preview step, XR (iOS 18.5) about 220 ms; with the 480 × 270 test video the XR took 35–40 ms, so on a 4K source the step is bound by decoding and drawing the frame, not by the net.

## Light relock

[DOC: light-relock] OpenCV's tracker accepts any frame scoring 0.2 or more, so once the object is gone it hops onto whatever scores 0.2–0.5. On the SE2 (`IMG_0430`: a swan, a pan over a bridge, a statue, then a second swan) the preview dot jumped onto railings, roofs and empty water, and the box grew from r 46 to 251 (in the 512 space) while it searched, which widened the search crop and made more junk match. `step` now keeps a lost state:

- Tracking: a score under 0.2 makes the frame absent and the tracker lost. Otherwise the centre moves to the decoded one and the size follows the decoded size at half rate (`SIZE_RATE`), at most ±10 % per step (`SIZE_STEP`).
- Lost: every candidate scoring 0.2 or more moves the search there (wander) at the frozen size and the frame stays absent. The object counts as found again after `HITS` = 3 consecutive candidates, each within one box diagonal of the previous, scoring at least `RELOCK` = 0.55 × the median score of the first 5 tracked steps (`REF_STEPS`), and never under 0.3 (`RELOCK_MIN`). The reference is relative because a dark or small object scores 0.4–0.6 from the start (XR log) where a white swan scores 0.9.
- Why each part (offline, `IMG_0430`'s video area with the app's two white dots painted over, 166 frames at 15 fps, 360 × 616, the real `light-infer.js` in Node): OpenCV behaviour, 12 jumps over 40 px and garbage boxes through the whole pan; this, 2 jumps, absent through the pan, found the second swan at frame 103 (about 1 s after it came into view). Without wandering (search frozen at the last box) the second swan was never found (22 frames present of 166). With 2 hits at 0.5 the tracker locked onto a white statue for 7 frames (score 0.52); 3 hits held at 0.5, 0.55 and 0.6 alike. The ball clip (`dev/media/proxy.mp4`, 480 frames at 15 fps, 640 × 360) stayed as good: median 1.7 px (was 1.8), p95 4.0 (3.9), max 11.7 (20.2), radius range 38–48 (38–55).
- On the relock frame `step` reports the box after `relock` moved it. Until 2026-11-06 it read `state.rect` as the first argument of `found(...)` before `relock(...)` ran as the last one (JS evaluates arguments left to right), so the first present frame after a loss showed the previous wander position (3–23 px off on the occlusion test). Found by the parity run of the Python port (`backend/rounds/README.md`, Vit track); keep `relock` called before the box is read.
- An absent frame is what the camera path wants (it bridges gaps itself; Camera path), and the preview holds the dot at the last box (`viewer/README.md`, Follow hold).
- Tuned on one real clip and one synthetic one: the thresholds are a first guess for phone footage, to revisit with more owner clips.

## Light frames

[DOC: light-frames] VitTrack frames come from `lightFrames` in `light-frames.js` (called by `frames` in `track-local.js`): each decoded sample gets one `drawWithFit(ctx, {fit: 'fill'})` onto a canvas of the target size (`imageSmoothingQuality = 'high'`), is closed at once, and the page keeps only its `getImageData` copy (Light pump). ## Light pump

[DOC: light-pump] `oneByOne` in `light-frames.js` replaces `VideoSampleSink.samplesAtTimestamps` for VitTrack so that at most one decoded frame is alive (owner, 2026-11-01: "on weak devices it is a necessity"). Why: Mediabunny 1.63 (`mediaSamplesAtTimestamps`, `media-sink.js`) keeps decoding until its queue plus the decoder's queue reach `MAX_QUEUE_SIZE` 4, holds one more sample to know it is the last before a timestamp, and hands one out: 4–6 frames of 12.4 MB each on a 4K source (NV12), in WebKit's GPU process, which Jetsam killed at about 300 MB on the XR and the SE2 (`BUGS.md`, iPhone reload on tracking).

- It drives Mediabunny's own decoder wrapper (`sink._createDecoder(onSample, onError)`, `sink._createPacketSink()`), so the custom HEVC WASM decoder (Local HEVC fallback), Safari's B-frame reordering (`sampleHandler`), the HEVC RASL skip and the Chromium AVC fixes all still apply. These are `@internal` methods: `lightFrames` checks that `_createDecoder` exists and falls back to `samplesAtTimestamps` otherwise. Check this file when Mediabunny is upgraded (`^1.63.0` in `package.json`).
- The batching copies Mediabunny's: for each time the target packet (`getPacket`) and its key packet (`getKeyPacket`, else the first key packet if it is earlier); a new batch (flush, then decode from the key) when the key lies past what was decoded or the time goes back; otherwise decoding continues up to the target's sequence number. The answer to a time is the last sample at or before it, known when the next sample arrives or on the flush.
- The difference: a sample is drawn and closed inside `onSample`; the held answer is the small RGBA copy, not the frame. Samples before the pending target's packet time (minus 1 ms, `SLACK`) are closed without a draw (the pre-roll from the key frame). Feeding stops while one answer waits for the page (`AHEAD` 1) or two packets wait in the decoder (`QUEUE` 2); the page takes the answer and nudges the pump before it yields, so the next frame decodes while VitTrack runs.
- Safari's wrapper still holds frames until a later timestamp arrives (its own `sampleQueue`), so one or two frames may sit there with B-frames; the decoder's reference frames are its own and not counted.
- Wakeups: the page and the pump sleep on one shared signal (`wait` / `nudge`), and every change either side waits for must nudge it: an answer pushed to `out` (inside `answer`, so the flush's `answer(Infinity)` nudges too), a sample, a dequeue, the page taking an answer, an error, the end. A push without a nudge is a deadlock with no error: the page waits for `out`, the pump waits in `room` for the page. That is what hung the first phone runs (2026-11-01, `miniapp/dev/trace/2026-11-01T17-58-12.log`: XR session `jl48xt` after 191 of 261 steps, SE2 `3rukam` after 556 steps of a 4K source; the worker answered the last `step`, no next `step` and no `reset` followed, beats went on for 80–90 s, no error). It needs a batch flush (a GOP boundary) whose last answer comes only from `answer(Infinity)`, finishing while the page already waits: a flush slower than a VitTrack step. So it hit at random points, and the XR went through the same clip on the next try. Reproduced off the phone with a model of the wrapper (one frame held until the next, a 40 ms flush, a 10 ms step: hung after 14 of 285 frames; a 5 ms flush or a 60 ms step passed); after the fix the same model ran every case (GOP 1, 2, 15, 30; flush 0–120 ms; step 0–60 ms) to the end with every answer right (scratch script, not kept).
- Measured (2026-11-01, headless Edge, the 12 s ball clip upscaled to 3840 × 2160, `trackLocal` on VitTrack, `VideoDecoder` wrapped to count frames not yet closed; scratch scripts, not kept): at most 1 frame alive against 7 with `samplesAtTimestamps`, the same boxes (median error 11.2 px on the 3840 grid, best at zero lag), 14.7 s against 15.3 s. With the prompt at 4 s (backward chunks): frame 0 within 2 px, 420 frames decoded, at most 1 alive.

## Camera path

[DOC: camera-path] Camera path computation (`camera.js` + `camera-lp.js`, with `gaussianFilter1d`, `CubicSpline`, `sampler`, `interp` and `roundEven` in `spline.js` since 2026-10-30 for the 200-line limit) ports `backend/rounds/camera.py` (`solve`, `_shot`, `_lp`, `_hold`, `_clean`, `_fallback`, `sampler`), including the stabilization branch (`world`, Local stabilization). - [DOC: camera-lp] The path itself is the server's L1 linear program (Grundmann-style: L1 norms of velocity, acceleration and jerk per axis with `WEIGHTS = (10, 1, 100)`, zoom ×8, data and framing terms, pan / acceleration / zoom speed caps relative to the zoom, the frame bounds, and the 8-sided "object inside the safe circle" constraints with exit slacks), sampled every `STEP = 2` frames, solved by HiGHS (`highs@1.15.3`, MIT, WASM: 3.5 MB raw / 1.2 MB gzip plus 107 kB JS in the `camera-*.js` chunk, fetched only by a render with tracking) through its structured API (`withModel`, `passModel` with a CSR matrix: the LP text format would be megabytes of text). Duplicate entries in one row (the zoom cap row names `z[j]` twice) are summed before `passModel`, like SciPy's sparse sums. ## Local motion flow

[DOC: local-motion-flow] `flows(track, meta, start, end, onProgress)` (`motion.js`) decodes every sample of the range in order with `VideoSampleSink.samples(start, end)` (not the tracker's frames: those are 512² `fill`-squeezed, on the 30 fps grid, partly backwards, and 2 fps on the CPU), draws each whole frame (`drawWithFit` `fill`, no source rectangle: WebKit bug, Local crop draw) to an `OffscreenCanvas` of short side `BUDGET.side` (480, the server's `SIDE`), takes BT.709 luma, and sends it to `BUDGET.workers` module Workers (`motion-worker.js`). Frames go out in chunks of 30 per Worker, round robin; the first frame of a chunk is also sent to the previous Worker so that it closes its last pair, and the new Worker starts with `first` (no pair). Pairs are independent, so this uses several cores without WASM threads. At most `BUDGET.queue` frames wait per Worker (back pressure: a 4K hardware decode outruns the LK). Output `{t (seconds from start), pairs (per frame, [px, py, qx, qy] in source px, edge coordinates: `fround(v + 0.5) × scale`), disc}`, as `motion.flows`.

- `motion-flow.js` is a scalar port of OpenCV 5.0 (`goodFeaturesToTrack` 600 / 0.01 / 8 with `cornerMinEigenVal` block 3 Sobel 3 `REFLECT_101`, 3×3 NMS on the interior, ties broken by the larger offset first as `greaterThanPtr`, the min-distance grid; `calcOpticalFlowPyrLK` 21×21, 3 levels, 30 iterations / 0.01, `minEigThreshold` 1e-4, `pyrDown` with integer rounding, images padded by 21 with `REFLECT_101`, Scharr derivatives in int16 padded with zeros, 14-bit fixed-point bilinear weights with `CV_DESCALE`, the half-step oscillation exit), then the forward-backward check (< 1 px). Read from memory of `lkpyramid.cpp` / `featureselect.cpp` and confirmed by Test C. Known difference: OpenCV accumulates the window sums (A11, A12, A22, b1, b2) in float32 SIMD lanes; the port accumulates in float64, so some points move by up to a few thousandths of a pixel.
- Baked disc: `flat` on the first grey frame, the corner mask `ring(0, DISC_IN)`, `disc` confirmed on the last frame, as `motion.flows`.
- Grey: ffmpeg's `gray` from the server's decode came out as `1.055 × luma709 − 2` on one test clip and `0.992 × luma709 + 0.5` on another (fit on the first frame, observed). The browser computes luma709 from the browser's RGB: approximate; LK and the relative corner threshold barely depend on the gain.
- **Test C** (2026-10-30, Node, the exact grey frames the Python reference decoded, written to disk and fed to both): a synthetic shaky 1080p clip (mandelbrot still with 7 / 5 / 4.3 Hz shake, 3 Hz roll, a moving overlay, a cut) and a 384² baked-disc round, 150 frames each. ## Local motion fit

[DOC: local-motion-fit] `similarity(m)` ports `cv2.estimateAffinePartial2D` with the server's RANSAC (1.5 px, 2000, 0.995): `cv::RNG` with state `2^64 − 1` (multiply-with-carry, coefficient 4164903690, BigInt), two distinct indices per draw, OpenCV's closed form of the 2-point model, inlier test in float32 (`Math.fround` per operation, `err ≤ fround(1.5²)`), `RANSACUpdateNumIters` with `DBL_MIN` and `cvRound`. The 10 Levenberg–Marquardt refinement steps are replaced by the exact linear least squares on the inliers (the similarity is linear in `a, b, tx, ty`, so LM converges to it). `params` ports `motion.params` (subject exclusion 1.2 r at `roundEven(t × 30)`, < 24 points or < 24 inliers → identity, a pair across a cut → identity, accumulation by the inverse step).

## Local motion world

[DOC: local-motion-world] `world(flow, p, strength, size, n)` and `placer(at, world)` port `motion.world` / `motion.placer`: the slow part of position, roll and scale (Gaussian σ = 0.5 s in samples, `mode='nearest'`) stays, removed about the smoothed centre; quad or 16-sided disc edge rows per motion frame; `track` = the parameters interpolated (`interp`, numpy's formula order) to the n tracking frames at 30 fps. `placer` takes the nearest motion frame (not an interpolation) and returns `[cx, cy, side, angle]` in source px; the angle is the rotation the warp (step 5) must apply.

## Motion budget

## Local gl

[DOC: local-gl] `gl.js` is the small WebGL2 layer of `warp.js` and `fill.js` (not of the viewer's `look-gl.js`, which ships in the Mini App and stays untouched): a full-screen-triangle vertex shader, `texelFetch`-only fragment shaders (no hardware filtering anywhere: its sub-texel precision is too coarse for parity), `texStorage` textures with `NEAREST` and a byte counter (`bytes()`), framebuffers cached per texture, layer and attachment count (MRT for the fill), `pass(program, out, size, inputs, uniforms, {layer, scissor})`, `upload` (a `TexImageSource` or `{data}` as RGBA8 / RGBA32F / R32F) and `read` (float readback, tests only). It needs `EXT_color_buffer_float` (or `EXT_color_buffer_half_float` for RGBA16F); `canStabilize()` is the cheap probe of exactly that (a 1×1 context, lost right after). Every allocation checks the size against `MAX_TEXTURE_SIZE` and `getError()` after `texStorage`, and throws a readable error ("too large for the graphics card", "ran out of memory for stabilization") instead of rendering into a missing texture. The context has `preserveDrawingBuffer: true`, because the presented frame is wrapped into a `VideoSample` after the draw. Texel row 0 is the top image row everywhere; only `present` flips, for the canvas.

## Local warp

[DOC: local-warp] `createWarp(canvas, {size, half})` ports `render.crop` / `render.turned` (`backend/rounds/README.md`, Stabilization warp; change both together). `weights(c, side, n, size)` is `render.weights` (Lanczos-3, support × `max(side / size, 1)`, rows normalised, the start index per output stored in column 0 of an R32F texture, clamped indices = edge replicate). Angle 0: the separable path at `size` (vertical, then horizontal, as `wy @ lin @ wx.T`), sRGB 8-bit → linear by `max(v, 0)^2.4` in the first pass, `clamp(0, 1)` at the end (`to_sdr`). Otherwise: the box of `m = ceil(1280 (|cos| + |sin|)) + 8` at 2×, PyTorch's bicubic `grid_sample` (Keys −0.75, each tap clamped = `padding_mode='border'`, `align_corners=False`, the grid computed as `torch` does) to 1280², then Lanczos 2:1 down on `max(x, 0)` and `max(·, 0)` at the end. Output: linear RGBA at `size`. `present` writes gamma (`^(1/2.4)`, flipped) to the canvas; `load` reads a gamma 8-bit image back to linear.

- **Test D** (2026-10-30, headless Edge, ANGLE D3D11 on the GTX 1660 Ti, against `render.crop` / `render.turned` with `render.window` replaced by the same Lanczos on 8-bit RGB, so only the YUV conversion is left out; 1080p and 384² inputs, angles 0, ±0.5–10°, a window half outside the frame): RGBA32F max |Δ| 3.6e-7 (separable) and 4.3e-5 linear (rotated), ≤ 0.027 of a level in gamma; RGBA16F (the default) max 2.7e-3 linear, ≤ 0.32 of a level in gamma, PSNR 63–71 dB.
- The server applies the look on the 2× box before the rotation; the browser applies it on the 640² output before the fill (`stabilize.js`), approximate.

## Local fill

[DOC: local-fill] `createFill(g, {size, n, world, base, times | rate, start})` ports `fill.frames` (`backend/rounds/README.md`, Edge fill; change both together). Per output frame: the window `base(t × 30)` and the inverse similarity of the nearest motion frame go into an RGBA32F table (`params`: frame k at column `k % pw`, rows `3 · floor(k / pw) + 0..2`, `pw = min(n, MAX_TEXTURE_SIZE)`, so 60 s at 240 fps still fits; `columns` overrides `pw` for tests, Test E passed with 50), so every mask is analytic in the shader (`good`: the output pixel mapped through the world into the source, outside `[RIM, w − RIM]` or beyond `DISC_SAFE` R is missing); the donor test `COVER` is the bilinear sum of those analytic validities, as `grid_sample` of the donor's mask. Passes: `MASK`, the 17-tap box twice (`count_include_pad=False`) times the mask = `alpha`, `FILL` (donors nearest first, ties to the earlier frame, then the canvas; MRT: `x, w` for the pyramid and `acc, cover`), the push-pull (`POOL` 2×2 over the in-bounds texels = `avg_pool2d(ceil_mode)`, `BASE` sum / max(Σw, 1e-6) at the first level ≤ 2, `UP` with PyTorch's bilinear `align_corners=False` coordinates), the combine in the last `UP`, then `WRITE` into the world canvas (RGBA16F like the server's fp16; scissored to the window, `discard` where the frame's own pixel is not valid, which equals `ok·rgb + (1 − ok)·old` for a binary `ok`). A frame whose 4 corner pixels are valid has no hole (the valid set is convex) and passes untouched, as `bad.any()` on the server. The ring is a 2D array texture of `2 · reach + 1` layers; `push(tex, onFrame)` copies into it and emits frame `k − reach` once frame `k` is in; `flush` emits the rest.

- Differences: the server stops the donor loop when `cover + keep ≥ COVER` everywhere, the shader per pixel when its own cover is 1, so a pixel with `keep ∈ [0.999, 1)` could take one donor more (weight ≤ 0.001, reasoned). VFR: `times` replaces `k / rate` (the motion samples are the render samples).
- **Test E** (2026-10-30, headless Edge, against `fill.frames` on 60 synthetic 192² frames at 30 fps, `reach` 15, with the Test C worlds: 1080p with the full-height still window, the same with the solved stabiliser path, the 384² baked disc; the Python spy confirmed donors and the canvas were used): the same frames painted as Python (59 / 28 / 60); RGBA32F ring max |Δ| 3.3e-6 / 1.3e-6 / 5.0e-4 (the disc's error is the fp16 canvas on both sides), RGBA16F ring max 1.1e-3 / 1.1e-3 / 3.4e-3, no channel off by more than 0.01.

## Local HEVC fallback

[DOC: local-hevc-decoder] A CPU WASM fallback for HEVC (H.265) video decoding via `@yume-chan/libde265@1.0.0` (LGPL-3.0-only, SIMD-accelerated C build of `libde265` in WebAssembly, 360.84 kB raw / 124.15 kB gzip, emitted as a separate lazy chunk `libde265-*.wasm`). It hooks into Mediabunny's decoding pipeline via `registerDecoder(HevcWasmDecoder)`.

- [DOC: local-hevc-check] Native priority: Mediabunny's custom decoder registry checks `CustomVideoDecoder.supports(codec, config)` before native `VideoDecoder`. To ensure native hardware decoding is preserved whenever the browser supports HEVC (Edge/macOS/iOS), `ensureHevc(track)` probes `VideoDecoder.isConfigSupported(config)` before `track.canDecode()`:
  - When native `VideoDecoder` returns `supported: true`, `HevcWasmDecoder.supports` returns `false`, so Mediabunny passes packets directly to native `VideoDecoder`.
  - When native `VideoDecoder` returns `false`, throws, or is absent (Firefox on Windows, or Chrome without system HEVC extensions), `HevcWasmDecoder.supports` returns `true`, and Mediabunny instantiates `HevcWasmDecoder`.
- Stream handling: parses MP4 `hvcC` (`HEVCDecoderConfigurationRecord`, byte 21 length size + byte 22 arrays) and feeds VPS, SPS, and PPS parameter sets to `decoder.pushNal()`; packet payloads are sliced by NAL length prefix and decoded frame by frame (`decoder.pushEndOfFrame()`). Unconfigured streams (e.g. Matroska Annex B) fall back to continuous `decoder.pushData()`.
- Output: decoded Y, U, V planes (`image.getImagePlane(0..2)`) are packed into an I420 planar buffer and emitted as Mediabunny `VideoSample` instances backed by `new VideoFrame(buf, {format: 'I420', ...})` (or planar `VideoSample` buffer fallback), maintaining presentation order and timestamps.
- Measured in Node and Edge (2026-10-29): 10 frames of 320 × 240 HEVC MP4 decoded in under 20 ms with 0 dropped frames; native `isConfigSupported` on Edge Windows returns `true` (native decoder used), while in headless/non-HEVC environments `track.canDecode()` succeeds via `HevcWasmDecoder`.
