# editor

The editing screen: composes `viewer`, `timeline` and the options, owns the draft and the submit. `app.jsx` renders it for every state (with `job` null while loading) so the loading, ingesting and error screens are the same layout as the ready one (layout stability). Files: `editor.jsx` (the screen, the form and the submit bar), `draft.js` (the option and codec lists, the draft's `init`, `isValid`, `optionsFor`; read by both components, and kept out of the `.jsx` files because oxlint's `only-export-components` warns on a component file that also exports functions), `options.jsx` / `options.css` (the switch rows, the level sliders and the codec picker), `editor.css`.

## Editor draft

One `useReducer(merge)` holds what the owner picks: `start`, `end`, `time` (the frame of the selection, `prompt.time`), `points` (`[x, y, label]`, label 1 = this; 0 = not this exists in the API but the UI no longer places it, `viewer/README.md`), `box` (`[x0, y0, x1, y1]`), `mask` (the lifted outline the tracker follows, a PNG data URL, null without one, `viewer/README.md`, Lift), `crop` (the box is only a crop, sent with a box only, `viewer/README.md`, Crop mode), `options`, `codec` (Codec picker), `look`, `exposure`, `stabilize`, `deblur`, `denoise` (Level rows), `posting`, `error`. It starts empty (`job` is null on the first render) and is filled once, from `job.request` (the previous submission) or from defaults (`0 … min(duration, max_duration)`), by a layout effect on `[job]` that also seeks to the selection frame. `useJob` never refetches a settled job, so `job` changes identity once (null → job) and the draft is never reset by the network. The editor is deliberately **not** keyed by job id any more (it was until 2026-10-26): a remount recreated every element, so nothing could animate from the loading state into the loaded one (the switches snapped on, the trim frame popped in), and the MainButton cleanup `hide()` of the old instance plus `show` of the new one made Telegram iOS slide the button out and back in (recording `IMG_0406.MP4`, 4.0 s). The layout effect runs before paint, so the one render with the job and the empty draft is never shown. Children get `dispatch` and patch the fields they own; the clamps live where the gesture happens (`timeline`, Trim bounds), validation in `draft.js` (`isValid`: a positive point or a box, or no selection at all for a square video without zoom (Square source), `MIN_RANGE ≤ end − start ≤ max_duration`, `start ≤ time ≤ end`).

States by `job.status`: `ready` edits; `done` / `failed` edit a prefilled draft and say so in the status line (resubmitting is allowed); `rendering` is read-only (no handles, no marks input, options disabled, no submit bar) but scrubbing still works to look at the submitted selection. After a successful POST: haptic success and `Telegram.WebApp.close()`; the bot reports progress in the chat.

Status line (owner request 2026-10-26: no empty nodes): two `Swap`s (`src/README.md`, Swap) with `as='p'`, the error (`role='alert'`) and the note (`role='status'`); keep notes short enough for 320 px. An empty text renders nothing, a new text swaps in, the last text leaves animated and its `p` unmounts. Both sit in the editor's fourth grid row (`grid-area: 4 / 1`, `align-self: start`), so when the note leaves while the error comes (a rejected resubmit of a `done` job) they cross-fade in one place instead of stacking for 200 ms. No `min-height` reservation: the status line is the last row and the submit bar is fixed, so nothing below it can move. When it appears it grows like a late row (Late rows); when its last text has left, its `p` goes at once, which only shortens the scroll height.

- Live-region trade-off (accepted by the owner): a region inserted together with its text is announced reliably for `role='alert'` (an alert is announced on insertion), less reliably for `role='status'`, which screen readers watch only once it exists. The old persistent empty `p` pair announced both reliably but cost two empty nodes.
- A rejected submit's error lands in the last row, which is below the fold on a short screen (375 × 667 in the mock): it is announced, but a sighted user has to scroll to see it. Not changed here (layout decision for the owner).

## Render boundaries

The draft lives in the editor, so every draft change renders `Editor`; the children are `memo` and get only what they read, so a change reaches only its consumers. `Viewer` gets `selection` (`time`, `points`, `box`, one `useMemo` object) and `aspect` (a number, Split layout), `look` and `exposure` (numbers, the live preview: `viewer/README.md`, Look preview), `Timeline` gets `start` / `end` / `time`, `Options` gets `meta`, `tier`, `options`, `codec`, the `LEVELS` values (`look`, `exposure`, `stabilize`, `deblur`, `denoise`), `locked`, `readOnly` and `dispatch`. The `<form>` and its `onSubmit` (a new closure every render) are rendered by `Editor`, not by `Options`, so the handler never reaches the `memo`. A trim drag (a `dispatch` per pointer move) therefore renders `Editor` + `Timeline` only, a tap on the video `Editor` + `Viewer` + `Marks`. The playhead never goes through the draft: `time` of the player store is read by `Clock`, `Scrub` and the boolean `useAway` selector (`hooks/player.js`, shared by `Marks` and `Lift`). `Editor` itself is `memo` because `useJob` re-renders `App` on every poll while ingesting (`job` stays null, `notice` is a constant). Do not pass `draft` or an inline object to a child: it defeats the `memo`. Reasoned from the props, not counted with the Profiler.

## Options seam

`OPTIONS` in `draft.js` is the list of render options: `key` (the field in `options` sent to `POST /render`), `label`, `hint`, `needs(meta)`. A new option (stabilization, audio filters) is one more entry plus the backend field; the switch row and the payload follow from the list. Owner request 2026-10-26: a row is **rendered only when `meta` exists and `needs(meta)` is true**; no disabled placeholder rows, no "missing" texts, and nothing while the job loads (the rows that may end up hidden must not flash in). The rows that appear with the job grow in (Late rows). `optionsFor` still sends every key and forces an unavailable one to `false`: a prefilled `job.request` may carry `true` for an option this video cannot have, and the draft keeps it invisibly. Missing keys in the draft read as `false` (`Boolean(options[key])`), so there is no defaults object.

- `zoom` ("Zoom in on the object", owner request 2026-10-26, off by default) lets the camera zoom; off, the note is only the square crop that follows the object (`backend/rounds/README.md`, Zoom option). Shown when `min(meta.width, meta.height) > 640`: a smaller source can never be zoomed into.
- `loudnorm` needs `meta.has_audio`.
- `interpolate` ("Smooth to 60 fps") reads `meta.interpolable`, which the backend decides at ingest (`backend/rounds/README.md`, Output rate); jobs ingested before the field have it undefined, so the row is absent for them.
- `upscale` ("AI upscale", 2026-10-26, contract with the backend session): shown when `min(meta.width, meta.height) < 640`, the same condition the backend applies. The hint's "about 4 min per 10 s" is the backend's L4 measurement at 30 fps (10 s of 384² took 254 s); it doubles at 60 fps. The copy does not branch on the rate on purpose (short hint, no logic for it).
- `metadata` ("Keep original metadata") reads `meta.tags` (the source tags the note can carry, `backend/rounds/README.md`, Note metadata): shown when it has at least one key. Its hint must keep saying that the location travels with the note (privacy: the owner sends notes to other people).
- The sliders are not in `OPTIONS`: they carry a float value each, their own top-level field (`look`, `exposure`, `stabilize`, `deblur`, `denoise`), and come from `LEVELS` (Level rows), rendered after the switch rows. HDR and exposure have no `needs` (every video); noise reduction needs `meta.has_audio` and is sent as 0 for a video without audio.
- The size and codec switches (`hires`, then `hd720`, `hd1080`, `hevc`) were removed for good on 2026-10-26: Telegram delivers any note above 640 as a regular video (`backend/rounds/README.md`, High resolution); the backend ignores the keys in old requests. The codec is its own field (Codec picker).
- The mock (`dev/mock-media.mjs`, 960 × 540 test video) shows every row except `upscale`; the rows that depend on the file (loudness, 60 fps, metadata) always show: the mock has no switches (the Dev panel was removed 2026-10-28). The browser version (`/`) is the way to test other files: a dropped video under 640 px shows `upscale` for a pro session.

## Square source

Owner request 2026-10-26: an already square video needs no selection to become a round. `isValid` in `draft.js` accepts an empty selection (`time === null`) when `meta.width === meta.height` and the Zoom switch is off (`optional`); with zoom on, the object is still required (there is nothing to zoom to otherwise). A selection on a square video is still allowed and sent, the backend just does not track it unless zoom is on (`backend/rounds/README.md`, Square source). The payload is unchanged: `prompt: {time: null, points: [], box: null, mask: null}`; the backend rejects an empty prompt for a non-square video with 422 "Select the object". No copy tells the owner that the selection is optional: "Make round" simply becomes enabled.

## Late rows

The option rows and the status line mount when the job arrives (or later), the codec row on the first render. Two cases, decided once per job:

- The cascade already ran (the usual case: the job takes longer than Telegram's expand, `src/README.md`, Entrance). The rows grow open **together** and fade in one after another from their own mount: `--i` = their index (0, 1, 2…), so no row waits for a long cascade delay. The codec row keeps `--i` = `FIRST_OPTION` (it entered with the cascade, right after the play buttons) and slides down in one motion while the rows above it open; the status line slides with it.
- The job came before `data-enter` (a warm backend on a slow expand). `Editor`'s job layout effect sets `data-early` on the form (`.options[data-early] {--early: 1}`), and the steps become `FIRST_OPTION + index` for the rows (the level rows count after the switches, in `LEVELS` order) and `FIRST_OPTION + rows` for the codec (`late` in `Options`: the switch rows plus the level rows), so the cascade still runs top to bottom. Safe because before `data-enter` no `.enter` animation exists yet, so the delays change before anything started. The inline `--i` is a `calc()` over `var(--early, 0)`, so this needs no state and no re-render. The status line keeps `--i` 0 in both cases (its mount time is inside `Swap`); in the early case a note enters with the viewer, not after the codec. Accepted: rare, and an error or note must never wait 700 ms.

The growth is the `grow` keyframes (`editor.css`) added to the `.enter` animation of `.options-row` and `.editor-status`: `grid-template-rows: 0fr` → the row's `1fr`, with `min-height` and `padding-block` from 0 and a `clip-path` that hides the overflowing content while it opens. 600 ms, `cubic-bezier(0.4, 0, 0.2, 1)`, no delay: the same as `FIT` in `viewer.jsx` (the viewer's height change), so the column moves as one; **change together with FIT**. The fade / blur / scale part keeps `--dur-enter` and the stagger. Owner, recording 2026-10-26 (Firefox 736 × 1036): with the stagger also on the height (700 ms each) the codec moved down in three steps right after the viewer, "not smooth enough".

- Why a CSS animation and not WAAPI from an effect: the viewer measures its own "from" height in a layout effect that runs before any effect of the options; a CSS animation applies its first frame in the same style pass that creates it, so the new rows are already collapsed when the viewer reads.
- The `0fr` trick needs every grid item of the row to have an automatic height: `min-height: 0` on the children and the switch box (`.options-switch`, a plain span, see Switch for why not the input itself) sized by `width` + `aspect-ratio`, not `height`. A grid item with a definite `height` contributes that height to the `0fr` track whatever its `min-height` (minimum contribution, CSS Grid §6.6): with `height: 31px` each row started 31 px tall and the codec jumped 93 px on the first frame (measured).
- `grid-template-rows` interpolates between `0fr` and `1fr` (same track count) in Safari 16+ and Chrome 107+. `calc-size()` / `interpolate-size` are not in Safari.
- Measured in Edge headless with real scrollbars (736 × 1036, `?job=ingest`, rAF samples): the codec row went 559.7 → 709.1 px in one ease-in-out over 600 ms, the three rows' `grow` at the same `currentTime`, the editor width constant at 705 px. With `?job=ready` the first frames after the job are 100–230 ms apart while the video and the filmstrip load, so the motion is choppy there whatever the curve. Reduced motion: no animation, the rows are there at once.

## Codec picker

Owner request 2026-10-26: a radio choice of the note's codec. `CODECS` in `draft.js`: `av1` (the default, first), `hevc`, `vp9` (`key` = the `codec` field of `POST /render`, a top-level field next to `options`: `options` is `dict[str, bool]` on the backend; the keys must match `RenderRequest.codec` and `encode.CODECS`, `backend/rounds/README.md`, Codecs). H.264 and H.266 were dropped on 2026-10-26 (owner). The hints are measured facts (VMAF per MB, HEVC hardware decoding), not guesses. The draft starts from `job.request.codec` when it is still in `CODECS`, else the first entry (`codecOf` in `draft.js`): a stored `h264` or `h266` gets 422 from the backend.

- Markup: one `role='radiogroup'` row (`.options-codec`) inside the form, after the switch rows. Real `<input type='radio'>`s stretched invisibly over each segment (arrow keys, the focus ring through `:has(:focus-visible)`), disabled while loading and for `rendering` (the shared 0.5 opacity).
- Sliding segmented control (owner request 2026-10-26, rebuilt 2026-10-29 after the iPhone recording `IMG_4422.MP4`): the indicator is the `::before` of `.options-segments`. `--n` (the checked index, inline, a registered `<number>`) is the one animated value: it transitions with `--spring` (`index.css`, Springs, about 3 % overshoot, the inertia the owner asked for), and the thumb (`left` from `--at`) and the selected text both read it, so they never drift apart. `--at` clamps `--n` to `0 … --count − 1`, so the overshoot shows between segments but never carries the thumb past the ends (the old `translate` + spring version overshot by about 20 px). Pressing the checked segment shrinks the thumb to 0.95 (UIKit does the same).
- Selected text: `.options-chosen` is an `aria-hidden` copy of the labels in `--segment-text` (the thumb is `--segment`, `src/README.md`, Mono accent), above the thumb (z-index 2; the thumb is 1 and `pointer-events: none`, so the real labels under it still take the taps), clipped by `clip-path: inset(...)` to the thumb's cell from the same `--at`. The colour therefore changes exactly under the thumb's edge as it slides, like UIKit, instead of a whole label recolouring at once.
- Bug it fixes (`IMG_4422.MP4`): the old thumb was a `translate` transition (a composited layer) under `z-index: 1` labels, and on iOS the label of the target segment vanished under the moving thumb until it landed (the "flicker"). Now nothing is composited: a custom property transition runs on the main thread, cheap for one small control, and the paint order is plain z-index. Do not go back to `translate` on the thumb with the labels on top.
- Columns are implicit (`grid-auto-flow: column`, `grid-auto-columns: 1fr`): one per label, so the segment count follows `CODECS` with no CSS change. The old `repeat(4, 1fr)` had to be edited with the list.
- The title and the hint are centred (owner, 2026-10-26): left alignment is for a row with a switch on its right; this row has nothing on the right and its control below. Both `.options-text` and the hint's `[data-swap]` get `justify-items: center`, because `.swap` items are `width: fit-content` and `text-align` alone would not move them.
- The hint under the title is a `Swap` (`as='small'`): the old text leaves (blur, scale down, fade) and is unmounted, the new one enters.
- Checked in the mock (Edge headless, 375 × 667, dark and light, 320 px): the pill slides (translate 0 → 60 % → 86 % → 95 % → 100 % in 60 ms samples), arrow keys move the choice, the old hint is gone after the swap, all disabled for `rendering`, the payload carries the picked codec. After the cut to three (2026-10-26, 390 × 844): AV1 preselected, the pill 118 px = one segment, its left edge on the checked label's at 0 / 100 / 200 %, the title and both hints during a swap centred to the pixel.

## Level rows

The sliders are one component, `Level` in `options.jsx`, driven by `LEVELS` in `draft.js` (owner request 2026-10-26 with the HDR look: no copy-paste of the noise slider). Each entry: `key` (the draft field and the top-level field of `POST /render`), `label`, `min`, `max`, `steps` (the slider's step is `(max − min) / steps`), `zones`, optional `unit` and `needs(meta)` (missing = every video). Order on screen: HDR, Exposure, Stabilize, Deblur, Reduce noise, after the switch rows and before the codec.

- Draft and payload: `init` takes every `key` from `job.request` (default 0); `levelsFor` sends every key, 0 for a level this video does not show (`shows`), so a prefilled `denoise` of a video without audio is never sent.
- Zones: `{to, hint}` per zone; the zone is the first entry whose `to` ≥ the value. The hint is the zone's, so the `Swap` under the title swaps only on a zone change, never per step. `aria-valuetext` is the hint, with the value in front when the level has a `unit`.
- Haptics: `haptic.tick()` (selection changed) when a move crosses a zone border, not on every step.
- Value readout: a level with a `unit` shows its signed value at the right of the title (`<output>`, tabular figures, `−` as the minus sign, one decimal), hidden at 0. Kept out of the `Swap` on purpose: a text that changes every 0.1 would swap (blur, fade) on every step of a drag.
- Look and input: the shared `Slider` (`src/components/README.md`, Slider), owner request 2026-10-27; the native `input type=range` is gone. UIKit look by eye: track 4 px, `--button` fill, `--track` (the switch's off colour) elsewhere, a 28 px `--on-stage` thumb with the switch knob's shadow. A centred level passes `origin` 0, so the fill runs from the middle to the thumb. The row is a `div`, not a `label` (there is no form control to label); the thumb carries `aria-label`. Read-only dims the row (`.options-level:has(.slider[aria-disabled])`).
- Double tap on a centred slider (`min < 0`, the exposure) resets it to 0: the slider's own tap detection (`reset`), not `dblclick`, which WebKit on iOS may not send. The first tap still moves the value to the tapped spot; on the thumb that is where it already is. Checked in the mock (Edge headless, mouse). A double tap during the lock (Slider lock) is ignored.
- Layout: the row's grid has one column (`.options-level`), and its one item is a wrapper span (title + slider) so the `0fr` growth of Late rows still has a single track; measured collapsed height 0.0 for the noise row (Edge headless, before the generic rows).
- Hints are short (≤ 40 characters) so a zone change does not turn one line into two at 320 px and move the rows below.

## Slider lock

Owner request 2026-10-27: the HDR and exposure sliders used to pile up work. Every pause longer than the debounce in a slow drag sent its own `POST /look`, and they ran back to back on the one `Lift` GPU container: the device log showed a burst of about 0.85 s calls. They also delayed `/segment` on the same container. The owner's rule: a drag shows the live preview, and the release locks the slider until the real effect is on screen, so nothing can stack.

- Draft fields, ephemeral, not in `init` (undefined = false): `adjusting` (a level slider is pressed, from `Slider` `onDrag`) and `previewing` (an exact AI frame is debounced or in flight, set by the viewer's `Look`, `viewer/README.md`, Single flight).
- `adjusting` goes to the viewer: while it is true no exact frame is asked; only the live WebGL preview follows the finger. Release → after the debounce one request with the final values.
- `previewing` goes to `Options` as `locked`; only the levels in `PREVIEWED` (`look`, `exposure`) lock, since noise reduction does not touch the picture. A lock only happens when an exact frame is needed: the AI zone of HDR (`look > HONEST`), paused, online. In the honest zone the effect is the synchronous WebGL draw, so there is nothing to wait for and no lock.
- The lock ends when the frame is decoded or the request fails; a request that never answers (a cold GPU) keeps the slider locked until the fetch fails. The fill dims (`components/README.md`, Slider) instead of the 50 % row opacity of read-only, while the thumb keeps its 28 px size, so it reads as "working", not "off".
- Checked in the mock (Edge headless, 390 px, mouse, 2026-10-27): no request during a drag to 0.78, both sliders locked 450 ms after the release, a drag during the lock changes nothing, unlocked with the frame shown after the 600 ms mock answer, 10 arrow-key steps gave one request, no console errors. Not checked on the iPhone.

## HDR slider

Owner request 2026-10-26: one "HDR" slider, 0..1 (`look`, top-level in `POST /render`, backend `look.py`). 0 is off; the first part (`0 < look ≤ HONEST`, 0.4) ramps the honest recovery up to full (local tone mapping that darkens blown highlights and lifts shadows, plus clipped-channel reconstruction); the rest (`HONEST..1`) keeps it full and adds the strength of the AI repair (FastDVDnet temporal denoise + Zero-DCE++ low-light curve), which runs only on the server (`src/constants/look.js`, `split`). Zones: Off, "Recovers highlights and shadows", "AI cleans noise, lifts the dark. Slower"; the zone border is `LOOK.HONEST` itself, so the haptic tick marks where the AI part starts. The viewer shows the effect at once (`viewer/README.md`, Look preview; the AI part as an exact server frame when paused, Exact frame). In the browser version (`job.local`, `local: LOOK.HONEST` in `LEVELS`), anonymous (`local` tier) sessions unlock the slider capped at `LOOK.HONEST` (`0..0.4`, 40 steps of 0.01) so the honest WebGL zone runs locally on the device (`local/look.js`), while `free` and `pro` sessions keep the full `0..1` slider (values up to `LOOK.HONEST` still render locally; values above go to the server: Modal for `pro`, Oracle for `free`, where the AI zone is the Zero-DCE++ curve without the FastDVDnet denoise, `backend/rounds/README.md`, Free look). HDR and exposure are `need: 'free'` since 2026-10-30 (Oracle runs both).

## Submit form

Owner request 2026-10-26: the editor is formally a form we confirm, so it is one. The options block is the `<form id='round' class='options'>` (it replaced the `fieldset`, which had only a visually hidden `legend`), `onSubmit` prevents the navigation and posts the draft. "Make round" is `type='submit'` with `form='round'`: the bar stays outside `.editor` (Submit bar), and the `form` attribute ties it to the form without moving it (Preact sets `form` as an attribute; it is read-only as a property). The viewer and the timeline stay outside the form: they are custom widgets with no form-associated controls, and `<main>` stays the page's landmark (Lighthouse scores `landmark-one-main`; a `<form>` replacing `<main>` would have failed it, a form wrapping `main` would have cost a node).

- Implicit submission: HTML (§4.10.21.2) lets the user agent submit a form implicitly by Enter in a field, by a click on its default button (the first submit button whose form owner it is, here the external one), and does nothing when that button is disabled; which fields trigger it is left to the browser. Measured in Edge headless: Enter on a checkbox or a radio of a form with a submit button submits it (2 of 2); a form with no submit button and no text field does not. So Enter on a switch or a codec segment would have posted the round. `onKeyDown` on the form cancels Enter (`noEnter`), which also cancels the `keypress` that drives implicit submission (UI Events: a cancelled `keydown` suppresses `keypress`). Space still toggles a switch, arrows still move the codec. WebKit's `InputType::shouldSubmitImplicitly` is the same Enter-keypress rule as Blink's (shared origin, reasoned, not run in Safari).
- web.md says Enter in any field submits: that rule is about text fields; this form has none, and the owner wants no accidental submit while toggling.
- Checked in the mock: Enter on a focused switch → no `submit` event, no request; a click on "Make round" → one `submit` and the draft in `window.mockRequests`.

## Safe areas

`.editor` pads itself with `max(env(safe-area-inset-*), var(--tg-safe-area-inset-*))` plus `--tg-content-safe-area-inset-*` (Telegram's own controls over the page in fullscreen, Bot API 8.0). The Telegram script sets those variables and updates them on `safeAreaChanged` / `contentSafeAreaChanged`; outside fullscreen they are 0. `env()` is used only as padding of this element (web-platforms.md: it is not a stable number on iOS). ## Editor scroll

## Split layout

## Submit lock

One press of Make round sends one request, however laggy the first press is (owner 2026-10-29: repeated presses used to start the same render several times). `posting` is state, so two clicks in the same frame both read the old `false` before the re-render disables the button; the guard is `lock`, a ref set synchronously before the first `await` and cleared in `finally`. ## Switch

The option rows are iOS switches built on a real `<input type='checkbox' role='switch'>` (`Switch` in `options.jsx`, styles in `options.css`): the label click, Space, `disabled` (the shared 0.5 opacity of a disabled row) and the perf harness tap (`.options-row input`, the first match is still a switch: the slider row comes after them) keep working natively. The switch styles are scoped to `.options-switch input` so they do not reach the slider's input; the off-track colour and the knob shadow are the `--track` / `--knob` variables on `.options`, shared with the slider. Owner request 2026-10-26 (`IMG_4373.MP4`): "far more Apple-native physics". The model is WebKit's own `<input type=checkbox switch>`, whose constants WebKit says it chose "for consistency with UIKit" (read 2026-10-26, WebKit main `15ab57a`: `html/CheckboxInputType.cpp`, `rendering/cocoa/RenderThemeCocoa.mm`, `rendering/ios/RenderThemeIOS.h`). No library. It replaced a design adapted from the Slider of react-animated-select (one overshooting spring, the thumb dragged 1:1 under the finger).

- Row: a grid (`1fr auto`, one `1fr` row track for Late rows). Box: `.options-switch` (51 × 31 from `width` + `aspect-ratio`, Late rows says why not `height`); the input absolutely fills it (`inset: 0`, `width` / `height: 100%`). The wrapper exists because WebKit on iOS did not take the input's own height from `aspect-ratio`: the track rendered as a thin line with the thumb hanging over it (owner's recording `IMG_4373.MP4`; observed, the WebKit cause not traced; Chromium was fine).
- Geometry and colour (WebKit's legacy iOS path, the UIKit switch before iOS 26): thumb 27 px with a 2 px margin, white (`--on-stage`), shadow `0 2.5px 6px` at 0.12; travel 20 px. Off track: `--hint` at 16 % (light) / 32 % (dark) through `light-dark()` (WebKit: `rgba(120, 120, 128, .16 / .32)`; `--hint` is about that grey in Telegram's themes, so the track follows the theme; `light-dark()` reads the `color-scheme` that `index.html` takes from `--tg-color-scheme`; Safari 17.5, Chrome 123). On track: `--toggle` (WebKit takes `accent-color` over system green; we take the Telegram theme, or system green in the mono accent, `src/README.md`, Mono accent). No inset ring.
- Motion: two registered numbers on the input (`@property`), `--on` (the visual state, 0 / 1) and `--held` (0 / 1), each with its own transition; the thumb is `left: 2px + on × (20px − 8px × held)`, `width: 27px + 8px × held`, so a press grows it toward the centre with its outer edge anchored on either side, and a flip during a press travels the shorter 12 px. `left` / `width` of one absolutely positioned pseudo-element: a layout of that box only. Rejected: `translate` + `width` with per-state curves (a flip and a press change the same property with different springs) and a fixed-size thumb cut by `clip-path` (it clips the shadow too).
- Springs (UIKit, from WebKit): move = mass 1, stiffness 438.65, damping 31.42 (response 0.3 s, ζ 0.75) over `switchAnimationVisuallyOnDuration` 488 ms; press = stiffness 322.27, damping 31.24 (response 0.35 s, ζ 0.87) over `switchAnimationHeldDuration` 507 ms. WebKit clamps the spring to [0, 1], so there is no overshoot: the 2.8 % peak of the move spring is cut, the thumb arrives in about 180 ms and rests. `--move` / `--press` on `.options` are `linear()` curves sampled every 2.5 % (generator: the underdamped step response at `p × duration`, clamped, stopped at 1; regenerate both if a duration changes). The track colour is not a spring: smoothstep `3p² − 2p³` over the same 488 ms, exactly `cubic-bezier(1/3, 0, 2/3, 1)`, on the `::before` opacity. Reduced motion: both durations 0. A reversal mid-flight uses CSS's reversing shortening, the same idea as WebKit's mirrored start offset.
- Haptics: `haptic.tap('light')` (Telegram's impact; WebKit uses UIKit's impact generator) on every visual flip during a drag and on a toggle that did not already flip (tap, hold, label click, Space).
- Kept from before: `[data-press]` and not `:active` (iOS WebKit applies `:active` only with touch listeners), `touch-action: none` on the input, the `matches(':disabled')` check (web.md: inside a disabled `fieldset` `input.disabled` stays false). The hint is a plain `small`: rows are hidden instead of disabled, so a hint never changes and needs no `Swap`.
- Not built: the iOS 26 Liquid Glass thumb (it turns to glass and grows over the track while touched). Apple publishes no metrics for it (HIG, WWDC25 sessions 284, 323, 356), and WebKit's refreshed path draws a plain pill (64 : 28 track, thumb 36 / 64 wide) with no press state on iOS; it could only be copied by eye from a device.
- Checked in Edge headless (mobile emulation, CDP touch and mouse, 2026-10-26): box 51 × 31; tap; hold on the thumb (`data-press` after 200 ms, mid-stretch left 18.2 / width 30.8, right edge at 49), drag across and back (two flips, two haptics, value unchanged on release, thumb back to 22 / 27), drag across and release (off), hold without moving (toggles), mouse drag and click, label click, Space; rows still grow from 0 (Late rows). The feel on the iPhone is for the owner to judge.

## Switch gesture

`down` / `move` / `end` on the label, after WebKit's `CheckboxInputType` (touch: lines 177-228, flip: 473-502, commit: 232-257).

- Touch and pen: nothing tracks for `HOLD` 200 ms (`switchHeldDelay`). Released earlier, it is a tap: toggle. After 200 ms: `data-press` (the stretch), the pointer is captured on the label, and tracking starts from the finger's position at that moment. Mouse: tracking starts at `pointerdown`, no press state (as on the Mac).
- Tracking never moves the thumb under the finger: it flips the visual state with the move spring whenever the finger crosses the threshold, as often as it crosses. The threshold is the middle of the control; only before the first flip, a press that started away from the thumb needs `REACH` 0.4 × width more travel (`flipAt`). WebKit's two conditions are not mirror images (`start > w − h` for a left thumb, `start < w − h` for a right one, which flips a held right thumb at once for a press at 20–25 px); ours are mirrored (`start < h` for a right thumb). Deliberate.
- The visual state differs from `checked` only during a drag: `data-flip` (set while they differ), read by CSS as `:is(:checked:not([data-flip]), :not(:checked)[data-flip])`. `end` removes it and commits in the same task (Preact renders `checked` in a microtask, before the next style pass, so nothing animates twice).
- Commit on release (WebKit's `willDispatchClick`): after at least one flip, the value is the visual state (back where it started = no change); otherwise toggle (a tap, a hold, a drag that never crossed). `pointercancel` commits the same way while tracking (WebKit treats `touchcancel` like `touchend`) and does nothing for an untracked touch.
- We commit on `pointerup` ourselves instead of trusting the native click: iOS may send no click after a long hold or a moved finger. The click that may follow is cancelled in the capture phase (`g.done`; `preventDefault` on a checkbox click restores its state and fires no `change`); keyboard clicks (`detail` 0) and clicks on the label text (their `pointerdown` is not on the input, so `gesture` is null) pass and toggle natively. A new `pointerdown` clears a leftover gesture and its timer.
- Not copied: WebKit's hold timer captures the first touch once (`lazyInitialize`), apparently a bug.

## Tiers

`GET /api/jobs/:id` carries `tier` (`backend/rounds/README.md`, Tiers); the browser version adds a third, `local` (no session), built by `features/web`. Tiers rank `local` < `free` < `pro`; an item in `OPTIONS` / `LEVELS` has `need`: absent (the device can do it), `'free'` (loudness, metadata, noise reduction: Oracle) or `'pro'` (Modal only; "pro" is a convention for what needs Modal, not a paid tier: `CLAUDE.md`, Owner decisions). `locked(tier, item)` returns the `need` while the tier ranks below it. The Mini App only ever sees `free` and `pro`, so for it nothing changed from the former `pro: true` flag. A locked row stays visible but disabled (the shared disabled style), with a badge next to the label ("PRO" for `pro`, "Sign in" for `free`; only the browser version's `local` tier can show the second), and `optionsFor` / `levelsFor` send them as off / 0, so a draft restored from an earlier request cannot post them. These two take the job (`meta` + `tier`), not `meta`. A free job may go without a selection (centre crop, `isValid`); a selection, when given, centres the frame. The server refuses PRO values anyway; the lock only keeps the UI honest. The viewer skips the warm, tap-to-lift and track preview calls on `free` (`viewer/README.md`, Tiers). Any tier but `pro` may go without a selection (`isValid`).

## Editor seams

The editor knows neither Telegram's `close()` nor the browser's local render; two props from its host decide that (2026-10-28, so the browser version reuses the editor without browser code in the Mini App):

- `send(job, body)`: posts the render. `app.jsx` (Mini App) posts to the API and closes the app; `features/web` renders locally or uploads. It throws on failure (the editor shows the message) and the editor resets `posting` after it resolves (the Mini App is already closing).
- `gate(draft, job)` (optional): returns `{network, block, note}`. `block` disables the submit bar, `note` replaces the status line text, and `network: false` keeps the bar enabled offline (a local render needs no connection). Without it the editor behaves as before (`{network: true}`). It runs on every draft change, so it must stay cheap.
- `job.meta.off` (optional, browser only): codecs the device cannot encode; the codec picker disables those radios.
- `job.resume` (optional, browser only): a patch function the job layout effect dispatches instead of `init(job)`, and then it does not seek; the web shell swaps a local job for the server's with it and keeps the draft (`features/web/README.md`, Web promote). `retry` (prop, browser only): after an error the Make round button reads Retry.
- The notice's `local: true` keeps its action button enabled offline (`viewer/README.md`).
- `job.local` (optional, browser only, set by `features/web`): an `OPTIONS` / `LEVELS` item with `local` truthy (`loudnorm`, `metadata`, `denoise`, `exposure`, `look` with `local: LOOK.HONEST`) skips its tier lock for that job, because the device runs it (`locked(tier, item, device)`, `optionsFor`, `levelsFor`, `Options` prop `local`, and `cap` on `Level` when `local < 1`). The Mini App job has no `local`, so its locks are unchanged. Adding an option to the device: set `local: true` (or a numeric cap `< 1`) in `draft.js`, add its key to `LOCAL_OPTIONS` in `local/plan.js`, implement it in `local/render.js` (`local/README.md`).

- Reveal order (owner, recording 2026-10-29): nothing below the video shows before the video has loaded. Options rows, the codec and the Make round bar mount only when the player is loaded (`ready` in `options.jsx`), then wait `--reveal` (600 ms, the viewer's glide, `editor.css`) before their `enter` + `grow`; the stagger runs switches and sliders, then the codec, then the bar (`rowCount` in `draft.js`). Nothing flies across during the split flip any more. `.editor` clips overflow (`overflow: clip`, not a scroller) so the flip never makes scrollbars.

## Glide wait

Owner recording 2026-10-29: the option rows appeared while the viewer was still flying to its place. useGlide in `editor.jsx` collects the running `fit` (viewer) and `flip` (Split flip) animations after each layout commit; until they finish, `Options` gets `ready={false}` (and the submit bar is not rendered), so the rows mount only once the viewer rests, then run the usual cascade. `data-glided` (set once a glide ran) zeroes `--reveal`: the wait for the video was already spent. Without a glide the old `--reveal` delay stays.

In the split layout the options form spans all three grid rows with `justify-content: space-evenly` (Split layout): the panel fills the page height; the status line overlays the bottom of that column (`align-self: end`, no pointer events).
