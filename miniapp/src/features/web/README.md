# web

The browser version's shell (`web-app.jsx`, `result.jsx`, `web.css`): the same editor as the Mini App (`features/editor`) with a local file instead of a server job. Imported only by `src/web.jsx`; `web.css` goes in through `?inline` (`miniapp/README.md`, Inline CSS). Owner decision 2026-10-28: no separate web page; three levels in one editor: anonymous (`local`: whatever the device can do, the round is downloaded), signed in (`free`: plus Oracle, plus sending to the chat), signed in and in `ALLOWED_USER_IDS` (`pro`: plus Modal). Executor priority: device, then Oracle, then Modal (`features/local/README.md`, Local plan).

## Web shell

`WebApp` builds a job from the dropped file: `{id: null, status: 'ready', max_duration: 60, request: null, tier, local: true, lift, follow, file, name, size, meta, proxy_url (blob URL), filmstrip_url, filmstrip}`. `id: null` keeps server-bound viewer features off while `lift` and `follow` run tap-to-lift and video tracking locally (`features/local/README.md`, Local lift, Local tracking; for a `pro` job that already has a server `source.id`, which only a file the device could not read gets, local failure falls back to `POST /api/jobs/:id/segment` and `POST /api/jobs/:id/track`); `tier` is `local` without a session, else the session's `user.tier` (`account/session.js`, `tierOf`). Nothing is shown but the viewer's notice until a file is loaded, like the Mini App while its job loads; the notice carries `local: true` so its button works offline (`viewer.jsx` disables a notice action offline otherwise).

- [DOC: web-local-ai] `lift` and `follow` are built inside the job's `useMemo` by `attachLocal` (`features/local/attach.js`, shared with the Mini App since 2026-11-07, `features/local/README.md`, Local attach), called by the viewer as `(want, report)`: lazy-load the module, pass `confirm(kind)` (the consent card, Web consent) and turn the model download share, the preparation share (`onReady`, `onPrepare`, `onLoaded`, `features/local/README.md`, Model prepare) and the tracking share into `report({label, share})` with the three `LABELS` of that kind (downloading, preparing, busy); the viewer draws it on the point (`viewer/README.md`, AI progress). There is no `.web-sync` line any more (owner 2026-10-29). `follow.stop` aborts a local preview track (`viewer/README.md`, Follow confirm). For `pro` with a server `source.id` fall back to the server route (`segment`, `track`) on a local failure. `lift` and `follow` run inside `awake` (a screen Wake Lock, `features/local/README.md`, Local awake), as does the render (its card shows "Following the object…" during the tracking stage, `features/local/README.md`, Render progress); `follow` always exists (no feature is ever switched off after a crash, Track guard); with WebGPU it is fast, without it it runs on the CPU (slow, same memory rules).
- Speed gate (`features/local/README.md`, Speed gate): the job has a `fast` getter (`fast()` of `models.js`, attached when the shell imports that module on mount; `undefined` before, which counts as not slow). On a slow touch device `follow` on `pro` goes straight to `POST /api/jobs/:id/track` when the job already has a server id (the label shows the busy text; the server sends no shares), else it tracks locally with VitTrack; `needsServer` sends the render of a `pro` selection to the server there. The check inside `attachLocal` imports `models.js` instead of reading the `device` ref, because oxlint's `react(refs)` flags a ref read in a function built during render.
- Signing in or out changes `tier`, so the job object is rebuilt and `Editor` resets its draft (it reinitialises on job identity): the trim and the selection are lost, so sign in before them. Keying the effect on `job?.meta` worked but oxlint's `exhaustive-deps` warns about it.
- Replacing the file: a new drop revokes the old blob URLs and re-probes; a result card open or a render running blocks it.
- Automatic server fallback on probe failure: when local probe fails (e.g. unsupported codec like ProRes or corrupted stream) and the user is signed in (`user != null`, online, `<= 2000 MB`), the shell skips the blocking error and immediately hands the file over to server preparation (`prepare(file, say, tier !== 'pro')` via Oracle or Modal), where FFmpeg generates the proxy video and filmstrip. The upload text replaces the "Preparing the video…" notice's text meanwhile.

## Web drop

The drop zone is the whole `.viewer` (owner): the wrapper handles `dragover` / `drop` for anything carrying files, always calling `preventDefault` (a drop outside the viewer must not make the browser open the file) and accepting the file only when the event target is inside `.viewer`; the viewer gets an inset ring while a file is over it (`data-over`). A click on the empty viewer's "Choose a video" button opens the file input (`accept='video/*'`, but a file with an empty `type` is still tried: the probe decides). The input is held in state, not a ref, because oxlint's `react(refs)` rule flags a ref read inside a callback that ends up in the rendered notice.

## Web result

A modal card over the editor (`result.jsx`): grows out of what opened it and shrinks back into it over a dimmed, blurred backdrop (Web morph); while the work runs, its text and progress (rendering, uploading); when a local AI model needs a first-use download (`consent`, `features/local/README.md`, Local models), a confirmation card (Web consent), followed by byte progress on the point (`viewer/README.md`, AI progress); afterwards, for a local round, a looping preview in a circle (a tap toggles sound), the size, Download (`<a download>` of the blob URL), Send to Telegram for a signed-in user (`POST /api/notes`; `held: true` in the answer means Telegram refused because the user restricts voice and video messages, and the card says to allow the bot and press Resend in the chat) and Another video / Close; for the server path, only the "sent to the server, the round arrives in your chat" line. When Modal was unavailable and the round was made on Oracle instead, the status line says so and lists what was left out (`dropped`, `features/local/README.md`, Modal fallback). A failure goes to the editor's own error line (the shell rethrows from `send`), so it is announced like a Mini App error.

## Web progress

The work card's bar and percent (`Bar` in `result.jsx`) are written straight to the DOM from a rAF loop, never through React state: the `progress` gets its initial value only (a constant prop, so Preact never overwrites the DOM value) and the percent text is set by `textContent`. The shown value eases toward each new `work.share` (`EASE` 180 ms, exponential) and, between sparse reports on a slow device, creeps on at the recent rate (the last step over the time it took), capped at 0.9 of the last step and at `CREEP` 0.03 above the real value; at 100 % it does not creep. It never goes backwards, and a drop of more than 0.3 is a new job and resets. With `prefers-reduced-motion` it jumps to the value. The loop stops once settled and restarts on the next report. `keyOf` leaves `share` out of the work key; it only decides when `prev` is kept, the card is never remounted per update.

Expected input: `share` in 0..1, non-decreasing within a job, reported as often as the work yields (per frame, not batched).

## Web morph

Owner request 2026-10-29, reworked the same day after the iPhone recording `IMG_04161.MP4` ("a rectangle appears from nowhere and the text is spat out"): the card grows out of what opened it, like a shared element transition, and shrinks back into it. Everything is WAAPI in `morph.js` (`useMorph`, `useScrim`); `result.jsx` only says where each card comes from (`ORIGINS`, a list of selectors tried in order: the tapped point or the box for the selection model, the Follow pill then the point for the tracking model, the Make round button for work and result; the crash card has none).

- Grow (`GROW` 640 ms, `--spring` from `index.css`, about 3 % overshoot): the card is laid out at its real size and animated by `transform: translate` (from the origin's centre) plus `clip-path: inset(... round r)`, never `scale`, so the text inside is never squeezed. Its fill starts as the origin's colour (the blue point) and turns into the card's own in 300 ms (`TINT`).
- [DOC: web-morph-circle] A circular origin passes through a middle keyframe (`ROUND` 0.38 of the way): a circle of 0.6 × the card's short side (`CIRCLE`), 40 % of the way from the point (`TRAVEL`). Without it the radius grew linearly from 11 to 22 px while the size grew 15 times, so the dot turned into a square almost at once (filmed frame by frame in headless Edge). "Circular" means a radius of half the short side, so a stadium counts too: the Follow pill and, since the web Make round became a floating pill (Web pill), the stacked layout's button. A rounded-rectangle origin (the split layout's inline button, another card) goes straight to the card.
- Content: every child of the card fades and rises in (`LIFT`: opacity, 12 px, 0.97, a 6 px blur) from 32 % of the grow (`REVEAL`, "halfway"), 50 ms apart (`STAGGER`).
- [DOC: web-morph-scrim] Dim, blur and transparency are one layer: `.web-backdrop::before` holds the tint and `backdrop-filter: blur(18px) saturate(1.4)` at full strength and only its `opacity` is animated (WAAPI with `pseudoElement: '::before'`), by `useScrim` in `Result` with the card's duration and Apple's sheet curve (`SETTLE`). Animating the blur radius itself (the old `web-backdrop-enter`) and running it on a 300 ms CSS transition beside a 480 ms card is what looked torn. The backdrop element lives in `Result`, not in each card, so switching cards (work → result) does not flash the scrim.
- Leave: the current animated values are read (`getComputedStyle`), the running animations cancelled, the content fades in 140 ms, and the card goes from where it is now through the circle back into the origin, measured again (the point may have moved), with an accelerating curve (`EXIT`, `SHRINK` 380 ms) while its fill turns back into the origin's colour; the scrim fades over the same 380 ms. So a card closed halfway through its grow reverses from that point without a jump. `usePresence`'s ref sits on the card (`host` in `result.jsx`), so the unmount waits for the card's own animations; `data-closing` on the backdrop stops it from catching taps meanwhile.
- [DOC: web-morph-handoff] When one card replaces another while open (work → result, consent → work), the old card's cleanup stores its box (`handoff`, module state in `morph.js`, one modal host) and the new card grows from it instead of from the origin. `Result` clears it once nothing is mounted.
- No origin on screen or reduced motion: a plain fade and scale (0 ms with reduced motion).

## Web pill

[DOC: web-pill] In the browser version the fixed Make round bar of the stacked layout (`editor/README.md`, Submit bar) is a floating pill, like the bottom tab bar of the react-animated-select demo (`apps/demo/src/menu/README.md`, Mobile bottom bar): no full-width `--bg` band, the bar box is only the button, `width: min(88%, 688px)` centred, `bottom: max(8px, env(safe-area-inset-bottom))`, the button a stadium (`--pill`) with a drop shadow. The Mini App keeps the opaque band: Telegram has no browser toolbar under it. Only `.web` scopes it (this file is loaded only by the browser shell); the split layout's inline button is untouched (`:not([data-inline])`).

- Why: Safari 26 (and in-app `SFSafariViewController`) samples the middle of the bottom edge 4 px inside the layout viewport and walks up to the first fixed or sticky box; a box found there with a background makes Safari replace its translucent toolbar glass with an opaque slab of that colour, and it keeps that element while it stays visible (`claude-rules/web-platforms.md`, Safari 26 colours the area under its toolbar). The old band, `inset: auto 0 0` with an opaque background, was exactly that box, so the glass under the toolbar broke while the button was shown (owner, 2026-11-07).
- Invariant: nothing of the bar may come within 4 px of the bottom edge, not even for one frame. The 8 px gap is the guard (the 88 % width is not: shipped iOS 26 was reported to accept 80 %-wide boxes). The bar has no bottom padding, so its own box ends where the button ends. The `enter` animation is a fade with `scale: 1.06` (1.5 px on a 50 px button), no translate, so it never crosses the edge.
- `env()` reaches only the bar's own `bottom` through `max()`, never `--bar` (the editor's reserved bottom space): iOS reports the inset as 0 or about 34 px depending on the toolbar state. The pill (8 + 50 px, or inset + 50) stays inside the reserved `--safe-bottom + --bar` (66 px + inset), so the last row still scrolls clear of it.
- Not verified on a phone: the glass under Safari's toolbar with the pill shown, the pill above the home indicator with the toolbar collapsed (XR).

## Web toolbar

[DOC: web-toolbar] When a card opens, the area under Safari's toolbar (and under the top bar) dims and blurs with the scrim in step, frame for frame, instead of keeping the undimmed page or a slab of Safari's choosing. The recipe is the shelf lightbox's (`shelf-sharing-webapp/src/app/components/README.md`, Lightbox toolbar, final version of 2026-10-17; `claude-rules/web-platforms.md`, A full-screen modal over the iOS 26 Safari toolbar).

- The fixed `.web-backdrop` was a viewport-sized fixed box with no background colour of its own at the bottom edge: Safari reads such a box as a dimming layer and paints a colour view sampled from the page, which lags the fade (sample-and-hold, 90–110 ms in the shelf recordings) and is flat (no blur). And every fixed layer is clipped at the layout viewport, so a fixed scrim never reaches under the bars in an in-app browser, where the area under the toolbar is live page.
- Fix, WebKit only (`@supports (-webkit-backdrop-filter: none)`, true in Safari, false in Chromium and Firefox, which keep the fixed backdrop): while a card is open nothing is fixed at the middle of the top or bottom edge, so Safari makes no colour view and the bars show the live page, which is the scrim itself. `.web-backdrop` is `position: absolute` at `top: var(--web-y)` with `height: 100dvh`; `useScrim` (`morph.js`) sets `--web-y` to `scrollY` on mount, before paint, and `data-modal` on `<html>`, which locks the page (`overflow: hidden`, so the absolute backdrop cannot scroll away). Its containing block is the initial one: no ancestor of `Result` (`.web`, `#root`, `body`) may become positioned or get a `transform`, `filter` or `backdrop-filter`.
- The scrim `::before` reaches 160 px beyond each edge (`inset: -160px 0`), and paints two layers: the dim (`--scrim`, as a gradient layer, because `background-color` paints under the images) over a `--bg` gradient that is opaque in the 160 px outside the layout viewport and fades out 40 px inside it. Under the bars the page is flat `--bg` dimmed by the scrim, and the blurred page fades into it, with no seam at the viewport line. Only the `::before` opacity is animated (Web morph), so the strip under the toolbar follows the scrim with no lead and no loop.
- The pill fade (`[DOC: web-pill-fade]` in `useScrim`): the floating Make round pill near the bottom, seen through the blur, would be a dark patch over the toolbar line (shelf's popup, `IMG_0332`). It fades out with the scrim's duration and curve and back on close (its opacity is `1 −` the scrim's on every frame, WAAPI `id: 'scrim'`, cancelled and restarted from the current value like the scrim). The Work and Result cards still grow out of it and shrink back into it (Web morph); the origin is measured by its rect, which opacity does not change.
- `::backdrop`-style inheritance is not involved: `.web-backdrop` is a plain element, so the variables reach `::before` in every engine.
- Not verified on a phone: Safari and an in-app browser (a link opened from Telegram), open and close, at the page top and scrolled. Expected: the strip under the toolbar dims and blurs like the page above it, in step, and the Make round pill fades with the scrim.

## Web consent

[DOC: web-consent] The model download card says what is downloaded and why (owner 2026-10-29): per kind (`lift`, `follow`, from `confirm(kind)` in the shell) a title, what the model does for the user, the files with their sizes (`models` from `loadModels`, names mapped by `PARTS`), the model and its origin from the first file's `credit` (`local/weights.js`: SAM 2.1 Tiny, or EdgeSAM with its non-commercial licence on touch devices, `local/README.md`, Lift model), "from Hugging Face", the total, and that it runs on the device and stays cached for offline use. Consent is per model now (`approved` is a set of names in `local/models.js`), so the tracking model asks on its own instead of riding on the selection model's yes.

## Web crash

[DOC: web-crash] After the tab died during a model call (Safari reloads it; `crashed` from `local/models.js`, `features/local/README.md`, Track guard), the shell imports `models.js` on mount and opens a crash card in `Result` (`crash: 'gpu' | 'wasm'`, before work and result, after consent). Owner 2026-10-29: never slow the work down behind the user's back, offer it. The card is one title ("The page restarted") and one sentence (owner 2026-10-29: the first version with a list of tips was too wordy). After a `gpu` crash the sentence says it was most likely memory and offers "Use the processor" (`preferCpu()`, for this tab) or "Keep the graphics card"; after a `wasm` crash it says to close other apps and tabs, with OK. The private-tab tip was dropped: that Private Browsing keeps the Cache API (the models included) in memory is reasoned from WebKit's ephemeral sessions, not measured. The memory cause is confirmed by jetsam logs from both the SE2 and the XR (`highwater` at about 1.54 GB, `BUGS.md`, iPhone reload on tracking; `features/local/README.md`, gpu-buffer-cache), but a reload can have other causes, so "usually" is deliberate.

- Safari's own "Reduce Protections" banner after the reload (owner, iPhone SE2) is its generic prompt for Advanced Fingerprinting Protection, which Private Browsing turns on; it does not touch memory, so the card does not send users there.
- No origin for the morph (nothing opened the card), so it uses the plain CSS enter.

## Web same render

[DOC: web-same-render] `send` remembers the last finished render (`last`: the file, `JSON.stringify(body)`, and the result: the blob, or `remote`). Make round with the same file and the same body shows that result again (a new blob URL, `again: true`, a line saying nothing was rendered twice; for the server path "Already sent with these settings") instead of rendering again. With the editor's submit lock and the server's dedupe (`editor/README.md`, Submit lock) one round is never made twice by accident. Any change of the body renders again. Loading another file clears `last` at once: its key can never match again, and it would keep the old round's blob (up to 10 MB) alive until the next render.

## No background upload

Nothing leaves the device before Make round (owner 2026-11-06: no bot or Modal work that the render does not need; Modal credits are short). The server is reached only by Make round when `needsServer` says the device cannot do the render (`features/local/README.md`, Local plan), or on load when the device cannot read the file at all (Web shell, server fallback).

- Removed: the "Web promote" upload, which sent every file a `pro` user loaded to Modal at once so that the server lift, track and HDR preview were ready. Each such upload opened a status message in the chat, ran Modal's `ingest` (proxy and filmstrip) and ended with the bot's "Ready. Open the editor" message, before the user had decided anything (observed in headless Edge, 2026-11-06: `POST /api/uploads` right after the file loaded, nothing on the toggles; the bot side read in `backend/rounds/files.py` `new_job` and `pipeline.py` `ingest_job`). The job swap that kept the draft (`resume`, `CARRY`) went with it.
- What `pro` loses in the browser: the server fallback for a failed local lift or track, the server track on a slow touch device (it tracks with VitTrack on the device instead; the render still goes to Modal, Speed gate) and the exact AI frame of the HDR preview above `LOOK.HONEST` (the honest part previews locally). A job that came from the server fallback has an id and keeps all three.
- On Make round, a render that needs Modal (`needsModal`) uploads to Modal (or uses the job of the server fallback); one that needs the server but not Modal goes to Oracle with `?via=oracle` (Oracle first, owner 2026-10-28).
- Retry: after a failed Make round the button reads Retry (the `retry` prop of `Editor`, passed only here; the same submit runs again), and the result card's Send button reads Retry after a refused or failed send.
